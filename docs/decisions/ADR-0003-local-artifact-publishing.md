# ADR-0003: артефакты ядра публикуются локально, GitHub — только хранилище репозитория

## Контекст

Решение [ADR-0001](ADR-0001-shared-core.md), пункт 4, выбрало публикацию в GitHub Packages, а проверки выполнялись в GitHub Actions. Опыт двух месяцев показал цену этого выбора для одного разработчика:

1. Проверки в Actions были выключены с 10 июля по 6 сентября, и никто этого не заметил; каскад накопленных отказов разбирался отдельной задачей.
2. Обязательные проверки статуса для приватного репозитория недоступны на бесплатном плане: `403 Upgrade to GitHub Pro or make this repository public`. То есть проверки в Actions не могли ничего запретить и служили сигнализацией.
3. Registry требует учётных данных на каждой машине сборки. У машины production-деплоя их нет: она клонирует коммит и собирает бэкенд сама, а `settings.xml` с токеном на ней не настроен. Значит зависимость от registry делает деплой зависимым от секрета, которого там нет.
4. Разработчик один. Ценность общего сервера сборки — согласование между людьми — не возникает, а стоимость остаётся: очередь, минуты, дублирование команд между `mise` и workflow.

## Решение

Решение владельца от 2026-09-07: GitHub остаётся хранилищем репозитория и ничем больше.

1. Артефакты ядра публикуются локально: Java-артефакты устанавливаются в локальный репозиторий Maven, npm-пакет собирается архивом. Версия по-прежнему берётся из тега.
2. Потребитель фиксирует версию ядра ссылкой на коммит или тег и получает артефакты, собрав ядро из этого состояния одной командой.
3. Всё, что можно проверить и собрать локально, делается локально. Машина production-деплоя забирает коммит и выполняет ровно те же команды.
4. GitHub Actions не используются ни для проверок, ни для публикации; workflow удалены из обоих репозиториев.

## Последствия

Плата за решение названа прямо:

- проверки выполняются, только если их запустили; шлагбаумом становится локальный хук, а не сервер;
- следа «на этом коммите проверки прошли» в удалённой системе не остаётся; доказательством служит прогон у разработчика и результат сборки на машине деплоя;
- сборка под amd64 из машины разработчика на ARM64 не проверяется; риск принят: бэкенд и интерфейс архитектурно нейтральны, артефакты агента кросс-компилируются под оба таргета и проверяются через `qemu`.

Взамен исчезают: зависимость сборки от учётных данных registry, очередь и минуты, дублирование набора проверок между `mise` и workflow, и необходимость платного плана ради шлагбаума.
