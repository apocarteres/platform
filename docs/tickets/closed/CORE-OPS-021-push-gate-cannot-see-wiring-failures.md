# Шлагбаум перед отправкой не видит отказов проводки

## Проблема

`REQ-QUALITY-002` держит `check` быстрым и оставляет в нём документацию,
правила, модульные тесты и статический разбор. `REQ-QUALITY-003` относит
интеграционные тесты к `verify`. `REQ-QUALITY-004` ставит шлагбаум перед
отправкой на `check`. Значит класс отказов, который виден только при подъёме
приложения — проводка бинов, условные конфигурации, миграции, транзакционные
границы — по построению не мешает отправке в origin.

## Чем подтверждено

Случай в проекте `zavpn` 2026-09-10. Бины двух шифров были объявлены в
конфигурации, помеченной `@ConditionalOnWebApplication`. Веб-приложение
работало, `check` был зелёным, изменения ушли в origin. При этом не-веб
рантайм — админская команда провижининга — не поднимался вообще: бина нет в
контексте. Отказ нашёлся только при ручном прогоне профиля интеграционных
тестов, уже после отправки.

Потребитель закрыл конкретный класс статическим разбором: architecture test
запрещает объявлять бин проектного типа в web-условной конфигурации. Это
работает для одного вида проводки и не отвечает на общий вопрос.

## Последствия при сохранении текущего поведения

Зелёный `check` читается как «можно отправлять», хотя приложение может не
запускаться в одном из своих рантаймов. Каждый потребитель платформы приходит
к этому выводу самостоятельно и своей ценой: сначала отправкой сломанного
состояния, потом ручным прогоном.

## Ожидаемый результат

Правила говорят прямо, что `check` не покрывает отказы уровня подъёма
приложения, и называют средство: либо быстрая проверка проводки в составе
`check` (подъём контекста без внешних зависимостей — секунды, а не минуты),
либо обязательная расписка `verify` для отправки, либо явная запись, что этот
класс отказов ловится только `verify` и отправка без расписки допускается на
свой риск.

## Критерии приёмки

- Требования называют, какой набор отвечает за отказы проводки и подъёма
  приложения.
- Если выбран вариант с проверкой в `check` — она остаётся в пределах минут и
  не требует внешних служб.
- Потребителю не нужно догадываться о разнице между зелёным `check` и рабочим
  приложением.

## Ход выполнения

### Шаг 1 (2026-09-10)

Решение владельца: первый вариант из ожидаемого результата — быстрая проверка
проводки входит в состав `check`. Обязательная расписка `verify` для отправки
отклонена как замедляющая отправку; явная запись «на свой риск» — как честная,
но проблему не решающая.

`REQ-QUALITY-012` называет проверку проводки: контекст приложения каждого
рантайма поднимается без внешних служб — без базы, брокера, сети и учётных
данных. Рантаймом считается каждый способ запуска: веб-приложение, консольная
команда, обработчик очереди; у библиотеки — контекст с её автоконфигурацией.
`REQ-QUALITY-002` включает проверку в `check`, `REQ-QUALITY-003` уточняет
границу: в `verify` уходят интеграционные тесты, которым нужны внешние службы,
а тест, обходящийся без них, живёт в `check` — иначе из-под шлагбаума выводится
то, что проверяется за секунды.

Правило не осталось текстом: потребителям объявлено обязательство
`wiring-check` (директива, `REQ-QUALITY-012`, начиная с 1.3.0, срок 2 выпуска).
При открытии выпуска оно материализуется задачей с перечнем требуемого и
критериями приёмки, а незакрытым будет видно на каждой проверке правил по
`REQ-RELEASE-035`.

Само ядро правилу удовлетворяет уже сейчас: автоконфигурации `platform-time` и
`platform-persistence` проверяются `ApplicationContextRunner` — контекст
поднимается без внешних служб, — а эти тесты входят в `check` через задачу
`java-test`. Отдельной работы в ядре правило не потребовало.

### Результаты проверок (2026-09-10)

| Прогон | Результат |

| `mise run check` | 107 документов, 276 положений, правила соблюдены, Java-сборка успешна |

| Обязательство у потребителя | на фикстуре материализуется задачей `TICKET-ADOPT-WIRING-CHECK` с полем `obligation: wiring-check` |

### Что не покрыто

Ядро не проверяет, что потребитель действительно поднял контекст каждого
рантайма: перечень рантаймов знает только потребитель, и ядро по своему
назначению его не знает. Механизм здесь — обязательство со сроком и заготовкой
задачи, а не автоматическая проверка. Это осознанная граница, а не упущение:
`REQ-RELEASE-035` делает незакрытое обязательство видимым на каждом прогоне, а
просроченное — роняющим проверку.
