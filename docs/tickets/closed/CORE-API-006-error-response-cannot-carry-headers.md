# Ответ об ошибке не может нести заголовки

## Проблема

`ApiErrorAdvice` возвращает `ProblemDetail` — то есть только тело. Ответ об
ошибке не может нести `Retry-After`, `WWW-Authenticate` и прочие заголовки, без
которых статус неполон: `429` без `Retry-After` сообщает об отказе, но не о
том, когда повторять.

Потребителю приходится оставлять локальный обработчик, хотя общий отказ он в
статус не отображает — он лишь ставит заголовок.

Вторая половина заявки — про собственные поля расширения — относится к
`CORE-API-004`: та же потребность пришла и от второго потребителя, и её
подтверждение записано там.

## Чем подтверждено

Заявка потребителя `clanlog` от 2026-09-11, ядро 1.6.0:
https://github.com/apocarteres/platform/issues/1

Потребитель исполнил обязательство `web-errors` полностью: убраны 50 локальных
обработчиков и 22 собственных типа тела ошибки, коды сверяются проверкой в
наборе. Остались два обработчика: один ставит заголовок — о нём эта задача, —
второй добавляет поля, и о нём `CORE-API-004`.

Проверено по коду ядра: `HttpHeaders` и `ResponseEntity` в
`platform-web-errors` не упоминаются ни разу.

## Последствия при сохранении текущего поведения

1. Ответ со статусом, требующим заголовка, остаётся вне контракта, и клиент
   разбирает два формата вместо одного — ровно то, ради чего контракт вводился.
2. Потребитель, исполнивший обязательство, формально остаётся нарушителем
   `REQ-API-005`: положение читается как запрет любого локального обработчика.
3. Каждый следующий потребитель напишет свои два обработчика заново.

## Ожидаемый результат

Ответ об ошибке несёт заголовки, не требуя локального обработчика.
Формулировка `REQ-API-005` отделяет обработчик, отображающий общее исключение
в статус, от обработчика, который добавляет к ответу то, чего контракт пока не
выражает.

Предложение заявителя принято за основу: отказ, уже являющийся `ErrorResponse`
платформы приложений, пропускается со своими заголовками и дополняется
расширением `code`. Проверить при разборе: покрывает ли это случай заявителя —
его исключение ограничителя частоты может `ErrorResponse` не реализовывать, и
тогда заголовки должен уметь отдавать порт.

## Критерии приёмки

- Ответ об ошибке может нести заголовки; случай `429` с `Retry-After`
  закреплён тестом на собранном конвейере.
- `REQ-API-005` различает два вида локальных обработчиков.

## Ход выполнения

### Шаг 1 (2026-09-11)

Совет по ошибкам возвращает `ResponseEntity<ProblemDetail>` вместо голого тела
и собирает ответ из трёх источников: обязательные поля и `code` — ядро, поля
расширения — порт `ErrorExtensions`, заголовки — заголовки исключения
платформы приложений плюс порт `ErrorHeaders`. Без объявленных портов ответ
прежний.

Портов сделано два, а не один: заголовок и поле тела — разные части ответа, и
сервису, которому нужен только `Retry-After`, незачем объявлять порт,
говорящий о теле.

Нормативный текст: `REQ-API-007` (поля расширения) и `REQ-API-008`
(заголовки). Заодно уточнён `REQ-API-005` по замечанию заявителя: запрет
касается обработчика, который отображает исключение в статус или вводит свою
форму тела; обработчик, добавлявший то, чего контракт не выражал, запретом не
охватывался — и теперь не нужен.

### Результаты проверок (2026-09-11)

| Прогон | Результат |
| --- | --- |
| Тесты модуля | 12 в трёх файлах, из них 4 новых на порты |
| `mise run check` | 128 документов, 296 положений, правила соблюдены, сборка успешна |
| Тесты пакета правил | 151 из 151 |

Новые тесты проверяют: порт заголовков ставит `Retry-After` на `429`;
заголовки рамочного исключения доходят без порта; порт расширений кладёт
`requestId` и `available` рядом с `code`; без портов ответ прежний, и тип
содержимого остаётся `application/problem+json`.

### Что до заявителя

Проверено, о чём говорилось в задаче: пропуск заголовков исключения платформы
приложений покрывает случай, только если исключение реализует `ErrorResponse`.
Поэтому сделано и второе: порт `ErrorHeaders` работает с любым исключением
сервиса, в том числе с его собственным исключением ограничителя частоты.
