# Сериализатор команд требует Jackson 2, которого в платформе приложений уже нет

## Проблема

`JsonSqlCommandWriter` написан на Jackson 2, а его автоконфигурация включается
по условию наличия класса `com.fasterxml.jackson.databind.ObjectMapper`
(`REQ-PERSISTENCE-012`). Четвёртая версия платформы приложений поставляет
Jackson 3 и поддержку Jackson 2 из автоконфигурации убрала.

У потребителя порт `SqlCommandWriter` существует ровно до тех пор, пока Jackson 2
кто-нибудь тянет транзитивно. Условная регистрация при этом молчит: бина просто
нет, и обнаруживается это не при сборке, а при первом обращении к DAO, которому
нужна сериализованная команда.

## Чем подтверждено

Заявка потребителя [issue #6](https://github.com/apocarteres/platform/issues/6),
ядро 1.7.0. Дерево зависимостей `clanlog` 2026-09-12 показывает единственный путь
к `jackson-databind` — через библиотеку документации API:

```
\- org.springdoc:springdoc-openapi-starter-webmvc-ui:3.0.3
   \- ... \- com.fasterxml.jackson.core:jackson-databind:2.21.5
```

В самом ядре зависимость объявлена `optional`, у потребителя не объявлена вовсе.
Собственную сериализацию потребитель перевёл на Jackson 3 в начале сентября:
после этого Jackson 2 не нужен никому, кроме библиотеки документации и —
косвенно — сериализатора ядра.

## Последствия при сохранении текущего поведения

Слой доступа к данным зависит от того, притащит ли посторонняя библиотека
устаревшую версию чужого сериализатора. Потребитель не может ни убрать Jackson 2
из сборки, ни объявить его своей зависимостью честно: он ему не нужен. Условие
`REQ-PERSISTENCE-012` описывает эту зависимость как штатную, то есть правило
закрепляет дефект.

## Ожидаемый результат

`SqlCommandWriter` работает в сборке, где Jackson 2 нет вовсе, и не зависит от
версии чужого сериализатора. Формат команды остаётся прежним: имена полей,
даты в ISO-8601.

## Критерии приёмки

- Сериализация команд работает без Jackson на classpath.
- Порт регистрируется всегда; условной регистрации по наличию библиотеки нет.
- Несериализуемое значение отказывает с указанием типа команды и поля
  (`REQ-PERSISTENCE-010`).
- Формат прежний: проверено на записи с датой, идентификатором, перечислением,
  вложенной записью и списком.

## Откуда пришла задача

Заявка потребителя [issue #6](https://github.com/apocarteres/platform/issues/6):
задача `CL-DATA-017` в `clanlog`.

## Что сделано

Сериализатор команд написан без внешней библиотеки: запись обходится по
компонентам, отображение — по строковым ключам, набор — по элементам; строка,
число, признак, идентификатор, перечисление и момент времени пишутся напрямую.
Даты остались в ISO-8601 — формат сохранён вплоть до секунд, которые
стандартное строковое представление `OffsetDateTime` опускает, когда они нулевые.
Это поймал тест на прежнем ожидании, а не читатель кода.

Условная регистрация отменена: порт объявляется всегда и ничего не требует на
classpath. Зависимости от Jackson в `platform-persistence` больше нет ни в каком
виде.

**Сужение поведения, о котором сказано потребителям.** Прежний сериализатор брал
и обычные классы с методами чтения. Новый принимает закрытый перечень
(`REQ-PERSISTENCE-009`) и на всём остальном отказывает с указанием команды и типа
значения (`REQ-PERSISTENCE-010`). Команды обоих потребителей — записи и наборы
записей, поэтому переход для них ничего не меняет; проект, передающий в порт
обычный класс, увидит отказ сразу, а не молчание.

Закреплено семью тестами: порядок полей записи, дата в прежнем формате,
отсутствие значения, экранирование кавычек и управляющих знаков, ключи
отображения, отказ на неподдерживаемом значении, работа без чужой библиотеки на
classpath. Проверка автоконфигурации переписана с «без Jackson порта нет» на
«порт есть без чужих библиотек».
