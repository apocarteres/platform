# Telegram: связь учётной записи с ботами проекта и уведомления

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: служба на Spring Boot с аутентификацией ядра и её одностраничный клиент, подключившие Telegram.** Ядро поставляет модуль библиотекой: starter `platform-telegram` и пакет клиента `@apocarteres/telegram`. Модуль необязателен: проект без него требованию не подлежит. Решение владельца от 2026-11-16: Telegram — подключаемый модуль ядра, по этапам — связь, уведомления (`CORE-ARC-031`), вход из Mini App (`CORE-ARC-032`), вход на сайт и второй шаг (`CORE-ARC-033`). Документ описывает все четыре этапа — связь, уведомления, вход из Mini App и вход на сайт со вторым шагом. У приложения может быть несколько ботов — указание владельца от 2026-11-16 (`CORE-ARC-034`): всё, что модуль делает, он делает по боту.

**Уровень требования: директива.**

Связь хранит идентификатор человека в Telegram и номер его личного чата с ботом — персональные данные по 152-ФЗ. Учётная запись без почты модулем не заводится: связь всегда принадлежит учётной записи ядра (`REQ-AUTH-001`).

## Модуль

1. <a id="REQ-TELEGRAM-001"></a> **REQ-TELEGRAM-001** — Модуль строится поверх аутентификации ядра (`REQ-AUTH`): связь принадлежит учётной записи ядра. Таблицы создаёт журнал ядра `platform/changelog/platform-telegram.yaml`, который проект подключает в главный журнал Liquibase после журнала `platform-auth` (`REQ-DATA-ACCESS-007`); образцы `sql/platform-telegram/create-*.sql` — справка.
2. <a id="REQ-TELEGRAM-002"></a> **REQ-TELEGRAM-002** — Боты проекта объявляются по идентификатору — `platform.telegram.bots.<бот>.*`, идентификатор — строчные латинские буквы, цифры и дефис, до 16 знаков: `token` — токен бота, `name` — имя бота без `@`, `webhook-secret` — секрет webhook, от 32 до 256 знаков из латинских букв, цифр, `_` и `-`. Токен и секрет — секреты и приходят из окружения (`REQ-CONFIG-001`). Без единого бота, без любой из трёх настроек, с неверной формой и с токеном, именем или секретом, повторённым у двух ботов, служба не стартует; отказ называет настройку, но не её значение. Ключи одного бота `platform.telegram.bot-token`, `bot-name`, `webhook-secret` (17.9.0) останавливают запуск со ссылкой на миграцию выпуска 18.0.0. Запрос к необъявленному боту — отказ `telegram-bot-not-found` с кодом 404. Срок ссылки связи — `platform.telegram.link-ttl`, по умолчанию 10 минут, положительный и не длиннее суток. Адрес Bot API — `platform.telegram.api-base`, по умолчанию `https://api.telegram.org`; переопределяется для тестов.

## Webhook

3. <a id="REQ-TELEGRAM-003"></a> **REQ-TELEGRAM-003** — Обновления бота приходят на `POST /api/telegram/<бот>/webhook` — у каждого бота свой путь. Запрос удостоверяет модуль портом `RequestAuthenticator` (`REQ-AUTH-037`): заголовок `X-Telegram-Bot-Api-Secret-Token` сверяется с секретом этого бота сравнением постоянного времени; секрет другого бота не подходит. Нет заголовка или он неверен — отказ ядра `identity-rejected` с кодом 401 до разбора обновления, и ничего не меняется. Удостоверенный запрос несёт внешнюю личность вида `telegram-webhook` с идентификатором бота и без ролей; частоту ограничивает ядро по каждому боту (`REQ-AUTH-038`), и проект задаёт `platform.auth.external.requests-per-minute` по потоку самого оживлённого бота. Свои пути модуль отдаёт порту сам, поэтому проекту с Mini App пути webhook в своём порту объявлять не нужно.
4. <a id="REQ-TELEGRAM-004"></a> **REQ-TELEGRAM-004** — Удостоверенное обновление получает ответ 200, даже если модуль его не понял: на любой другой ответ Telegram повторяет обновление. Модуль читает только команду `/start <токен>` из личного чата; прочее пропускается без ответа.
5. <a id="REQ-TELEGRAM-005"></a> **REQ-TELEGRAM-005** — Webhook бота регистрирует явная команда `TelegramBots.bot(<бот>).useWebhook(url)`: она передаёт Telegram адрес и секрет этого бота из настроек, так что секрет у проекта не расходится с модулем. Ядро не регистрирует webhook само (требование к ядру о фоновой работе); проект вызывает команду при выкладке или из своей служебной точки.

## Связь

6. <a id="REQ-TELEGRAM-006"></a> **REQ-TELEGRAM-006** — Вошедший получает ссылку связи с ботом `POST /api/telegram/<бот>/link`: `https://t.me/<имя бота>?start=<токен>` и срок её действия. Токен — 32 случайных байта в base64url, хранится только отпечатком SHA-256. Ссылка одноразовая, и у учётной записи действует одна на бота: новая выдача гасит прежнюю. Учётной записи, у которой связь с этим ботом уже есть, ссылка не выдаётся — отказ `telegram-already-linked` с кодом 409: связь сначала снимают.
7. <a id="REQ-TELEGRAM-007"></a> **REQ-TELEGRAM-007** — Команда `/start <токен>` из личного чата с ботом записывает связь учётной записи, выдавшей токен, с этим ботом, человеком и чатом Telegram и язык человека в Telegram (`language_code`) — для текстов уведомлений (`REQ-TELEGRAM-015`). Токен гасится при любом исходе. Связь не записывается, если токен истёк, уже использован, не выдавался или выдан для другого бота; если у учётной записи уже есть связь с этим ботом; если этот человек Telegram у этого бота уже связан с другой учётной записью. У учётной записи одна связь с каждым ботом, у человека Telegram у каждого бота — одна учётная запись: иначе вход через Telegram (`CORE-ARC-033`) не знал бы, кого пускать.
8. <a id="REQ-TELEGRAM-008"></a> **REQ-TELEGRAM-008** — Ответ в чат на `/start` пишет проект портом `TelegramReplies`: `linked(bot, language)` и `refused(bot, language)`, где `bot` — идентификатор бота, `language` — `language_code` человека из обновления, может быть пустым. Пустой текст — без ответа; без бина модуль отвечает молча (`TelegramReplies.SILENT`). У ядра нет текстов и перевода (`CORE-ARC-028`). Ответ уходит телом ответа webhook методом `sendMessage`, без отдельного вызова Bot API.
9. <a id="REQ-TELEGRAM-009"></a> **REQ-TELEGRAM-009** — Владелец видит связи со всеми ботами службы одним запросом `GET /api/telegram/links` — бот, его имя, есть ли связь и когда записана — и снимает связь с ботом `DELETE /api/telegram/<бот>/link`; снятие отсутствующей связи безвредно. Код проекта читает и снимает связь Java API `TelegramLinks`: `chat(account, bot)` и `unlink(account, bot)`. Точки — только вошедшему и только о своих связях.

## Персональные данные

10. <a id="REQ-TELEGRAM-010"></a> **REQ-TELEGRAM-010** — Идентификатор человека в Telegram и номер чата — персональные данные (`REQ-AUTH-040`): в журналы, метки метрик и ответы об ошибках они не попадают, и точки модуля их не отдают — владельцу достаточно знать, что связь есть. Удаление учётной записи (`REQ-AUTH-024`) стирает её связи и невыданные ссылки внешним ключом с каскадом: исход — `REMOVED`, а не `HELD`.

## Bot API

11. <a id="REQ-TELEGRAM-011"></a> **REQ-TELEGRAM-011** — Вызовы Bot API идут через `TelegramBots.bot(<бот>)` — каждый своим токеном: `send(chat, text)` и `useWebhook(url)`. Адрес метода Bot API содержит токен бота, поэтому отказ `TelegramUnavailable` не несёт ни адреса, ни исходного исключения с ним — только имя метода и описание Telegram. Повторов у клиента нет: очередь и повторы — у доставки уведомлений (`REQ-NOTIFICATIONS-013`, `REQ-TELEGRAM-016`).

## Уведомления

14. <a id="REQ-TELEGRAM-014"></a> **REQ-TELEGRAM-014** — Модуль доставляет уведомления ядра (`REQ-NOTIFICATIONS`), когда проект подключил `platform-notifications` и объявил бин `TelegramTexts`; каждый бот — свой канал `telegram-<бот>` (`REQ-NOTIFICATIONS-011`), и уведомление уходит в каждый бот, с которым у учётной записи есть связь и для которого проект дал текст. Без бина каналов нет и очередь для Telegram не пишется: у ядра нет текстов (`REQ-NOTIFICATIONS-003`). Отправляет общая команда `NotificationDelivery.deliverPending()` (`REQ-NOTIFICATIONS-013`). Добавлено 2026-11-16, `CORE-ARC-031`.
15. <a id="REQ-TELEGRAM-015"></a> **REQ-TELEGRAM-015** — Текст пишет проект: `TelegramTexts.text(notice)` получает бот, учётную запись, вид, параметры, полную ссылку — путь уведомления от `platform.auth.link-base` — и язык связи с этим ботом, который может быть пустым. Пустой ответ — уведомление этого вида в этот бот не уходит (`SKIPPED`): так проект решает, какой бот что несёт. Текст отправляется без разметки и не длиннее 4096 знаков — предела Bot API; длиннее — `FAILED` с записью в журнал службы.
16. <a id="REQ-TELEGRAM-016"></a> **REQ-TELEGRAM-016** — Уведомление учётной записи без связи с ботом — или со связью, снятой после `notify`, — в этот бот не уходит (`SKIPPED`). Ответ Bot API читается так: `403` — человек заблокировал бот или чат недоступен: связь с этим ботом снимается, уведомление не уходит (`FAILED`) — номер недоступного чата хранить незачем, а связь человек восстановит новой ссылкой; прочие `4xx` — `FAILED`; `429` — ждать срок `retry_after` без счёта попытки (`LATER`); `5xx` и отсутствие ответа — повтор (`RETRY`). Журнал службы называет вид уведомления и код ответа — без учётной записи, чата и текста (`REQ-TELEGRAM-010`).
17. <a id="REQ-TELEGRAM-017"></a> **REQ-TELEGRAM-017** — Каждый бот шлёт в один чат не чаще раза в секунду: следующее уведомление того же чата ждёт секунду без счёта попытки (`LATER`). Общий предел Bot API держится размером пачки (`REQ-NOTIFICATIONS-013`) и ответом `429`; учёт по чатам — в памяти экземпляра службы, и у нескольких экземпляров превышение ловит тот же `429`.

## Вход из Mini App

18. <a id="REQ-TELEGRAM-018"></a> **REQ-TELEGRAM-018** — Модуль проверяет вход из Mini App бота сам: проект объявляет пути и роли — `platform.telegram.bots.<бот>.mini-app.paths` и `.mini-app.roles`, — и модуль удостоверяет эти пути портом `RequestAuthenticator` (`REQ-AUTH-037`). Пути — под `/api/**`, кроме путей модуля `/api/telegram/**`, и у каждого бота свои; роли — только из `platform.auth.external.roles` (`REQ-AUTH-039`); иначе служба не стартует. Запрос несёт `initData` в заголовке `X-Telegram-Init-Data`. Подпись проверяется по правилам Telegram — ключ — HMAC-SHA256 токена бота с ключом `WebAppData`, сравнение постоянного времени — тем ботом, чей путь: подпись другого бота не подходит. Срок `auth_date` — `platform.telegram.mini-app.max-age`, по умолчанию час, положительный и не длиннее 7 суток; время подписи из будущего дальше минуты отвергается. Подделанная, просроченная, неполная initData и initData без пользователя или с повтором поля — отказ ядра `identity-rejected`. Добавлено 2026-11-16, `CORE-ARC-032`.
19. <a id="REQ-TELEGRAM-019"></a> **REQ-TELEGRAM-019** — Верная initData — внешняя личность вида `telegram` с идентификатором пользователя Telegram и ролями бота (`CurrentIdentity.get()`); учётной записи у неё нет (`CurrentAccount.id()` пуст). Бот, имя, имя пользователя и язык код проекта читает `TelegramMiniApp.user()` — только в этом запросе. Учётную запись человека, связанного с ботом (`REQ-TELEGRAM-007`), находит `TelegramLinks.account(bot, telegramUser)`. Идентификатор и имя пользователя — персональные данные (`REQ-TELEGRAM-010`).

## Вход на сайт и второй шаг

20. <a id="REQ-TELEGRAM-020"></a> **REQ-TELEGRAM-020** — Вход через Telegram Login Widget — `POST /api/telegram/<бот>/login` с данными виджета как есть; точка открыта без входа и требует токена CSRF. Подпись проверяется по правилам Telegram — ключ — SHA-256 токена этого бота, HMAC-SHA256, сравнение постоянного времени; срок `auth_date` — `platform.telegram.login.max-age`, по умолчанию 10 минут, не длиннее суток. Вход — только учётной записи, связанной с этим ботом (`REQ-TELEGRAM-007`); учётная запись по Telegram не заводится. Неверная или просроченная подпись и человек без связи получают один отказ `credentials-rejected` (`REQ-AUTH-003`). Предел — 50 попыток за 15 минут с адреса сети. Сессию открывает ядро (`REQ-AUTH-048`) со всеми проверками входа по паролю: блокировка, неподтверждённая почта, счёт неудач, второй шаг. Клиент: `AuthSession.signInWith('/api/telegram/<бот>/login', данные)` из `@apocarteres/auth`. Добавлено 2026-11-16, `CORE-ARC-033`.
21. <a id="REQ-TELEGRAM-021"></a> **REQ-TELEGRAM-021** — Готовый второй шаг (`REQ-AUTH-041`) включает настройка `platform.telegram.second-factor.bot` — бот, через который идёт код. Он требуется учётной записи, связанной с этим ботом, при любом входе — по паролю и через Telegram. Код — шесть случайных цифр, хранится отпечатком, живёт 5 минут — столько же, сколько ожидающий вход, — и принимается одной попыткой: неверный код гасит его, и вход начинают заново. Текст сообщения с кодом пишет проект бином `TelegramCodeText`: без него служба с этой настройкой не стартует. Свой бин `SecondFactor` проекта вместе с настройкой не объявляется. Код уходит отдельным вызовом Bot API, не через очередь уведомлений: он нужен сейчас.

## Контракт и клиент

12. <a id="REQ-TELEGRAM-012"></a> **REQ-TELEGRAM-012** — Точки модуля описаны контрактом OpenAPI `platform-telegram/src/main/resources/openapi/platform-telegram.openapi.json`, копия лежит в пакете клиента, типы клиента выводятся из него (`npm run contract-types`). Тест держит контроллер в соответствии с контрактом: пути, поля и коды отказов.
13. <a id="REQ-TELEGRAM-013"></a> **REQ-TELEGRAM-013** — Клиент объявляет модуль один раз — `provideTelegram({ base })` — и получает `TelegramLink`: сигнал `bots` — связи со всеми ботами службы или `null` до первого чтения и без входа, сигнал `linked` — боты, с которыми связь есть, `refresh()`, `invite(bot)` — ссылка связи, `unlink(bot)`. Экраны и переход по ссылке — проекту: ядро не знает, открывать ли ссылку в новой вкладке или показывать код.
