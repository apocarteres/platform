# Задачи и выпуски во внешнем хранилище по контракту ядра

## Мысль

Ядро читает и меняет задачи и выпуски не напрямую из `docs/tickets` и
`docs/releases`, а через **хранилище** с двумя реализациями:

- **файлы** — нынешние каталоги, по умолчанию; для проектов ничего не меняется;
- **внешнее** — любой сервис, исполняющий HTTP-контракт ядра (ниже).

Проект выбирает хранилище в `.conventions.json`:

```json
"store": {
  "kind": "external",
  "url": "https://tracker.example/api/conventions/DRIAD",
  "readKeyEnv": "CONVENTIONS_STORE_READ_KEY",
  "writeKeyEnv": "CONVENTIONS_STORE_WRITE_KEY",
  "idPattern": "^(?:DRIAD|SEC)-\\d+|^LS-[A-Z]+-\\d{3}"
}
```

Контракт описывает ядро, исполняет хранилище. О внутреннем устройстве хранилища
ядро не знает ничего: адрес, ключи и форма ответа. Транспорт — только HTTP
(встроенный `fetch`, без зависимостей); внутри ядра шов — интерфейс хранилища,
другие адаптеры сейчас не строятся.

При внешнем хранилище в репозитории не остаётся ни задач, ни выпусков: вся
история переносится в хранилище. В git остаются тег выпуска и запись о
выпущенном в его аннотации.

## Почему

Задача, которая живёт в двух системах сразу, — две правды. Файл в репозитории
и карточка в трекере расходятся, и любое деление полей между ними («статус —
в файле, исполнитель — на доске») людям непонятно: на доске карточку можно
перетащить, а на деле её состояние — в другом месте. То же с выпуском: состав,
который виден на доске, но меняется только правкой файла, — вторая правда.
Проекту, который ведёт работу в трекере, ядро сейчас не оставляет выбора: цикл
выпуска, проверка коммитов и проверка документации читают только файлы.

## Кто что исполняет

Открыть выпуск на доске и открыть его командой — одно и то же действие. Это
достигается одной реализацией каждого правила, а не двумя.

| Что | Кто исполняет | Почему |
|---|---|---|
| Операции над данными: открыть выпуск, снять задачу, отменить выпуск, отметить действие развёртывания, учесть коммит, перенести или закрыть обязательство | хранилище | данные его, проверяются без репозитория |
| Инварианты данных (см. «Инварианты») | хранилище | их мало, они декларативны и одинаковы для кнопки и для API |
| Шлагбаум закрытия: первый шаг закрытия, перезакрытие, завершающий шаг | ядро | нужен репозиторий: дерево кода, история коммитов, расписка, тег |

Команда ядра для операции над данными — тонкий клиент той же операции
хранилища: своих проверок сверх хранилища она не добавляет, поэтому кнопка и
команда неразличимы по определению. Имена команд и задач менеджера окружения
не меняются.

Кнопка «закрыть выпуск» в хранилище запускает **ту же команду ядра** там, где
есть рабочая копия, — в CI — и показывает её результат. Как хранилище её
запускает — его дело, в контракт это не входит. Человек с рабочей копией и
кнопка исполняют один код и получают одни отказы.

Проверки цикла хранилище не повторяет. Им нужны чистое рабочее дерево,
расписка `verify` по дереву кода (`REQ-RELEASE-045`), история коммитов от
прошлого тега, файлы миграций на коммитах прошлых выпусков, сам тег. Исполнить
их через API хостинга значило бы написать цикл второй раз и привязать контракт
к одному хостингу.

**Что при внешнем хранилище переезжает из открытия в закрытие.** Две проверки
открытия требуют репозитория, а выпуск может быть открыт с доски:

- порог открытых вопросов (`REQ-RELEASE-047`): пределы заданы в
  `.conventions.json`; первый шаг закрытия и `release status` их и так
  проверяют;
- материализация обязательств ядра (`REQ-RELEASE-013`): каталог обязательств
  лежит в установленном пакете правил, отбор по стеку — в
  `.conventions.json`. Задачи обязательств заводит первая же команда ядра,
  увидевшая открытый выпуск; закрытие без них отказывает.

## Что ядро делает с задачами и выпусками сейчас

Сверено по `project-conventions` 17.3.1.

| Команда | Читает | Пишет |
|---|---|---|
| `commits --range` | номера задач на ревизии git (`ticketIdsAt`) | — |
| `docs-check` | форму каждой задачи и выпуска, сверку `release` с составами, сводки | — |
| `release open` | все задачи, все выпуски, учёт обязательств | документ выпуска, `release` названным задачам, задачи обязательств, учёт обязательств |
| `release close` / `reclose` | состав, зависимости, вопросы, поля проекта, коммиты, разделы развёртывания | документ выпуска, `release` задачам состава, тег |
| `release finish` | состав, критерии выхода | документ выпуска, учёт обязательств |
| `release cancel` / `drop` / `account` / `mark` / `defer` / `satisfy` | открытый выпуск, задачи | документ выпуска, `release` задач, учёт обязательств |
| `tickets-index`, `releases-index` | всё | сводки |

Все чтения задач идут через `tickets(root)` (`lib/release/documents.mjs`): она
читает каждый файл, а команды фильтруют список в памяти. Все выпуски читает
`releases(root)`.

## Нет ли тут N+1 и роста с историей

Объём для оценки — legacy-store: 551 задача, 4,6 МБ текста.

Перенести чтение «всё разом» на сеть как есть — значит на каждую команду
выгружать всю историю проекта: чем она длиннее, тем медленнее каждая отправка
коммитов. Поэтому контракт историю не отдаёт вовсе.

**Что ядру нужно на самом деле:**

| Потребитель | Какие данные |
|---|---|
| проверка коммитов (`commitStanding`) | только задачи, названные коммитами диапазона: существует ли, отменена ли |
| состав выпуска (`compositionTickets`) | задачи открытого выпуска и выполненные без выпуска |
| порог открытых вопросов (`questionStanding`) | задачи с `questions: open` — по `REQ-TICKETS-012` они всегда не закрыты |
| обязательства | незакрытые задачи с полем `obligation`, учёт обязательств |
| зависимости (`dependencyProblems`) | прямые цели `depends-on` задач состава, без обхода вглубь |
| действия развёртывания, поля проекта | только задачи состава |
| прошлый тег, коммиты прошлых выпусков (`previousReleaseTag`, `releasesCarrying`) | теги git — хранилище не нужно |

Места, которому нужна вся история задач или выпусков, в ядре нет. Отсюда три
ограниченных чтения: **рабочий набор** задач, **поиск задач по номерам** и
**открытый выпуск**. Размер первого — объём текущей работы, второго — число
названных номеров, третьего — один выпуск. От длины истории не зависит ни одно.

Ловушки, которые остаются:

1. **Повторные загрузки.** Одна команда зовёт `tickets()` несколько раз:
   `closability` — около пяти. Лечится набором на команду: он загружается
   один раз и держится в памяти до её конца. Полезно и файловой реализации.
2. **Текст задачи по одной.** Набор несёт поля, два признака наличия разделов
   и тексты только двух разделов развёртывания, а не тело задачи.
3. **Записи по одной.** Каждая операция цикла — один запрос, а не запрос на
   каждую задачу состава.

**Сколько запросов на команду:**

| Команда | Запросы |
|---|---|
| `commits` (`pre-push`, CI) | 0, если номера уже известны; иначе 1 поиск по номерам |
| `docs-check` | 0 |
| `release status`, `close`, `reclose` | открытый выпуск + рабочий набор + не больше одного поиска + одна операция |
| остальные команды выпуска | открытый выпуск + одна операция |

**N+1 внутри самого хранилища** — та же ловушка с другой стороны: ответ
собирается из нескольких запросов к базе и склеивается в памяти, а не запросом
на каждую задачу. Контракт это не проверяет, но требование к реализации
записывается.

## Контракт

Обмен — JSON, ошибки — `application/problem+json` с полем `code`
(`REQ-API-ERRORS`), вход — `Authorization: Bearer <ключ>`. Ключ на чтение — для
`pre-push` и CI; ключ с правом записи — тому, кто исполняет операции выпуска.
Ядро ключ не печатает и в аргументы процессов не кладёт
(`REQ-PROJECT-PROCESS-016`). Каждый ответ несёт `contract` — версию контракта:
ядро меняет набор разбираемых полей чаще, чем хранилище; если хранилище старше
требуемого — понятный отказ.

### Форма задачи

```json
{
  "id": "DRIAD-301",
  "aliases": [],
  "title": "Синхронизация задач с трекером",
  "url": "https://tracker.example/projects/DRIAD/issues/301",
  "status": "in_progress",
  "priority": "P1",
  "scope": "ops",
  "release": null,
  "questions": null,
  "dependsOn": ["LS-OPS-280"],
  "related": [],
  "obligation": null,
  "supersededBy": null,
  "fields": { "manual-qa": "required", "executor": "owner" },
  "sections": {
    "whyNot": false,
    "openQuestions": false,
    "beforeDeploy": "1. …",
    "afterDeploy": null
  }
}
```

- Словарь — ядра: `status` из `REQ-TICKETS-007`, `priority` из `REQ-TICKETS-006`.
  Перевод из своих состояний — забота хранилища.
- `release` — выпуск задачи или `null`. Это правда, а не копия: меняют её
  только операции над выпуском.
- `fields` — поля проекта (`REQ-PROJECT-PROCESS-024`). Определения остаются у
  проекта в `.conventions.json`; хранилище получает их копию операцией
  `defineFields`, чтобы доска предлагала выбор из допустимых значений, а не
  принимала то, что закрытие потом отвергнет. Копия на доске не правится.
- Формат номера (`idPattern`) — в `.conventions.json`, не в ответе: проверка
  коммитов без сети должна его знать. Задачи, перенесённые из репозитория,
  сохраняют прежние номера; новым номер выдаёт хранилище.

### Рабочий набор

`GET {url}/tickets/working` → `200` с `ETag`; с `If-None-Match` → `304`.

```json
{ "contract": 1, "revision": "18422", "fieldsDigest": "9f2c…", "tickets": [ … ], "referenced": [ … ] }
```

В наборе — задачи в нетерминальном статусе и выполненные, чей выпуск ещё не
вышел или не назначен. Отменённых, заменённых и выпущенных в нём нет, поэтому
набор не растёт с историей. Ответ целый, без постраничности.

`referenced` — прямые цели `depends-on` задач набора, которых в самом наборе
нет, в той же форме: закрытию нужен их статус и выпуск. Один уровень.

`fieldsDigest` — отпечаток определений полей проекта, которые держит
хранилище. Команда ядра с ключом записи, увидев расхождение с
`.conventions.json`, шлёт `defineFields`. Отпечаток — SHA-256 в
шестнадцатеричной записи от значения `fields` операции `defineFields`,
записанного как JSON в UTF-8 без пробелов с ключами объектов по алфавиту на
каждом уровне; `null`, пока определения не публиковались.

`revision` — непрозрачная строка: ядро её только сравнивает и записывает в
манифест тега. `ETag` — она же в кавычках.

### Поиск по номерам

`POST {url}/tickets/lookup` — чтение, работает с ключом без права записи:

```json
{ "ids": ["LS-OPS-280", "DRIAD-999"] }
```

→ `200 { "contract": 1, "tickets": [ … ], "missing": ["DRIAD-999"] }`.

- Номер ищется и среди псевдонимов. Находится задача в любом статусе: номер не
  переиспользуется и не исчезает. Это заменяет `ticketIdsAt` по ревизии git.
- Предел — 500 номеров за запрос; больше ядро делит на части само.
- Найденные номера ядро запоминает в игнорируемом каталоге рядом с расписками
  (не в `.conventions/`, там версионируемые файлы): раз найденный номер
  существует всегда.

### Открытый выпуск

`GET {url}/releases/open` → `200` с выпуском в статусе `draft`, `closing`,
`in_progress` или `blocked`, либо `"release": null`, если открытого нет.

```json
{
  "contract": 1,
  "releasedCount": 41,
  "release": {
    "id": "RELEASE-2026-11-3",
    "status": "draft",
    "openedOn": "2026-11-12",
    "named": ["DRIAD-301"],
    "dropped": [ { "ticket": "DRIAD-305", "reason": "…", "on": "2026-11-13" } ],
    "accounted": [ { "sha": "0a6cd3a", "subject": "…", "reason": "…" } ],
    "actions": [ { "ticket": "DRIAD-301", "step": "before", "item": 1, "text": "…", "done": false, "note": null } ],
    "result": null,
    "retagged": []
  },
  "obligations": [
    { "id": "OBL-backups", "ticket": "DRIAD-312", "due": 3, "seenAtCount": 40, "deferred": null, "closed": null }
  ]
}
```

- Состав открытого выпуска ядро считает само по рабочему набору: задачи с
  `release`, равным номеру выпуска, и выполненные без выпуска
  (`REQ-RELEASE-007`). Хранилище показывает тот же состав тем же правилом.
- `releasedCount` — число вышедших выпусков проекта; `seenAtCount` — его
  значение в момент, когда обязательство взято в работу. Разность — срок в
  выпусках (`REQ-RELEASE-014`); считает её ядро.
- `obligations` — по одной записи учёта на обязательство проекта, закрытые
  включены: их число ограничено перечнем обязательств, а не историей.
  `deferred` — `null` или `{ "reason", "on" }`; `closed` — `null` или
  `{ "ticket", "on" }`.
- Историю выпусков ядро не запрашивает: прошлый тег и коммиты прошлых выпусков
  берутся из тегов git.

### Операции

`POST {url}/operations` — одна операция, одна транзакция хранилища. Заголовок
`Idempotency-Key`: повтор с тем же ключом возвращает первый ответ. Тело —
имя операции и её аргументы на одном уровне:
`{ "operation": "defineFields", "fields": { … } }`.

| Операция | Кто зовёт | Что делает |
|---|---|---|
| `openRelease { id?, tickets }` | доска, команда | открывает выпуск; без `id` выдаёт следующий `RELEASE-YYYY-MM-N`; названным задачам ставит `release` |
| `dropTicket { ticket, reason }` | доска, команда | снимает задачу из состава, `release` → `null`, запись в `dropped` |
| `cancelRelease { reason }` | доска, команда | отменяет открытый выпуск, задачам состава `release` → `null`; номер остаётся занятым |
| `accountCommit { sha, subject, reason }` | доска, команда | запись в `accounted` |
| `markAction { ticket, step, item, done, note }` | доска, команда | отметка действия развёртывания |
| `deferObligation { id, reason }` | доска, команда | перенос обязательства с причиной |
| `satisfyObligation { id, ticket }` | доска, команда | закрывает обязательство выполненной задачей; незаконченную задачу обязательства переводит в `superseded` |
| `unfreezeRelease { reason }` | ядро, менеджер на доске | снимает заморозку: выпуск возвращается в статус до неё, запись в журнал |
| `defineFields { fields }` | ядро | заменяет определения полей проекта в формате `metadata.fields` |
| `freezeRelease {}` | ядро | замораживает открытый выпуск: статус → `closing` |
| `takeObligations { obligations }` | ядро | для каждого обязательства: незакрытая задача с ним существует или создаётся, входит в открытый выпуск, запись учёта есть; закрытая запись начинается заново — с новой задачей и текущим `releasedCount` |
| `closeRelease { commit, tag, composition, actions, receipt }` | ядро | замороженный выпуск → `in_progress`, задачам `composition` ставит `release`, незаконченные задачи обязательств снимает на следующий выпуск, записывает `actions` и `result` |
| `recloseRelease { commit, tag, reason, composition, actions, receipt }` | ядро | то же для выпуска, замороженного из `in_progress`, запись в `retagged` |
| `finishRelease { note, closedObligations }` | ядро | выпуск → `released`, `releasedCount` растёт, обязательства закрываются названными задачами |

Операции ядра хранилище принимает только с ключом записи и на доске не
предлагает: их исход зависит от проверок, которые исполняет ядро. Исключение —
`unfreezeRelease`: брошенную заморозку менеджер снимает с доски с причиной.

### Инварианты

Хранилище держит их при любой правке — с доски и через API одинаково — и
отказывает с кодом:

| Код | Правило |
|---|---|
| `release-already-open` | открытых выпусков не больше одного (`REQ-RELEASE-010`) |
| `release-id-taken` | номер выпуска не переиспользуется, включая отменённые (`REQ-RELEASE-005`, `-029`) |
| `release-not-open` | состав и учтённые коммиты меняются только у выпуска в `draft`; отметки действий — в `draft` и `in_progress` |
| `release-closing` | пока выпуск заморожен, отказывают все операции над ним с доски и через API, смена статуса задач его состава и выполненных задач без выпуска, указание задач в выпуск |
| `release-closed` | вышедший и отменённый выпуск неизменны (`REQ-RELEASE-006`) |
| `ticket-missing` | названная задача существует |
| `ticket-in-release` | задача, уже отнесённая к выпуску, второй раз не указывается (`REQ-RELEASE-007`) |
| `ticket-is-obligation` | задача обязательства не снимается из состава и не отменяется (`REQ-RELEASE-032`, `-033`) |
| `reason-required` | снятие, отмена, перенос и учёт коммита несут причину |
| `evidence-not-done` | обязательство закрывается только выполненной задачей (`REQ-RELEASE-019`) |
| `obligation-overdue` | просроченное обязательство не переносится (`REQ-RELEASE-014`) |
| `whynot-required` | отмена задачи без «Почему не делаем» (`REQ-TICKETS-004`) |
| `questions-open` | работа или закрытие задачи при открытых вопросах (`REQ-TICKETS-012`) |
| `dependency-cycle` | цикл в `depends-on` (`REQ-TICKETS-010`): ядро видит только состав и цикл за его пределами не найдёт |
| `release-is-derived` | `release` задачи меняют только операции над выпуском |
| `field-value-invalid` | значение поля проекта — из объявленных `defineFields` |

`conventions store --check` проходит по адресу проекта и прогоняет сценарии
цикла ядра: форму ответов, версию, границы рабочего набора, поиск по номеру и
псевдониму, каждую операцию, её повтор и каждый отказ. Тот же набор сценариев
ядро гоняет на файловой реализации.

## Тег и хранилище

Тег и запись в хранилище не атомарны вместе, а закрытие идёт минуты: кнопка
запускает команду в CI. За это время с доски можно отменить выпуск, снять
задачу, вернуть выполненную задачу в работу. Без защиты тег утверждал бы
состав, которого уже нет. Поэтому выпуск на время закрытия замораживается.

Порядок первого шага закрытия и перезакрытия:

1. Проверки, которым хранилище не нужно: чистое дерево, расписка. Если
   расписки нет, команда выполняет `verify` сама (`REQ-RELEASE-003`) — до
   заморозки, чтобы доска не стояла на время прогона.
2. `freezeRelease`. С этого момента данные выпуска не меняются.
3. Чтение открытого выпуска и рабочего набора, остальные проверки. Отказ —
   `unfreezeRelease`; ни тега, ни записи (`REQ-RELEASE-001`).
4. Тег с аннотацией-манифестом: номер выпуска, состав (номера и заголовки),
   ревизия рабочего набора, расписка. Тег не встал — `unfreezeRelease`.
5. `closeRelease` с составом из манифеста: заморозка снимается, выпуск
   переходит в `in_progress`.

Сбой после шага 2 оставляет выпуск замороженным. Повтор команды видит
`closing`: если тег этого выпуска стоит на проверенном коммите и несёт
манифест — воспроизводит `closeRelease` по нему (ключ идемпотентности — номер
выпуска и коммит); если нет — снимает заморозку и начинает заново. Заморозку,
которую некому повторить, менеджер снимает с доски с причиной; это
единственная ручная операция над замороженным выпуском.

Задача, выполненная после заморозки, в состав не входит и остаётся без
выпуска — выйдет в следующем. Сверка ревизий всей доски не нужна: заморожен
только этот выпуск и его состав.

Манифест — ещё и ответ на вопрос, что остаётся в git: замороженная запись о
выпущенном лежит в самом теге, неизменная вместе с ним. При перезакрытии
(`REQ-RELEASE-046`) она переезжает вместе с тегом.

## Учёт обязательств

Сейчас состояние обязательств — версионируемый файл
`.conventions/obligations.json`, который цикл правит и фиксирует коммитом
(`REQ-RELEASE-015`). Выпуск, открытый с доски, коммита сделать не может,
поэтому при внешнем хранилище учёт — данные хранилища: поле `obligations`
ответа об открытом выпуске и операции `takeObligations`, `deferObligation`,
`satisfyObligation`, `finishRelease`.

Каталог обязательств и их сроки по-прежнему объявляет ядро; хранилище хранит
только то, что произошло: взято в работу, перенесено с причиной, закрыто
задачей. Сообщение о долгах перед ядром (`REQ-RELEASE-035`) при внешнем
хранилище печатают `release status` и шлагбаум закрытия; `conventions check`
остаётся без сети и долгов не называет — задачи обязательств видны на доске.

## Проверки и сеть

- `docs-check` к хранилищу не обращается. Сводки `docs/tickets/INDEX.md` и
  `docs/releases/INDEX.md` не обязательны, сверка состава с задачами
  снимается; файл `type: ticket` или `type: release` в репозитории — отказ,
  чтобы задача не завелась мимо хранилища.
- `commits` ищет только номера, названные коммитами диапазона. Номер уже
  известен — проходит молча и без сети; номера нет и сети нет —
  предупреждение. С ключом `--strict` (CI) — отказ: иначе несуществующая
  задача всплывает только при закрытии выпуска. При внешнем хранилище ядро
  требует `commits --strict` в CI.
- Шаблон этапа плана (`STAGE_ID`) при внешнем хранилище выключен: номер вида
  `DRIAD-12` под него подходит, всё решает `idPattern`. Этапы плана — обычные
  задачи хранилища.
- Команды выпуска без хранилища отказывают с понятным сообщением.
- `tickets-index`, `releases-index`, `tickets-renumber`, `naming-migration`,
  `release adopt` — только файловые; при внешнем хранилище отказывают с
  названием причины.

## Что меняется в ядре

Сверено по `project-conventions` 17.3.1. Изменение совместимо: без `store` в
`.conventions.json` всё работает как сейчас.

**Шов.** Модуль хранилища с одной формой задачи и одной формой выпуска для
обеих реализаций. Сейчас задача и выпуск — это `{ file, content, metadata }`
(`lib/release/documents.mjs`), и потребители разбирают `content` напрямую:
разделы «Состав», «Критерии выхода», «Учтённые коммиты», «Переносы тега».
Их нужно перевести на форму хранилища; файловая реализация разбирает
документ в ту же форму и пишет его обратно.

## Переход проекта

Выполняется между выпусками: открытого выпуска нет.

1. Хранилище принимает все задачи и все выпуски проекта, включая закрытые, с
   прежними номерами и полным текстом. Вышедшие выпуски переносятся как есть и
   в хранилище неизменны: `REQ-RELEASE-006` не нарушается, документ не
   правится, а переезжает. Учёт обязательств переносится из
   `.conventions/obligations.json`.
2. `store --check` по адресу проекта проходит.
3. Одним коммитом: `docs/tickets` и `docs/releases` убираются, ссылки на них
   из остальных документов заменяются номером в обратных кавычках (разовая
   команда перехода), `.conventions.json` переключается,
   `.conventions/obligations.json` убирается, `commits --strict` добавляется
   в CI.

## Открытые вопросы

1. Постановка задачи (проблема, подтверждение, критерии приёмки, ход работы)
   переезжает в хранилище целиком или остаётся файлом? Цена переезда: история
   правок постановки и «ход работы» (`REQ-TICKETS-003`) уходят из git в журнал
   хранилища; агентам нужен доступ к хранилищу, а не к файлам. Ответ:
   2026-11-10 — владелец: постановка целиком в хранилище.
2. Что делать с задачами и выпусками, закрытыми до перехода: оставить
   замороженным архивом в репозитории или перенести? Ответ: 2026-11-10 —
   владелец: в репозитории не оставляем, переносим в хранилище; хранилище
   поддерживает выпуски, чтобы перенести исторические. Прежний ответ того же
   дня (архив в репозитории) отменён.
3. Не деградирует ли обмен с ростом истории, если ядро каждый раз загружает
   все задачи проекта? Ответ: 2026-11-10 — замечание владельца принято:
   полного снимка в контракте нет, есть рабочий набор, поиск по номерам и
   открытый выпуск.
4. Остаются ли команды точкой входа, если выпуски живут в хранилище? Ответ:
   2026-11-10 — владелец: команды сохраняются и вызывают API хранилища; при
   этом выпуск открывается через хранилище — руками или через API — без
   разницы.
5. Кто исполняет закрытие выпуска? Ответ: 2026-11-10 — владелец: операции над
   выпуском исполняет хранилище, шлагбаум закрытия и тег — ядро; кнопка
   «закрыть выпуск» запускает ту же команду ядра в CI.

Решено при обсуждении ядра и трекера:

- `pre-push` без сети — предупреждение, CI — отказ.
- Этапы плана — обычные задачи хранилища; поле родителя в контракт не входит.
- Ключ для `pre-push` и CI — отдельный, только на чтение.
- Тексты требований о файлах задач и выпусков переписываются на «хранилище»
  той же версией ядра, что и реализация: минорная версия, файлы по умолчанию.
