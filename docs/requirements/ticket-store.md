# Хранилище задач и выпусков

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: любой проект.** Правило не зависит от стека.

Происхождение и расчёты — идея `CORE-IDEA-003` репозитория ядра.

## Две реализации

1. <a id="REQ-STORE-001"></a> **REQ-STORE-001** — Задачи и выпуски проекта лежат в хранилище, у которого две реализации: файлы репозитория (`docs/tickets`, `docs/releases`) и внешнее хранилище по контракту ядра. Реализацию выбирает поле `store` в `.conventions.json`; без него действуют файлы, и поведение пакета правил прежнее. У проекта одна реализация: задача не ведётся в двух местах сразу.
2. <a id="REQ-STORE-002"></a> **REQ-STORE-002** — Внешнее хранилище объявляется полями `kind: external`, `url`, `readKeyEnv`, `writeKeyEnv`, `idPattern`. Неизвестный ключ, отсутствие адреса, шаблона номера или имени переменной с ключом — отказ команды, а не молчаливый переход на файлы.
3. <a id="REQ-STORE-003"></a> **REQ-STORE-003** — Ключ хранилища берётся только из переменной окружения, имя которой названо в `.conventions.json`. Ключа нет ни в конфигурации, ни в адресе, ни в аргументах процессов, ни в выводе команд (`REQ-PROJECT-PROCESS-016`). Ключ на чтение — для `pre-push` и CI; ключ записи — тому, кто исполняет операции выпуска.
4. <a id="REQ-STORE-004"></a> **REQ-STORE-004** — Каждый ответ хранилища несёт версию контракта `contract`. Версию, которой пакет правил не знает, команда отвергает с названием требуемой версии.

## Чтения

5. <a id="REQ-STORE-005"></a> **REQ-STORE-005** — Чтений три, и ни одно не зависит от длины истории проекта: рабочий набор `GET {url}/tickets/working` — задачи в нетерминальном статусе и выполненные, чей выпуск ещё не вышел или не назначен, с прямыми целями `depends-on` вне набора; поиск `POST {url}/tickets/lookup` — не больше 500 номеров за запрос, по номеру и по псевдониму; открытый выпуск `GET {url}/releases/open` вместе с учётом обязательств. Ни одна команда не запрашивает все задачи или все выпуски проекта. Рабочий набор отвечает `ETag` и `304` на повтор.
6. <a id="REQ-STORE-006"></a> **REQ-STORE-006** — Задача приходит в одной форме: `id`, `aliases`, `title`, `url`, `status`, `priority`, `scope`, `release`, `questions`, `dependsOn`, `related`, `obligation`, `supersededBy`, `fields`, `sections`. Словарь статусов и приоритетов — ядра (`REQ-TICKETS-006`, `REQ-TICKETS-007`); перевод из своих состояний — забота хранилища. `sections` несёт признаки наличия разделов «Почему не делаем» и «Открытые вопросы» и тексты разделов развёртывания (`REQ-TICKETS-023`), а не тело задачи.

## Операции и разделение исполнения

7. <a id="REQ-STORE-007"></a> **REQ-STORE-007** — Операция над выпуском — один запрос `POST {url}/operations` с именем операции и её аргументами на одном уровне и одна транзакция хранилища. Заголовок `Idempotency-Key`: повтор с тем же ключом возвращает первый ответ. Отказ — `application/problem+json` с полем `code` и текстом причины в поле `reason`; без него команда печатает `detail`.
8. <a id="REQ-STORE-008"></a> **REQ-STORE-008** — Операции над данными выпуска исполняет хранилище: открытие, снятие задачи, отмена, учёт коммита, отметка действия развёртывания, перенос и закрытие обязательства. С доски хранилища, через его API и командой пакета правил они действуют одинаково: команда при внешнем хранилище вызывает операцию и своих проверок поверх не добавляет, а отказ хранилища печатает его кодом и его текстом. Шлагбаум закрытия (`REQ-RELEASE-001`) и тег исполняет ядро: первый шаг закрытия, перезакрытие и завершающий шаг выполняются только командой пакета правил.
9. <a id="REQ-STORE-009"></a> **REQ-STORE-009** — Инварианты данных хранилище держит при любой правке и отказывает с кодом: `release-already-open`, `release-id-taken`, `release-not-open`, `release-closing`, `release-closed`, `ticket-missing`, `ticket-in-release`, `ticket-is-obligation`, `reason-required`, `evidence-not-done`, `obligation-overdue`, `whynot-required`, `questions-open`, `dependency-cycle`, `release-is-derived`, `field-value-invalid`. Поле `release` задачи меняют только операции над выпуском.

## Закрытие выпуска

10. <a id="REQ-STORE-010"></a> **REQ-STORE-010** — Первый шаг закрытия и перезакрытие идут в таком порядке: проверки, которым хранилище не нужно, — чистое дерево и расписка; заморозка выпуска операцией `freezeRelease`; чтение замороженных данных и остальные проверки шлагбаума; тег; одна операция `closeRelease` либо `recloseRelease`. Отказ проверки и не вставший тег снимают заморозку операцией `unfreezeRelease`. Пока выпуск заморожен, хранилище отказывает во всех операциях над ним и в смене статуса задач его состава.
11. <a id="REQ-STORE-011"></a> **REQ-STORE-011** — Тег выпуска при внешнем хранилище несёт в аннотации манифест: номер выпуска, коммит, состав с заголовками задач и значениями их полей проекта, действия развёртывания, ревизию рабочего набора и расписку. Повтор команды, заставший выпуск замороженным, доводит запись в хранилище по манифесту тега и второго тега не ставит; если тега с манифестом этого закрытия нет — снимает заморозку и закрывает заново.
12. <a id="REQ-STORE-012"></a> **REQ-STORE-012** — Учёт обязательств ядра при внешнем хранилище — данные хранилища, а не файл `.conventions/obligations.json`. Незакрытые обязательства берёт в работу первая команда выпуска с ключом записи и закрытие: операция `takeObligations` заводит задачу обязательства и запись учёта. Каталог обязательств и сроки по-прежнему объявляет ядро. Сообщение о долгах (`REQ-RELEASE-035`) печатают `release status` и шлагбаум закрытия; `conventions check` к сети не обращается и долгов не называет.
13. <a id="REQ-STORE-013"></a> **REQ-STORE-013** — Порог открытых вопросов (`REQ-RELEASE-047`) при внешнем хранилище проверяется шлагбаумом закрытия, а не открытием выпуска: выпуск, открытый с доски, закрывается тем же путём, что и открытый командой.

## Проверки и сеть

14. <a id="REQ-STORE-014"></a> **REQ-STORE-014** — Проверка коммитов при внешнем хранилище берёт формат номера из `idPattern`, а существование задачи — из поиска по номерам, названным коммитами диапазона. Найденные номера запоминаются в игнорируемом каталоге `target/store`: известный номер проходит без сети. Номер, который проверить не удалось, даёт предупреждение, а с ключом `--strict` — отказ; CI проекта с внешним хранилищем запускает `conventions commits --strict`. Шаблон этапа плана и запись о задаче (`REQ-RELEASE-040`) при внешнем хранилище не действуют.
15. <a id="REQ-STORE-015"></a> **REQ-STORE-015** — Проверка документации при внешнем хранилище к нему не обращается. Сводки задач и выпусков не требуются; документ типа `ticket` или `release` в репозитории — отказ; ссылка поля метаданных на номер, подходящий под `idPattern`, принимается без поиска; поле `ticket` идеи сверяется с `idPattern`. Команда `tickets-index` собирает только сводку идей.
16. <a id="REQ-STORE-016"></a> **REQ-STORE-016** — Команды, работающие только с файлами задач и выпусков, — `releases-index`, `tickets-renumber`, `naming`, `release adopt`, `release full-run` — при внешнем хранилище отказывают с названием причины.
17. <a id="REQ-STORE-017"></a> **REQ-STORE-017** — Команда `conventions store --check` сверяет хранилище проекта с контрактом: формы ответов, версию, границы рабочего набора, `304`, поиск по номеру и псевдониму. С ключом `--operations` она между выпусками открывает пробный выпуск, проверяет повтор операции, отказы по инвариантам и заморозку и отменяет его; номер пробного выпуска остаётся занятым.
18. <a id="REQ-STORE-018"></a> **REQ-STORE-018** — Определения полей проекта типа `ticket` (`REQ-PROJECT-PROCESS-024`) остаются в `.conventions.json`. Хранилище получает их копию операцией `defineFields`, когда его отпечаток `fieldsDigest` расходится с отпечатком конфигурации; условие `done` полей проверяет шлагбаум закрытия.
19. <a id="REQ-STORE-019"></a> **REQ-STORE-019** — Историю выпусков команды при внешнем хранилище не запрашивают: прошлый тег и коммиты вышедших выпусков берутся из тегов git.

## Как читаются требования о файлах

20. <a id="REQ-STORE-020"></a> **REQ-STORE-020** — Требования, говорящие о файлах задач и выпусков, при внешнем хранилище действуют для данных хранилища: документ выпуска (`REQ-RELEASE-004`, `REQ-RELEASE-006`) — запись выпуска в хранилище, а неизменяемая запись о выпущенном — манифест тега; состав (`REQ-RELEASE-007`, `REQ-RELEASE-031`, `REQ-RELEASE-033`) — поле `release` задач; состояние обязательств (`REQ-RELEASE-013`, `REQ-RELEASE-015`) — учёт хранилища; сводки (`REQ-PROJECT-PROCESS-013`) и расположение файла задачи (`REQ-TICKETS-013`) не действуют; номер новой задаче выдаёт хранилище, и перенос номера (`REQ-TICKETS-022`) не нужен; существование задачи, названной коммитом (`REQ-PROJECT-PROCESS-023`), — по `REQ-STORE-014`.

## Переход проекта

21. <a id="REQ-STORE-021"></a> **REQ-STORE-021** — Проект переходит с файлов на внешнее хранилище командой `conventions store --move` между выпусками: открытого выпуска нет. Команда отказывает до любых изменений, если выпуск открыт, хранилище не исполняет контракт, номер задачи не подходит под `idPattern` или в каталогах задач и выпусков лежит документ иного типа. Она передаёт хранилищу выгрузку проекта, сверяет, что каждая задача и каждый выпуск приняты под прежним номером, и только после этого заменяет ссылки на файлы задач и выпусков в остальных документах номером в обратных кавычках, убирает `docs/tickets`, `docs/releases` и `.conventions/obligations.json` и записывает `store` в `.conventions.json`. Ссылка в строке кода и в блоке кода не заменяется: её называет проверка документации, и правит человек. Переход фиксируется одним коммитом; тем же изменением CI получает `conventions commits --strict`.
22. <a id="REQ-STORE-022"></a> **REQ-STORE-022** — Выгрузка `conventions store --export` несёт задачи в форме контракта с полным текстом, выпуски с их документами, учёт обязательств, число вышедших выпусков и определения полей проекта. Хранилище принимает её по адресу `POST {url}/import` частями: задачи — не больше 200 за запрос; повтор импорта ничего не удваивает, вышедшие и отменённые выпуски хранятся как есть. Срок обязательства после перехода равен сроку до него.

## Чтения для скриптов проекта

23. <a id="REQ-STORE-023"></a> **REQ-STORE-023** — Скрипт проекта читает хранилище командами пакета правил, а не своим клиентом контракта: `conventions store --lookup <номер,номер>`, `conventions store --working` и `conventions store --open` печатают ответ чтения (`REQ-STORE-005`) в JSON в форме контракта и ключа записи не требуют. `conventions release status --json` печатает открытый выпуск, тег, состав с полями проекта, действия развёртывания с отметками и препятствия: до первого шага закрытия — закрытию, после него — завершению. Отметок до первого шага закрытия нет: действие отмечается после него (`REQ-RELEASE-049`). На коммите тега значения полей проекта задач состава читаются из манифеста тега (`REQ-STORE-011`) без обращения к хранилищу.
