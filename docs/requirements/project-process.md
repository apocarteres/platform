# Порядок ведения проекта

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

## Источник требований

1. <a id="REQ-PROJECT-PROCESS-001"></a> **REQ-PROJECT-PROCESS-001** — Источником требований проекта является каталог `docs`. Правило, изложенное вне него, требованием не является.
2. <a id="REQ-PROJECT-PROCESS-002"></a> **REQ-PROJECT-PROCESS-002** — При добавлении функциональности обновляются соответствующие требования. Функциональность, не отражённая в требованиях, завершённой не считается.
3. <a id="REQ-PROJECT-PROCESS-003"></a> **REQ-PROJECT-PROCESS-003** — Функциональность не считается завершённой без тестов либо без явного указания, почему тест не добавлен.
4. <a id="REQ-PROJECT-PROCESS-004"></a> **REQ-PROJECT-PROCESS-004** — Если в каталоге есть `RULES.md`, он описывает порядок работы в этом каталоге и во вложенных; при нескольких таких файлах ближайший к файлу главнее. Читать его перед работой в каталоге обязательно.

## Строение требований

5. <a id="REQ-PROJECT-PROCESS-017"></a> **REQ-PROJECT-PROCESS-017** — Требование объявляет свою область действия сразу после нормативного абзаца: процесс работы, весь код вне зависимости от языка, конкретный язык или само ядро. Требование без объявленной области действия неполно: неизвестно, к чему его применять.
6. <a id="REQ-PROJECT-PROCESS-018"></a> **REQ-PROJECT-PROCESS-018** — Требование, которое опирается на конструкции или словарь одного языка, выносится в отдельный документ с именем `<язык>-<предмет>.md`; язык указывается в `scope`. В документ, объявленный общим, языкозависимое положение не помещается.
7. <a id="REQ-PROJECT-PROCESS-019"></a> **REQ-PROJECT-PROCESS-019** — Если общее требование перечисляет запрещённое или разрешённое по языкам, перечни разделяются подзаголовками с названием языка. Общая часть остаётся в положении, не привязанном к языку.
8. <a id="REQ-PROJECT-PROCESS-020"></a> **REQ-PROJECT-PROCESS-020** — Карта требований группирует документы по области действия теми же разделами. Документ, не попавший ни в один раздел, в карту не добавляется до выбора области.


## Индексы каталогов

9. <a id="REQ-PROJECT-PROCESS-021"></a> **REQ-PROJECT-PROCESS-021** — Индексный файл каталога документации называется `INDEX.md`. `README.md` в роли индекса запрещён: GitHub показывает его как описание каталога, из-за чего роли описания и перечня смешиваются. Решение владельца от 2026-09-07.
10. <a id="REQ-PROJECT-PROCESS-022"></a> **REQ-PROJECT-PROCESS-022** — Индекс перечисляет всё содержимое своего каталога: проверка документации отказывает, если документ каталога в индексе не упомянут. Генерируемые индексы вручную не правятся.

## Находки и задачи

11. <a id="REQ-PROJECT-PROCESS-005"></a> **REQ-PROJECT-PROCESS-005** — Каждая подтверждённая побочная проблема фиксируется задачей, включая находки в тестах и в окружении. Упоминания в ответе или в записи о ходе работы недостаточно: без задачи находка теряется.
12. <a id="REQ-PROJECT-PROCESS-006"></a> **REQ-PROJECT-PROCESS-006** — В задаче указывается, чем проблема подтверждена: отказ теста, измерение, наблюдение на стенде или точная ссылка на код. Гипотеза обозначается гипотезой, с указанием способа проверки, и не выдаётся за доказанный дефект.
13. <a id="REQ-PROJECT-PROCESS-007"></a> **REQ-PROJECT-PROCESS-007** — Перед созданием задачи проверяются существующие: повторная находка дополняет исходную задачу.
14. <a id="REQ-PROJECT-PROCESS-008"></a> **REQ-PROJECT-PROCESS-008** — Конфликт нового требования с действующим разрешается до реализации и записывается в документацию. Блокирующие вопросы и ответы на них хранятся в задаче, а не в переписке.
15. <a id="REQ-PROJECT-PROCESS-009"></a> **REQ-PROJECT-PROCESS-009** — Независимую часть работы при открытом вопросе можно выделить отдельной задачей с явными границами; она не затрагивает изменение, ожидающее решения.

## Тесты и проверки

16. <a id="REQ-PROJECT-PROCESS-010"></a> **REQ-PROJECT-PROCESS-010** — Тесты не отключаются без уведомления владельца и не изменяются так, чтобы скрывать дефект или ослаблять проверку ради её прохождения.
17. <a id="REQ-PROJECT-PROCESS-011"></a> **REQ-PROJECT-PROCESS-011** — Наборы проверок запускаются задачами менеджера окружения, а не голыми командами: нужные ключи заданы в задачах. Для точечного прогона используется задача с явным фильтром.
18. <a id="REQ-PROJECT-PROCESS-012"></a> **REQ-PROJECT-PROCESS-012** — Одновременные прогоны, использующие один каталог сборки или кеш, не запускаются; предыдущий прогон дожидается завершения.
19. <a id="REQ-PROJECT-PROCESS-013"></a> **REQ-PROJECT-PROCESS-013** — После изменения задач или выпусков пересобираются их сводки и выполняется проверка документации.

## Работа с репозиторием

20. <a id="REQ-PROJECT-PROCESS-023"></a> **REQ-PROJECT-PROCESS-023** — Работа ведётся в `main` и всегда по конкретной задаче: коммит без задачи не объясняет, зачем он сделан. Сообщение фиксации начинается с идентификатора этой задачи, а не называет её где-то в теле: по началу строки связь читается и человеком, и проверкой (`REQ-RELEASE-036`). Коммит, обслуживающий сам выпуск, задачи не имеет и несёт вместо неё строку `Release-cycle: <идентификатор выпуска>`. При открытом выпуске задача попадает в его состав (`REQ-RELEASE-007`); когда открытого выпуска нет, работа так же идёт в `main`, а задача остаётся в статусе `in_progress` до своего выпуска. Решение владельца от 2026-09-10.
21. <a id="REQ-PROJECT-PROCESS-014"></a> **REQ-PROJECT-PROCESS-014** — Операции с рабочим деревом и ветками выполняются обычным CLI `git`: коммит, отправка, слияние, перенос файлов. Клиент `gh` для них не нужен.
22. <a id="REQ-PROJECT-PROCESS-015"></a> **REQ-PROJECT-PROCESS-015** — Для того, чего `git` не умеет, используется `gh`: pull request, обсуждения, секреты репозитория, состояние прогонов и запросы к API. Обходить его самодельными вызовами API с ручной подстановкой токена не нужно.
23. <a id="REQ-PROJECT-PROCESS-016"></a> **REQ-PROJECT-PROCESS-016** — Учётные данные в командах не появляются: `gh` использует собственную авторизацию, а секреты задаются из файла или потока ввода, а не аргументом команды.
