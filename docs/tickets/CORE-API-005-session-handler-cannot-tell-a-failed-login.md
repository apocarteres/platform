# Обработчик истёкшей сессии не отличает её от неудачного входа

## Проблема

`sessionExpiredInterceptor` зовёт обработчик токена `SESSION_EXPIRED` на любом
ответе 401. Обработчик объявлен как `() => void`: он получает факт отказа и
больше ничего — ни запроса, ни разобранного тела.

Между тем 401 приходит и при целой сессии: неверный пароль на входе, выход,
регистрация, восстановление пароля, проверка версии клиента. Отличить эти
случаи обработчику нечем, а выбрасывать пользователя на страницу входа при
неверном пароле — не то поведение, которого ждут.

## Чем подтверждено

Заявка потребителя `clanlog` от 2026-09-11, ядро 1.6.0, пункт 3:
https://github.com/apocarteres/platform/issues/1

Потребитель перехватчик ядра **не подключил**: оставил свой, который
отбрасывает перечисленные пути и склеивает остальные окном 1,5 секунды.
Средство ядра в этой части им не принято.

Подпись подтверждена по коду: `packages/http/src/session-interceptor.ts`,
`new InjectionToken<() => void>`.

## Последствия при сохранении текущего поведения

1. Перехватчик ядра непригоден для приложения, где 401 означает не только
   истёкшую сессию, — то есть для любого приложения со входом по паролю.
2. Потребитель держит свой перехватчик, и клиентская половина контракта
   принимается наполовину.
3. Решение о том, что считать истёкшей сессией, остаётся у ядра, хотя знает об
   этом только приложение.

## Ожидаемый результат

Обработчик получает достаточно, чтобы решить самому: запрос и разобранный
отказ. Решение остаётся за приложением — ядро сообщает о событии, а не
толкует его.

## Критерии приёмки

- `SESSION_EXPIRED` принимает запрос и разобранный отказ.
- Тест на собранном конвейере: обработчик получает путь запроса и код отказа и
  может по ним различить случаи.
- Отказ по-прежнему пробрасывается дальше, а отсутствие обработчика
  по-прежнему роняет запрос названной ошибкой (`CORE-API-003`).
- Изменение подписи названо в обязательстве `web-errors`.
