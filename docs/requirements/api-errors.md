# Контракт ошибок API

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: HTTP-интерфейсы любого сервиса.** Требования не зависят от предметной области сервиса и от того, кто его клиент.

**Уровень требования: директива.**

## Форма ответа

1. <a id="REQ-API-001"></a> **REQ-API-001** — Ошибка HTTP отдаётся как `ProblemDetail` по RFC 9457 с типом содержимого `application/problem+json`: `type`, `title`, `status`, `detail`, `instance` и расширение `code`. Собственных форм тела ошибки сервис не вводит: клиент разбирает один контракт, а не по одному на сервис.
2. <a id="REQ-API-002"></a> **REQ-API-002** — Соответствие исключения коду и статусу задаёт сервис портом `ErrorCodeResolver`: ядро не знает его исключений. Неопознанное исключение отдаётся как `500` с кодом `unexpected`; исключение платформы приложений сохраняет свой статус, а код выводится из статуса. Молча превращать отказ клиента в отказ сервера нельзя: `404` и `400`, отданные как `500`, уводят разбор в неверную сторону.
3. <a id="REQ-API-003"></a> **REQ-API-003** — Текст `detail` даёт порт `ErrorMessages`. Реализация по умолчанию не раскрывает сообщение исключения: сообщение пишется для разработчика и способно нести имена, пути и части запроса. Сервис заменяет порт, когда ему нужны собственные тексты или их перевод.

## Наблюдаемость

4. <a id="REQ-API-004"></a> **REQ-API-004** — Ошибки считаются метрикой с кодом, статусом и шаблоном пути. Путь нормализуется по лучшему совпадению шаблона обработчика: конкретный адрес `/players/17` в метрику не попадает, иначе число рядов растёт с числом запросов, а не с числом обработчиков.

## Что сервис добавляет к ответу

5. <a id="REQ-API-007"></a> **REQ-API-007** — Сервис добавляет к телу ошибки собственные поля расширения портом, а не своей формой тела: RFC 9457 расширения допускает, и корреляционный идентификатор запроса, доступное количество, перечень занятых строк принадлежат ответу, а не сообщению. Обязательные поля и расширение `code` остаются за ядром. Без объявленного порта тело прежнее.
6. <a id="REQ-API-008"></a> **REQ-API-008** — Ответ об ошибке несёт заголовки: `Retry-After`, `WWW-Authenticate` и прочие, без которых статус неполон — `429` без `Retry-After` сообщает об отказе, но не о том, когда повторять. Заголовки исключения платформы приложений доходят до ответа сами; собственные добавляет порт сервиса. Без объявленного порта заголовков не прибавляется.

## Откуда берётся поведение

7. <a id="REQ-API-005"></a> **REQ-API-005** — Контракт даёт starter ядра одним общим советом по ошибкам. В сервисе не пишется локальный обработчик, который отображает исключение в статус или вводит свою форму тела: тринадцать однотипных обработчиков в одном проекте — это тринадцать мест, где контракт расходится. Обработчик, добавлявший к ответу то, чего контракт не выражал — заголовок или собственное поле, — запретом не охватывался, и теперь не нужен: для этого есть порты (`REQ-API-007`, `REQ-API-008`). Уточнено 2026-09-11 по заявке потребителя, исполнившего обязательство и оставшегося с двумя такими обработчиками.
8. <a id="REQ-API-006"></a> **REQ-API-006** — Совет по ошибкам объявлен для сервлетного веб-приложения и в других рантаймах не поднимается. Это не делает его условным бином вне правила `REQ-QUALITY-012`: рантайм, у которого нет HTTP-интерфейса, в этом совете не нуждается, и проверка проводки утверждает именно такое поведение, а не обходит его.
