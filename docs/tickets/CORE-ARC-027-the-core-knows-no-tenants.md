# Ядро не знает арендаторов

## Проблема

Потребитель хочет обслуживать несколько независимых арендаторов в одном
процессе и одной базе: у каждого свой домен, свои учётные записи, свои
администраторы и свои данные (заявка ZAVPN-IDEA-004 от 2026-10-23, выбор —
общие таблицы с полем арендатора и политиками строк Postgres). Учётные
записи, сессии, ключи доступа, роли и вход принадлежат ядру: почта уникальна
на весь процесс, роль `ADMIN` видит всё, сессия не привязана к домену. Без
понятия арендатора в ядре потребитель может разделить только свои таблицы,
а вход и учётные записи остаются общими.

## Последствия при сохранении текущего поведения

Второго арендатора можно обслужить только отдельным процессом и отдельной
базой; общий процесс с изоляцией строится в обход ядра.

## Ожидаемый результат

1. Арендатор — понятие ядра: таблица арендаторов, порт `TenantResolver`
   (арендатор запроса по домену; для запросов по ключу — по ключу).
2. Учётная запись принадлежит арендатору: почта уникальна в его пределах;
   роли — в его пределах; отдельная роль уровня платформы над арендаторами.
3. Сессия привязана к арендатору: сессия, выпущенная на домене одного
   арендатора, на домене другого недействительна; ключи доступа — так же.
4. Транзакция знает арендатора: ядро ставит `SET LOCAL <настройка арендатора>`
   в начале транзакции запроса; правила доступа к данным (`REQ-DATA-ACCESS`)
   описывают таблицы арендатора, составные внешние ключи и политики строк;
   архитектурная проверка находит таблицу без поля арендатора и политики.
5. Фоновые операции выполняются явно в пределах арендатора; без
   установленного арендатора запрос к таблице арендатора отказывает.
6. Порты, зависящие от арендатора (`AuthLetters`, `HumanCheck`, настройки
   ссылок писем), получают арендатора.
7. Переход потребителя: все существующие данные становятся одним
   арендатором по умолчанию, поведение до появления второго не меняется.
   Изменение несовместимо — старшая версия с описанной миграцией.

## Открытые вопросы

1. Нужен ли второму потребителю ядра режим без арендаторов, или один
   арендатор по умолчанию покрывает и его.
2. Выгрузка и удаление одного арендатора — в ядре (учётные записи, сессии,
   ключи) или только в потребителе.

## Критерии приёмки

1. Учётная запись одного арендатора не входит на домене другого.
2. Запрос без арендатора к таблице арендатора отказывает.
3. Потребитель с одним арендатором обновляется без изменения поведения.
