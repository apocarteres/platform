# ADR-0007: центр поддержки пользователей — что поставляет ядро

Дата исследования: 2026-09-24. Основание — задача `CORE-ARC-012` по заявке
потребителя. Решения не приняты: каждое записано вариантами с рекомендацией и
ждёт владельца.

**Решение владельца от 2026-09-24:** форма — библиотека (вопрос 1), но строится
она поверх входа, который поставит ядро (`CORE-ARC-013`): автор обращения —
учётная запись ядра, оператор — роль, объявленная проектом. До выпуска входа
центр поддержки на паузе; вопросы 3–5 ждут возобновления.

## Что есть у потребителя

Модуль обратной связи Clan Log разобран по коду.

- **Сервер:** 20 файлов, 1313 строк, 21 запрос SQL, 3 перехода базы; три
  таблицы — обращение, ход обращения, вложения.
- **Клиент:** 15 файлов, 1306 строк; журнал клиента — 127 строк.
- **Тесты:** полный цикл обращения интеграционным тестом, два сквозных
  сценария.

Портов в заявке названо три — пользователь, почта, ограничитель частоты.
Фактически связей больше:

- **База:** внешний ключ обращения и хода на таблицу игроков.
- **Роль оператора:** строка `ADMIN` в коде модуля.
- **Пакеты проекта:** шесть — хранилище файлов, замок работ, постраничность,
  время, слой, ошибки API.
- **Ограничитель частоты:** правила частоты зашиты в модуль входа.
- **Клиент:** переводы, сессия, модальные окна, постраничность проекта.

Сервер и экраны переносимы после работы по развязке. Журнал клиента переносим
почти как есть: из кода проекта он берёт только часы.

У второго потребителя, zavpn, приёма обращений и журнала клиента нет.

### Найдено при разборе

Эти дефекты проекта ядро обязано не повторить. Потребитель о них знает, два
заведены у него задачами:

1. **Полный адрес страницы в снимке.** В снимок попадает адрес вместе со
   строкой запроса и фрагментом, а там бывают одноразовые ключи (`CL-SEC-037`).
2. **Предел тела не проверяется до разбора.** Он общий на всё приложение —
   128 МБ, и разбор идёт раньше ограничителя частоты и пределов вложений
   (`CL-SEC-038`).
3. **Письмо с ответом уходит внутри транзакции**, до её фиксации: при откате
   письмо уже отправлено. Задачи у потребителя нет.
4. **Журнал клиента хранится бессрочно** как поле обращения. Сам модуль тоже
   не удаляется никогда (ADR потребителя), а это расходится с правом субъекта
   персональных данных требовать удаления.
5. **Стирание вложений запускает планировщик внутри приложения.** Для
   поставки ядра так нельзя: ядро не запускает фоновую работу само.

## Вопрос 1. Форма: библиотека или сервис

**A. Библиотека** — starter `platform-feedback` и пакет клиента.

- Обращения, авторы и операторы — данные и пользователи самого проекта.
- Библиотека живёт в его базе, его входе и его ролях.
- Оператором персональных данных остаётся проект.

**B. Отдельный сервис**, как решено для уведомлений (`ADR-0001`, вопрос 3).

- Уведомления — исходящая доставка, почти не связанная с тем, кто вошёл.
- Поддержке сервис дал бы общую очередь для нескольких проектов.
- Цена: единый вход или передача личности между системами, второе место
  хранения персональных данных, свой развёрнутый процесс.

**Рекомендация: A.** Уведомления оператору всё равно пойдут через сервис
уведомлений, когда он появится (`CORE-ARC-001`); до того — портом.

## Вопрос 2. Когда выносить код

Сейчас функция есть у одного потребителя. Ядро, вынесшее модуль ради одного
проекта, получает абстракцию, проверенную одной формой.

**A. Вынести модуль целиком сейчас.**

**B. Сначала требования, код — по шагам.**

1. Требование `REQ-SUPPORT` к персональным данным и приёму без входа
   (вопросы 3 и 4) — сразу. Оно нормирует и форму обратной связи, которую
   проект пишет сам, и закрывает найденные дефекты у всех.
2. Пакет `@apocarteres/client-journal` — следующим шагом. Он почти
   самостоятелен и полезен для разбора отказов и без поддержки.
3. Starter и логика экранов обращений — когда функция понадобится второму
   проекту либо по решению владельца раньше.

**Рекомендация: B.**

## Вопрос 3. Персональные данные (152-ФЗ)

Предлагаемые положения. Правовая часть — согласие, текст соглашения, порядок
ответа на запрос субъекта — остаётся проекту: ядро требует, чтобы она была,
а не пишет её.

1. **Цель обработки** — разбор обращения. Снимок и журнал прикладываются только
   при отправке обращения, и форма об этом говорит.
2. **Адрес страницы** в снимке и журнале — происхождение и путь. Строка запроса
   и фрагмент отбрасываются до записи на клиенте и ещё раз на сервере.
3. **Маскирование до записи** — почта, телефоны, маркеры от 20 знаков. Одни
   общие примеры для клиента и сервера, как у версии API
   (`REQ-CLIENT-UPDATE-007`).
4. **Сроки хранения конечны и объявлены проектом**; значения ядра по
   умолчанию:
   - вложения — 1 год после закрытия;
   - журнал и снимок — 1 год после закрытия;
   - почта невошедшего — 1 год после закрытия.

   Бессрочного хранения журнала нет.
5. **Удаление по запросу субъекта** — явная команда: стирает содержимое
   обращений автора и оставляет в ходе отметку. Правило «обращения не
   удаляются» не перекрывает запрос субъекта.
6. **Доступ** — автор и роль оператора, которую объявляет проект. Почту и
   журнал видит только оператор.
7. **Стирание по сроку** — явная команда, которую потребитель вызывает своим
   планировщиком. Для двух экземпляров — под замком `JobLock`
   (`REQ-DEPLOYMENT-028`).

## Вопрос 4. Приём без входа

1. **Предел тела** объявлен для точки приёма и проверяется **до разбора** — и
   на веб-сервере, и в приложении. Общий предел приложения точку не
   описывает.
2. **Ограничитель частоты** — по адресу сети и по почте, до разбора тела; если
   ограничитель недоступен — отказ, а не пропуск. В базе адрес сети не
   хранится, только отпечаток в ограничителе со сроком.
3. **Письма** уходят после фиксации транзакции.
4. **На неподтверждённую почту** содержимое обращения и ответа не
   отправляется. Письмо только сообщает, что ответ есть, и ведёт по ссылке с
   подтверждением. Иначе форма без входа позволяет слать письма с чужим
   текстом на любой адрес.

## Вопрос 5. Состояния

У потребителя оператор переводит обращение из любого состояния в любое, а
повторное открытие сбрасывает срок хранения вложений.

**Предложение:** четыре состояния — `NEW`, `IN_PROGRESS`, `ANSWERED`,
`CLOSED` — с разрешёнными переходами. Сообщение автора переводит `ANSWERED`
обратно в `IN_PROGRESS`. Срок хранения считается от последнего закрытия, и
каждая смена пишется в ход.

**Рекомендация:** принять, если выбран вынос кода (вопрос 2).

## Что следует из решения

Если приняты рекомендации:

1. **Задача на требование `REQ-SUPPORT`** — вопросы 3 и 4. Потребителю —
   обязательство со сроком для проектов с формой обращения; признак — раздел
   `.conventions.json`.
2. **Задача на `@apocarteres/client-journal`** — маскирование и адрес по
   вопросу 3; срок хранения объявляет проект.
3. **Starter и экраны** — отложены до второго проекта с этой функцией.
4. **Ответ потребителю:** найденные дефекты 3–5 и первый шаг ядра.
