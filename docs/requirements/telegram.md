# Telegram: связь учётной записи с ботом проекта

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: служба на Spring Boot с аутентификацией ядра и её одностраничный клиент, подключившие Telegram.** Ядро поставляет модуль библиотекой: starter `platform-telegram` и пакет клиента `@apocarteres/telegram`. Модуль необязателен: проект без него требованию не подлежит. Решение владельца от 2026-11-16: Telegram — подключаемый модуль ядра, по этапам — связь, уведомления (`CORE-ARC-031`), вход из Mini App (`CORE-ARC-032`), вход на сайт и второй шаг (`CORE-ARC-033`). Документ описывает первый этап — связь.

**Уровень требования: директива.**

Связь хранит идентификатор человека в Telegram и номер его личного чата с ботом — персональные данные по 152-ФЗ. Учётная запись без почты модулем не заводится: связь всегда принадлежит учётной записи ядра (`REQ-AUTH-001`).

## Модуль

1. <a id="REQ-TELEGRAM-001"></a> **REQ-TELEGRAM-001** — Модуль строится поверх аутентификации ядра (`REQ-AUTH`): связь принадлежит учётной записи ядра. Таблицы создаёт журнал ядра `platform/changelog/platform-telegram.yaml`, который проект подключает в главный журнал Liquibase после журнала `platform-auth` (`REQ-DATA-ACCESS-007`); образцы `sql/platform-telegram/create-*.sql` — справка.
2. <a id="REQ-TELEGRAM-002"></a> **REQ-TELEGRAM-002** — Бот проекта описан настройками `platform.telegram.*`: `bot-token` — токен бота, `bot-name` — имя бота без `@`, `webhook-secret` — секрет webhook, от 32 до 256 знаков из латинских букв, цифр, `_` и `-`. Токен и секрет — секреты и приходят из окружения (`REQ-CONFIG-001`). Без любой из трёх настроек и с неверной формой служба не стартует; отказ называет настройку, но не её значение. Срок ссылки связи — `platform.telegram.link-ttl`, по умолчанию 10 минут, положительный и не длиннее суток. Адрес Bot API — `platform.telegram.api-base`, по умолчанию `https://api.telegram.org`; переопределяется для тестов.

## Webhook

3. <a id="REQ-TELEGRAM-003"></a> **REQ-TELEGRAM-003** — Обновления бота приходят на `POST /api/telegram/webhook`. Запрос удостоверяет модуль портом `RequestAuthenticator` (`REQ-AUTH-037`): заголовок `X-Telegram-Bot-Api-Secret-Token` сверяется с `webhook-secret` сравнением постоянного времени. Нет заголовка или он неверен — отказ ядра `identity-rejected` с кодом 401 до разбора обновления, и ничего не меняется. Удостоверенный запрос несёт внешнюю личность `telegram:webhook` без ролей; частоту ограничивает ядро (`REQ-AUTH-038`), и проект задаёт `platform.auth.external.requests-per-minute` по потоку своего бота. Свой путь модуль отдаёт порту сам, поэтому проекту с Mini App путь webhook в своём порту объявлять не нужно.
4. <a id="REQ-TELEGRAM-004"></a> **REQ-TELEGRAM-004** — Удостоверенное обновление получает ответ 200, даже если модуль его не понял: на любой другой ответ Telegram повторяет обновление. Модуль читает только команду `/start <токен>` из личного чата; прочее пропускается без ответа.
5. <a id="REQ-TELEGRAM-005"></a> **REQ-TELEGRAM-005** — Webhook регистрирует явная команда `TelegramBot.useWebhook(url)`: она передаёт Telegram адрес и секрет из настроек, так что секрет у проекта не расходится с модулем. Ядро не регистрирует webhook само (требование к ядру о фоновой работе); проект вызывает команду при выкладке или из своей служебной точки.

## Связь

6. <a id="REQ-TELEGRAM-006"></a> **REQ-TELEGRAM-006** — Вошедший получает ссылку связи `POST /api/telegram/link`: `https://t.me/<bot-name>?start=<токен>` и срок её действия. Токен — 32 случайных байта в base64url, хранится только отпечатком SHA-256. Ссылка одноразовая, и у учётной записи действует одна: новая выдача гасит прежнюю. Учётной записи, у которой связь уже есть, ссылка не выдаётся — отказ `telegram-already-linked` с кодом 409: связь сначала снимают.
7. <a id="REQ-TELEGRAM-007"></a> **REQ-TELEGRAM-007** — Команда `/start <токен>` из личного чата записывает связь учётной записи, выдавшей токен, с человеком и чатом Telegram. Токен гасится при любом исходе. Связь не записывается, если токен истёк, уже использован или не выдавался; если у учётной записи уже есть связь; если этот человек Telegram уже связан с другой учётной записью. У учётной записи одна связь, у человека Telegram — одна учётная запись: иначе вход через Telegram (`CORE-ARC-033`) не знал бы, кого пускать.
8. <a id="REQ-TELEGRAM-008"></a> **REQ-TELEGRAM-008** — Ответ в чат на `/start` пишет проект портом `TelegramReplies`: `linked(language)` и `refused(language)`, где `language` — `language_code` человека из обновления, может быть пустым. Пустой текст — без ответа; без бина модуль отвечает молча (`TelegramReplies.SILENT`). У ядра нет текстов и перевода (`CORE-ARC-028`). Ответ уходит телом ответа webhook методом `sendMessage`, без отдельного вызова Bot API.
9. <a id="REQ-TELEGRAM-009"></a> **REQ-TELEGRAM-009** — Владелец видит связь `GET /api/telegram/link` — есть ли она и когда записана — и снимает её `DELETE /api/telegram/link`; снятие отсутствующей связи безвредно. Код проекта читает и снимает связь Java API `TelegramLinks`: `chat(account)` и `unlink(account)`. Точки — только вошедшему и только о своей связи.

## Персональные данные

10. <a id="REQ-TELEGRAM-010"></a> **REQ-TELEGRAM-010** — Идентификатор человека в Telegram и номер чата — персональные данные (`REQ-AUTH-040`): в журналы, метки метрик и ответы об ошибках они не попадают, и точки модуля их не отдают — владельцу достаточно знать, что связь есть. Удаление учётной записи (`REQ-AUTH-024`) стирает её связь и невыданную ссылку внешним ключом с каскадом: исход — `REMOVED`, а не `HELD`.

## Bot API

11. <a id="REQ-TELEGRAM-011"></a> **REQ-TELEGRAM-011** — Вызовы Bot API идут через `TelegramBot`: `send(chat, text)` и `useWebhook(url)`. Адрес метода Bot API содержит токен бота, поэтому отказ `TelegramUnavailable` не несёт ни адреса, ни исходного исключения с ним — только имя метода и описание Telegram. Повторов и очереди у клиента нет: доставку уведомлений с ними решает второй этап (`CORE-ARC-031`).

## Контракт и клиент

12. <a id="REQ-TELEGRAM-012"></a> **REQ-TELEGRAM-012** — Точки модуля описаны контрактом OpenAPI `platform-telegram/src/main/resources/openapi/platform-telegram.openapi.json`, копия лежит в пакете клиента, типы клиента выводятся из него (`npm run contract-types`). Тест держит контроллер в соответствии с контрактом: пути, поля и коды отказов.
13. <a id="REQ-TELEGRAM-013"></a> **REQ-TELEGRAM-013** — Клиент объявляет модуль один раз — `provideTelegram({ base })` — и получает `TelegramLink`: сигнал `state` — состояние связи или `null` до первого чтения и без входа, `refresh()`, `invite()` — ссылка связи, `unlink()`. Экраны и переход по ссылке — проекту: ядро не знает, открывать ли ссылку в новой вкладке или показывать код.
