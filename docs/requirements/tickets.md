# Документ задачи

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он описывает форму документа задачи. Когда задача создаётся и чем подтверждается находка — в [порядке ведения проекта](project-process.md).

**Уровень требования: директива.**

## Содержание

1. <a id="REQ-TICKETS-001"></a> **REQ-TICKETS-001** — В задаче есть проблема, подтверждение, последствия при сохранении текущего поведения, ожидаемый результат и критерии приёмки. Задача без критериев приёмки закрыта быть не может: нечего проверять.
2. <a id="REQ-TICKETS-002"></a> **REQ-TICKETS-002** — Гипотеза обозначается гипотезой с указанием способа проверки. Выдать её за доказанный дефект — исказить постановку.
3. <a id="REQ-TICKETS-003"></a> **REQ-TICKETS-003** — Ход работы записывается в самой задаче: принятые решения, изменения, результаты проверок. Непроверенная часть остаётся явно названной, а не умолчанной.
4. <a id="REQ-TICKETS-004"></a> **REQ-TICKETS-004** — Отменённая задача обязана содержать раздел «Почему не делаем» с тем, что опровергло постановку. Отсутствие раздела — отказ проверки. Отменять при открытых вопросах можно: решение не делать — это ответ на них, а не работа в обход.

## Метаданные

5. <a id="REQ-TICKETS-005"></a> **REQ-TICKETS-005** — Идентификатор задачи стабилен при переносе и переименовании файла: на него ссылаются выпуски, требования и другие задачи.
6. <a id="REQ-TICKETS-006"></a> **REQ-TICKETS-006** — Обязательное поле `priority`: `P0`, `P1`, `P2`, `P3` или `unassigned`; меньший номер означает более высокий приоритет. `unassigned` означает, что приоритет не определён и назначается до начала работы. Отсутствующий приоритет при переносе документов не придумывается.
7. <a id="REQ-TICKETS-007"></a> **REQ-TICKETS-007** — Поле `status` принимает: `backlog` — запланирована, `in_progress` — выполняется, `blocked` — заблокирована, `done` — выполнена, `cancelled` — закрыта решением не делать, `superseded` — заменена другой задачей. Для `superseded` обязательно `superseded-by`.
8. <a id="REQ-TICKETS-008"></a> **REQ-TICKETS-008** — Область задачи задаётся полем `scope`, а не каталогом: каталоги по областям не заводятся, сводки группируются по метаданным.
9. <a id="REQ-TICKETS-009"></a> **REQ-TICKETS-009** — Обязательное поле `release`: идентификатор выпуска, `unassigned` или `before-cycle`; принадлежность сверяется с составом выпуска в обе стороны (`REQ-RELEASE-007`, `REQ-RELEASE-020`).
10. <a id="REQ-TICKETS-010"></a> **REQ-TICKETS-010** — Зависимости записываются в `depends-on`, связи — в `related`. Приоритет и состояние живут только в метаданных: сводки получают их оттуда и вручную не правятся.

## Вопросы

11. <a id="REQ-TICKETS-011"></a> **REQ-TICKETS-011** — Вопрос, от которого зависит реализация, живёт в разделе «Открытые вопросы»; при наличии раздела обязательно поле `questions` со значением `open` или `resolved`, без раздела поле запрещено. Ответ и дата решения записываются рядом с вопросом, а постановка обновляется по договорённости.
12. <a id="REQ-TICKETS-012"></a> **REQ-TICKETS-012** — При `questions: open` запрещены `in_progress` и любой терминальный статус. Возникший в работе блокирующий вопрос переводит задачу в `blocked`. Задача не закрывается с открытым вопросом и тогда, когда её закрывают решением не делать: неразрешённый вопрос выносится отдельной задачей (`REQ-PROJECT-PROCESS-005`, `REQ-PROJECT-PROCESS-009`), иначе вопрос исчезает вместе с закрытой задачей, а отмена по `REQ-TICKETS-004` объясняет решение, но не отвечает на него. Решение владельца от 2026-09-10.

## Расположение и закрытие

13. <a id="REQ-TICKETS-013"></a> **REQ-TICKETS-013** — Самостоятельная задача в терминальном статусе лежит в каталоге `closed/`, открытая — в корне каталога задач. Перенос выполняется средствами системы контроля версий, ссылки внутри документа и на него обновляются вслед.
14. <a id="REQ-TICKETS-014"></a> **REQ-TICKETS-014** — Этапы и головной документ плана функции хранятся вместе, чтобы порядок плана оставался читаемым; их завершённость определяется метаданными, а не расположением.
15. <a id="REQ-TICKETS-015"></a> **REQ-TICKETS-015** — Перед переводом в `done` проверяются критерии приёмки, записываются результаты проверок и обновляются требования. Зелёная проверка сама по себе корректности решения не доказывает: её достаточность подтверждает исполнитель.
16. <a id="REQ-TICKETS-016"></a> **REQ-TICKETS-016** — Закрытие задачи не снимает её принадлежность выпуску: запись о том, в каком выпуске работа вышла, сохраняется.
