# Открытие выпуска создаёт задачу обязательства с именем, которое отвергает проверка правил

## Проблема

Материализация обязательства ядра при открытии выпуска (`REQ-RELEASE-013`)
создаёт документ задачи с идентификатором вида
`TICKET-ADOPT-<ОБЯЗАТЕЛЬСТВО>-<ДАТА>` и одноимённым файлом. Такой
идентификатор не соответствует `REQ-NAMING-001` — область и трёхзначный
номер — а имя файла не соответствует `REQ-NAMING-005`. Проверка правил того же
ядра этот документ отвергает.

Потребитель получает проект, который не проходит собственную проверку сразу
после штатной команды открытия выпуска, и вынужден переименовывать документ
руками.

## Чем подтверждено

Прогон 2026-09-11 на ядре 1.3.0 в проекте-потребителе со схемой номеров
`date`.

```
$ conventions release open --version 2026.09.9
Открыт выпуск RELEASE-2026-09-9, тег при закрытии: 2026.09.9.
- обязательство материализовано задачей TICKET-ADOPT-WIRING-CHECK-2026-09-11

$ conventions check
Проверка правил не пройдена:
- docs/tickets/adopt-wiring-check-2026-09-11.md: расхождений имени и
  идентификатора 1, зафиксировано 0 (REQ-NAMING)
- docs/tickets/adopt-wiring-check-2026-09-11.md:1: имя файла задачи должно быть
  <ОБЛАСТЬ>-<NNN>-<слаг>.md, область из перечня: ARC, API, DATA, FEAT, SEC,
  PERF, QUAL, TEST, OPS, DOC
```

Обязательство — `wiring-check` (`REQ-QUALITY-012`), объявленное ядром 1.3.0.
После ручного переименования документа в `CORE-OPS-026-adopt-wiring-check.md` с
идентификатором `CORE-OPS-026` проверка проходит.

## Границы задачи

Связь обязательства с задачей от переименования не страдает:
`.conventions/obligations.json` хранит идентификатор задачи только в разделе
`closed`, куда он попадает командой `release satisfy`. Поэтому задача о том,
каким именем документ создаётся, а не о способе хранения связи.

## Последствия при сохранении текущего поведения

Штатная команда ядра оставляет проект потребителя в состоянии, которого не
принимает проверка того же ядра. Потребитель либо чинит документ руками при
каждом открытии выпуска с новым обязательством, либо опускает храповик
именования и теряет проверку для всех задач разом.

Отдельно страдает состав выпуска: он ссылается на задачу по прежнему
идентификатору, поэтому переименование требует согласованной правки документа
выпуска, который по `REQ-RELEASE-022` пишет команда, а не человек.

## Ожидаемый результат

Задача, материализующая обязательство, создаётся с идентификатором,
удовлетворяющим `REQ-NAMING-001`: область из закрытого перечня и следующий
свободный трёхзначный номер в ней. Имя файла соответствует `REQ-NAMING-005`.
Состав выпуска ссылается на этот же идентификатор, ручная правка не требуется.

## Критерии приёмки

1. Открытие выпуска с незакрытым обязательством создаёт задачу с
   идентификатором вида `<ОБЛАСТЬ>-<NNN>` и соответствующим именем файла.
2. Номер выбирается следующим свободным в своей области и не переиспользуется
   (`REQ-NAMING-003`).
3. Состав открытого выпуска ссылается на созданную задачу её идентификатором.
4. `conventions check` и `conventions docs-check` проходят на проекте сразу
   после открытия выпуска, без ручных правок.
5. Тест закрепляет имя и идентификатор созданной задачи.
