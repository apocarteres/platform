# OpenAPI-контракт аутентификации ядра и типизированный профиль проекта

## Проблема

HTTP-API аутентификации ядра описан только текстом `REQ-AUTH` и константами
кодов. Потребитель, ведущий контракт в OpenAPI, после перехода теряет в
спецификации точки `/api/auth/*`; потребитель, строящий спецификацию из кода,
получает её без кодов ошибок и `ProblemDetail`. Профиль регистрации приходит
хуку словарём, и каждый проект разбирает его руками.

## Решение владельца

Решение владельца от 2026-09-24 — идея
[CORE-IDEA-001](../ideas/CORE-IDEA-001-openapi-contract-for-core-auth.md)
принята:

- `platform-auth` поставляет `openapi/auth.yaml`, тест держит контроллеры в
  соответствии с ним; код у потребителя не генерируется;
- клиент берёт из контракта только типы;
- `RegistrationHook<P>` с объявленным классом профиля **заменяет**
  `Map<String, Object>`: ядро разбирает и проверяет профиль до транзакции,
  отказ `400 profile-rejected`; клиент — `register<P>`. Старшая версия;
- профиль проекта ядру не принадлежит: `GET /api/auth/me` отдаёт только
  учётную запись, профиль проект отдаёт своей точкой;
- «Цена обновления» сверяет две версии контракта: снятая точка, поле или код
  ответа — несовместимость.

## Требуется

1. `openapi/auth.yaml` в поставке `platform-auth`: пути, схемы запросов и
   ответов, `ProblemDetail` и перечень кодов по точкам, `X-Api-Version`;
   `profile` открыт и помечен «схему задаёт проект».
2. Тест контракта: каждая точка контроллера описана, каждая описанная точка
   есть, коды отказов из `AuthRefused` и `ProblemResponses` совпадают с
   перечисленными.
3. `RegistrationHook<P>` и объявление класса профиля; проверка Bean Validation;
   `profile-rejected`. `Accounts.create` и профиль первого администратора
   проходят тот же разбор.
4. Типы клиента из контракта; `register<P>`.
5. Образцы подключения: ссылка из спецификации проекта с исключением путей
   ядра из генерации; `OpenApiCustomizer` для `springdoc`.
6. Сверка контрактов двух версий в «Цене обновления» и в `upgrade-report`.
