# Центр поддержки: обращения, ход, место оператора

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: служба на Spring Boot с аутентификацией ядра и её одностраничный клиент, подключившие центр поддержки.** Ядро поставляет центр библиотекой: starter `platform-support` и пакет клиента `@apocarteres/support`. Сервер и логика клиента — от ядра, экраны — от проекта. Центр необязателен: проект без него требованию не подлежит. Решения владельца от 2026-09-24 и 2026-09-25 — [ADR-0007](../decisions/ADR-0007-user-support-centre.md); основание — модуль обратной связи потребителя и дефекты, найденные при его разборе.

**Уровень требования: директива.**

Центр обрабатывает персональные данные по 152-ФЗ: почту, текст обращения, снимки экрана, журнал клиента. Ядро даёт механизмы — маскирование до записи, сроки хранения, удаление по запросу субъекта, узкий доступ. Правовая часть остаётся проекту: цель обработки в тексте соглашения, уведомление человека о снимке и журнале, порядок ответа на запрос субъекта.

## Обращение

1. <a id="REQ-SUPPORT-001"></a> **REQ-SUPPORT-001** — Центр строится поверх аутентификации ядра (`REQ-AUTH`): автор обращения — учётная запись ядра, оператор — роль проекта, названная настройкой `platform.support.operator-role` и объявленная в `platform.auth.roles`; без настройки и с необъявленной ролью служба не стартует. Таблицы проект создаёт своими переходами базы по образцам `sql/platform-support/create-*.sql`. Обращение называется UUID; номер — для людей, по номеру доступа нет. Текст обращения — от 1 до 4000 знаков; принятое обращение отвечает `201` с идентификатором и номером.
2. <a id="REQ-SUPPORT-002"></a> **REQ-SUPPORT-002** — Приём без входа проект объявляет портом `GuestIntake`: `GuestIntake.OPEN`, `GuestIntake.CLOSED` или своё условие по запросу. Молчание решением не считается: без бина служба не стартует. При закрытом приёме обращение невошедшего отказывает кодом `guest-intake-closed`; при открытом почта обязательна (`guest-email-rejected`). Точка `/api/support/policy` сообщает клиенту пределы и открыт ли приём. Самый частый повод обратиться — «не могу войти», поэтому решение о приёме без входа — решение о главном сценарии, а не подробность.

## Приём без входа

3. <a id="REQ-SUPPORT-003"></a> **REQ-SUPPORT-003** — Предел тела обращения проверяется **до разбора**: фильтр центра стоит раньше цепочки безопасности, потому что разбор multipart начинается в `DispatcherServlet`, а проверка CSRF без заголовка читает параметр и начинает разбор ещё раньше. Длина тела обязана быть объявлена (`length-required`, `411`) и не больше 16 МБ (`body-too-large`, `413`). До разбора же работает ограничитель частоты по адресу сети — 10 обращений в час; после разбора — 3 в час по почте невошедшего и 10 по учётной записи; недоступный ограничитель — отказ `503`, а не пропуск (`REQ-AUTH-011`). Общий предел multipart приложения не ниже вложения и тела центра: иначе служба не стартует и называет настройку `spring.servlet.multipart.*` — вложение отказало бы раньше, чем его увидит центр.
4. <a id="REQ-SUPPORT-004"></a> **REQ-SUPPORT-004** — На неподтверждённую почту текст ответа не отправляется. Невошедший получает письмо, что ответ есть, со ссылкой-ключом; ключ действует 7 дней (`platform.support.answer-link.ttl`), в базе хранится его отпечаток, и по ключу ответ открывается на чтение, без права писать. Ссылка и есть подтверждение почты: иначе форма без входа позволяла бы слать письма с чужим текстом на любой адрес. Ключи стираются вместе с почтой по сроку и при удалении по запросу субъекта.

## Вложения, снимок и журнал

5. <a id="REQ-SUPPORT-005"></a> **REQ-SUPPORT-005** — Вложений не больше трёх, каждое — PNG или JPEG по содержимому файла, а не по имени и заявленному типу, и не больше 5 МБ (`attachment-rejected`). Хранилище — порт `AttachmentStore`; по умолчанию — таблица ядра в базе проекта, бин проекта заменяет её объектным хранилищем, и его удаление обязано быть повторяемым. Вложение отдаётся автору и оператору с `Content-Disposition: attachment` и `X-Content-Type-Options: nosniff`; имя файла маскируется, как журнал.
6. <a id="REQ-SUPPORT-006"></a> **REQ-SUPPORT-006** — Адрес страницы в снимке — путь без строки запроса и фрагмента: на клиенте и ещё раз на сервере. Сервер маскирует журнал ещё раз по общим примерам журнала клиента (`REQ-CLIENT-JOURNAL-005`), отбрасывает записи чужого вида, держит не больше 5000 записей и 256 КБ, вытесняя самые старые. Строки снимка — не длиннее 300 знаков.

## Ход обращения

7. <a id="REQ-SUPPORT-007"></a> **REQ-SUPPORT-007** — Состояния — `NEW`, `IN_PROGRESS`, `ANSWERED`, `CLOSED`. Сообщение оператора переводит обращение в `ANSWERED`, сообщение автора — `ANSWERED` в `IN_PROGRESS`. Оператор переводит вручную: `NEW` — в `IN_PROGRESS` или `CLOSED`, `IN_PROGRESS` и `ANSWERED` — в `CLOSED`, `ANSWERED` — в `IN_PROGRESS`, `CLOSED` — в `IN_PROGRESS`; прочее — `transition-refused`. В закрытое обращение не пишут ни автор, ни оператор (`request-closed`): его сначала открывают снова. Каждая смена — запись в ходе с тем, чья она; изменение, пришедшее одновременно с другим, отказывает кодом `request-changed`. Ход упорядочен порядком записи, а не только временем: две записи одного момента не меняются местами.
8. <a id="REQ-SUPPORT-008"></a> **REQ-SUPPORT-008** — **Новое для оператора** — обращение, которое поддержка не смотрела, или в котором автор действовал после её просмотра; отметка одна на всех операторов. **Новое для автора** — обращение, в котором поддержка действовала после его просмотра. Просмотр отмечается отдельной командой `…/seen`: чтение обращения состояния не меняет. Счётчики отдаёт `/api/support/unread`; клиент спрашивает раз в минуту и сразу после просмотра.
9. <a id="REQ-SUPPORT-009"></a> **REQ-SUPPORT-009** — Письма центр отдаёт портом `SupportLetters`, пока нет сервиса уведомлений (`CORE-ARC-001`): `answered` — автору, с учётной записью — с текстом и ссылкой на обращение, невошедшему — по `REQ-SUPPORT-004`; `arrived` — о новом обращении и о сообщении автора, со ссылкой на место оператора. Язык письма — язык запроса, с которым обращение пришло. Письма уходят после фиксации транзакции; отказ письма не откатывает ответ и записывается в журнал службы без персональных данных — номером обращения и видом отказа.

## Хранение и удаление

10. <a id="REQ-SUPPORT-010"></a> **REQ-SUPPORT-010** — Вложения, журнал со снимком и почта невошедшего хранятся 1 год после **последнего** закрытия; проект переопределяет сроки `platform.support.retention.attachments`, `.journal`, `.guest-email` в обе стороны, но только положительными — бессрочного хранения нет, и нулевой срок останавливает запуск. Стирание — явная команда `SupportRetention.purgeExpired()`: ядро фоновую работу само не запускает, источник вызова выбирает проект. Каждая запись команды условная, поэтому одновременный запуск на двух экземплярах и повторный прогон ничего не портят; замок `JobLock` (`REQ-DEPLOYMENT-028`) не обязателен. Стёртое отмечается в ходе.
11. <a id="REQ-SUPPORT-011"></a> **REQ-SUPPORT-011** — Удаление по запросу субъекта — явные команды `SupportRetention.erase(UUID)` для учётной записи и `erase(String)` для почты невошедшего. Они стирают текст обращения и всех сообщений хода, вложения, журнал, снимок, почту и связь с учётной записью; остаются номер, состояния и моменты — остов для учёта, без персональных данных. Автор стёртое обращение больше не видит. Правило «обращения не удаляются» запрос субъекта не перекрывает. Внешний ключ держит учётную запись ядра, пока её обращения не стёрты: удалить запись раньше стирания не выйдет.

## Доступ и контракт

12. <a id="REQ-SUPPORT-012"></a> **REQ-SUPPORT-012** — Автор видит только свои обращения; чужое и стёртое отдаются как несуществующие (`request-not-found`). Оператор видит все. Почта, журнал, снимок и учётная запись автора есть только в месте оператора (`/api/support/operator/**`), и туда пускает только роль оператора (`access-denied`). Правила доступа центр объявляет `ModuleApiAccess` (`REQ-AUTH-022`).
13. <a id="REQ-SUPPORT-013"></a> **REQ-SUPPORT-013** — Точки центра описаны контрактом OpenAPI `platform-support/src/main/resources/openapi/platform-support.openapi.json`, копия лежит в пакете клиента, типы клиента выводятся из него. Тест держит контроллер в соответствии с контрактом — точки, тела, поля, состояния, коды отказов под своими статусами. Цена обновления сверяет контракт между версиями, включая значения перечислений: снятое значение несовместимо (`REQ-PUBLISHING-015`).

## Клиент

14. <a id="REQ-SUPPORT-014"></a> **REQ-SUPPORT-014** — Клиент объявляет центр один раз — `provideSupport({ journal, base, clientVersion })`. Журнал объявляется явно: `ClientJournal` из `@apocarteres/client-journal` или заглушка `NO_JOURNAL`; объявление без решения отказывает при запуске. Ядро даёт `SupportDesk` — отправка, свои обращения, ответ по ссылке, `SupportOperator` — место оператора, и `SupportUnread` — счётчики нового сигналами; формы, ленту и оформление рисует проект.
