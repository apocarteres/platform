# Клиент: журнал для разбора отказов

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: одностраничный клиент на Angular, подключивший пакет `@apocarteres/client-journal`.** Отказ, о котором человек пишет в поддержку, иначе разбирают по его словам: какой вызов не прошёл и какая ошибка была в клиенте, неизвестно. Журнал записывает это в самом браузере и отдаёт проекту по запросу. Пакет необязателен: проект без журнала требованию не подлежит. Журнал — первый шаг центра поддержки ([ADR-0007](../decisions/ADR-0007-user-support-centre.md)); решение владельца от 2026-09-24, основание — журнал, который потребитель написал сам.

**Уровень требования: директива.**

## Объявление

1. <a id="REQ-CLIENT-JOURNAL-001"></a> **REQ-CLIENT-JOURNAL-001** — Клиент объявляет журнал один раз — `provideClientJournal({ storageKey, limitBytes, skip })` — и подключает `clientJournalInterceptor` к `provideHttpClient(withInterceptors([...]))`. Все настройки необязательны: ключ хранилища по умолчанию `apcr.client-journal`, предел — 128 КБ, исключённых путей нет. Недопустимая настройка — пустой ключ, предел не целым числом или меньше 4 КБ, исключённый путь не от корня — отказывает при запуске и называет настройку.

## Что записывается

2. <a id="REQ-CLIENT-JOURNAL-002"></a> **REQ-CLIENT-JOURNAL-002** — Журнал записывает три вида событий, каждое с моментом записи:
   - **сетевой вызов** — метод, путь, статус, длительность в миллисекундах и код отказа ядра (`REQ-API-011`), если ответ его несёт; вызов, не получивший ответа, записывается со статусом `0`;
   - **переход** — путь страницы после перенаправлений;
   - **необработанная ошибка** — имя и сообщение, не длиннее 1024 знаков.
3. <a id="REQ-CLIENT-JOURNAL-003"></a> **REQ-CLIENT-JOURNAL-003** — Тела запросов и ответов, заголовки, источник адреса, строка запроса и фрагмент в журнал не пишутся: от адреса остаётся путь. В строке запроса и фрагменте бывают одноразовые ключи — ссылки подтверждения и сброса пароля, — а для разбора отказа нужен путь.

## Маскирование

4. <a id="REQ-CLIENT-JOURNAL-004"></a> **REQ-CLIENT-JOURNAL-004** — Путь и сообщение маскируются **до записи**: адреса почты, маркеры от 20 знаков из латиницы, цифр, `_` и `-`, номера телефонов заменяются знаком `***`. Немаскированное не попадает даже в хранилище браузера. Работа маскирования ограничена: текст длиннее 4096 знаков обрезается до маскирования, сообщение — до 1024 знаков после него.
5. <a id="REQ-CLIENT-JOURNAL-005"></a> **REQ-CLIENT-JOURNAL-005** — Правило маскирования и выделения пути записано общими примерами в `packages/client-journal/masking-vectors.json`. По ним проверяется пакет клиента, и по ним же будет проверяться повторное маскирование на сервере центра поддержки (`CORE-ARC-017`): правило, написанное дважды, расходится молча, а общий набор примеров роняет разошедшуюся сторону — тот же приём, что у версии API (`REQ-CLIENT-UPDATE-007`).

## Хранение

6. <a id="REQ-CLIENT-JOURNAL-006"></a> **REQ-CLIENT-JOURNAL-006** — Журнал хранится в `sessionStorage` вкладки: переживает перезагрузку страницы и стирается с закрытием вкладки. Предел считается по размеру записи JSON в UTF-8; при переполнении вытесняются самые старые записи. Недоступное или переполненное хранилище не ломает клиент: запись пропускается молча. Повреждённое содержимое читается как пустой журнал, а записи чужой формы отбрасываются.
7. <a id="REQ-CLIENT-JOURNAL-007"></a> **REQ-CLIENT-JOURNAL-007** — Пути из `skip` не записываются. Путь исключается по целым сегментам: `/api/support` исключает `/api/support` и `/api/support/requests`, но не `/api/supportive`. Вызов, которым проект отправляет журнал, проект обязан исключить — иначе журнал записывает собственную отправку. Запросы в обход перехватчиков, как сверка точки входа механизмом обновления (`REQ-CLIENT-UPDATE-002`), журнал не видит.

## Ошибки

8. <a id="REQ-CLIENT-JOURNAL-008"></a> **REQ-CLIENT-JOURNAL-008** — Объявление заменяет `ErrorHandler` приложения на `JournalErrorHandler`: он записывает ошибку и передаёт её стандартному обработчику, так что вывод в консоль сохраняется. Проект со своим обработчиком наследует `JournalErrorHandler` и объявляет наследника после `provideClientJournal`; объявленный раньше, он заменяется журналом.

## Выдача

9. <a id="REQ-CLIENT-JOURNAL-009"></a> **REQ-CLIENT-JOURNAL-009** — Журнал сам браузер не покидает: `ClientJournal.entries()` отдаёт записи проекту, а отправляет их проект — например, с обращением в поддержку. `clear()` очищает журнал. Отправка журнала — обработка персональных данных по 152-ФЗ: цель, уведомление человека и текст соглашения остаются проекту; ядро отвечает за то, чтобы отправлялось уже маскированное.

## Время

10. <a id="REQ-CLIENT-JOURNAL-010"></a> **REQ-CLIENT-JOURNAL-010** — Момент записи и длительность вызова берутся из порта часов `JOURNAL_CLOCK` (`REQ-TYPESCRIPT-CLOCK-001`); тест подставляет свои часы заменой зависимости. Системная реализация — единственный файл пакета, обращающийся к часам, и запись в `clockAllowlist` ядра.
