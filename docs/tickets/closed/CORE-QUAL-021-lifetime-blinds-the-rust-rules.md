# Аннотация времени жизни ослепляет разбор Rust

## Проблема

Разбор ядра читает одиночную кавычку как начало символьного литерала. В Rust
`&'a str` — аннотация времени жизни, а не литерал, и после неё разбор
пропускает текст до следующей кавычки.

Отказ бесшумный и неотличим от чистоты: ограничитель засеян, проверка зелёная,
а в ослеплённых файлах послабление можно добавлять свободно — множество не
растёт, потому что правило его не видит.

Ровно тот род отказа, про который ядро неделю назад записало `REQ-QUALITY-013`
и `REQ-QUALITY-014`.

## Чем подтверждено

Заявка потребителя [issue #23](https://github.com/apocarteres/platform/issues/23),
ядро 1.30.0, задача потребителя `ZAVPN-QUAL-082`. На крейте агента: объявлено 25
послаблений, правило видит 18, не видит 7. Два файла пропущены целиком.

Потребитель предупредил, что смотрел только Rust и что разбор строк общий с
другими правилами. Проверка ядра показала, что **дефект шире сообщённого**:

| правило | на Rust | насколько слепнет |
|---|---|---|
| `rust-exemptions` | ослеплено | до конца файла |
| `money-types` | ослеплено | до конца файла |
| `comments` | ослеплено | до конца строки |
| `clock` | не затронуто | разбор Rust отдан clippy в 1.23.0 |

Две функции ведут себя по-разному: `codeLines` кавычку до конца файла не
закрывает, `extractComments` обрывает её на переводе строки. Отсюда и разная
дальность слепоты.

## Что сделано

Разбор узнаёт аннотацию времени жизни: одиночная кавычка, за которой не следует
закрывающая через один знак, литерала не открывает. Различение однозначно и
проверено на всех трёх случаях — `'a'` литерал, `'a` время жизни, `'\n'` литерал
с экранированием.

Признак включается по языку: в Java и JavaScript одиночная кавычка остаётся
кавычкой. Исправлены обе функции разбора — `codeLines` и `extractComments`, — а
через них все три ослеплённых правила.

## Чем закреплено

Четыре проверки, покрывающие все три правила, а не одно сообщённое:
послабление после времени жизни видно; символьный литерал остаётся литералом и
объявление внутри строки не считается; нечётное число кавычек выше не прячет
послабления до конца файла; денежная величина и пояснительный комментарий после
времени жизни видны.

Различающая сила проверена возвратом прежнего поведения — упали все три.

## Что стоит записать отдельно

Потребитель заметил дефект только потому, что сверил вывод правила с `grep` по
коду: он делал засев и хотел знать точное число. Без такой сверки ограничитель
выглядел бы исправным, и в ослеплённых файлах послабления добавлялись бы
свободно.

Он же предупредил, что смотрел только Rust и что разбор строк общий с другими
правилами. Предупреждение оправдалось: из четырёх правил, читающих Rust,
ослеплены были три, а сообщено про одно. Правило часов уцелело случайно — его
разбор Rust отдан clippy в 1.23.0.
