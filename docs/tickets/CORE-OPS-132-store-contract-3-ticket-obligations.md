# Ворота выпуска при внешнем хранилище читают поля трекера

## Проблема

При внешнем хранилище ворота выпуска проверяют поля проекта задачи
(`REQ-PROJECT-PROCESS-024`): `manual-qa`, `qa-level`, `pre-deploy`,
`post-deploy`, `maintenance`, `team-action`. Ядро тем самым знает модель
данных трекера. В трекере задача становится статусом, маршрутом (шаблон
конвейера) и записями этапов, а эти поля со временем уходят (TR-173).

## Подтверждение

Заявка Manager (Driada-Lab) 2026-11-19 со ссылкой на решение владельца того
же дня; связанные задачи трекера: TR-171 (этапы завершаются действием),
TR-172 (хранилище по контракту 3), TR-173 (уход полей), DRIAD-740 (shop-core
по обязательствам).

## Последствия при сохранении текущего поведения

Каждое изменение маршрута в трекере требует правки ядра; поля, которые
трекер перестал вести, держат или пропускают выпуск по старым правилам.

## Решение владельца

Решение владельца от 2026-11-19, переданное Manager: модель «обязательства
задачи» принята, изменение — мажорное, с новой версией контракта хранилища.
Номер версии ядра — при выпуске.

## Требуется

1. Контракт хранилища 3: по задаче — список обязательств
   `{key, phase: before-release | after-release, state: pending | done |
   not-required}`; ядро не знает, откуда трекер их берёт.
2. Ворота закрытия выпуска: ни одного `pending` в `before-release` у задач
   состава. `after-release` — как нынешние действия развёртывания и
   завершающий шаг (`REQ-RELEASE-034`, `REQ-RELEASE-049`).
3. Проект изменений до кода, с решением вопросов:
   - имя: в ядре «обязательство» уже значит обязательство ядра перед
     потребителем (`REQ-RELEASE-008`, `obligations.json`) — расширить это
     понятие или назвать обязательство задачи иначе, чтобы термины не
     смешались (`REQ-TERMS`);
   - переходный период: принимает ли пакет правил контракты 2 и 3 сразу, или
     переход одним шагом, как требует `REQ-PUBLISHING-005`;
   - судьба полей проекта при внешнем хранилище и при файлах задач: цикл с
     файлами задач полей не теряет;
   - манифест тега (`REQ-STORE-011`) — что в нём вместо значений полей.
4. Миграция потребителей в документе выпуска; `conventions store --check`
   проверяет форму обязательств.

## Критерии приёмки

- Задача с `pending` в `before-release` держит закрытие; `done` и
  `not-required` — нет.
- Хранилище контракта, которого пакет правил не знает, получает отказ
  `contract-version`.
- `mise run verify` зелёный.

## Порядок

Начинать после ухода контракта 2: shop-core на ядре 19 (DRIAD-739), затем
выпуск трекера TR-166/TR-167.
