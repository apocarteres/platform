# Ядро не исполняет собственного требования о статическом разборе

## Проблема

`REQ-QUALITY-002` требует статического разбора с отказом на предупреждениях.
В ядре его нет ни в каком виде.

| Слой | Что есть | Разбор |
|---|---|---|
| Java, пять модулей | `maven-compiler-plugin` с `<parameters>true</parameters>` | нет: ни `-Werror`, ни `-Xlint`, ни одного плагина |
| TypeScript, `packages/http` | `tsc --strict` | нет: разбора TypeScript в репозитории не объявлено вовсе |
| Node, `packages/project-conventions` | ничего | нет |

`mise run check` содержит проверку документов, проверку правил, `tsc`, тесты
пакетов и тесты Java. Статического разбора в нём нет.

Потребитель сообщил, что у него требование выполнялось для одного компонента из
трёх. У ядра — ни для одного, с того дня, как оно это требование записало.

## Чем подтверждено

Заявка потребителя [issue #15](https://github.com/apocarteres/platform/issues/15)
и разбор состояния ядра 2026-09-15: `pom.xml` родителя, `mise.toml`, поиск по
репозиторию не находит ни одного объявления разбора.

## Что сделано

Разбор внедрён на всех трёх слоях, и каждый проверен намеренным нарушением.

| Слой | Набор | Находок при внедрении |
|---|---|---|
| Java | `-Xlint:all,-processing` с `-Werror`, `ErrorProne` 2.50.0 | 3 |
| TypeScript | `ESLint` 10 с типовым разбором | 0 |
| JavaScript | `ESLint` 10 | 5 |

Засев не понадобился: все восемь находок исправлены, ограничитель не поднимался.

### Что нашлось в Java

1. `SecretMismatchException` наследует сериализуемый класс без объявленного
   `serialVersionUID`. Для ядра, обещающего совместимость, это не мелочь:
   сериализованная форма ломалась бы при любом изменении класса.
2. Тест веб-ошибок пользовался устаревшим кодом состояния. Исправлен заменой
   кода, а не послаблением: предупреждение говорило дело.
3. `ErrorProne` нашёл `String.split` с неочевидным поведением в правиле
   архитектуры. **Автоправку применить было нельзя** — она переписывает на
   стороннюю библиотеку, которой в проекте нет, ровно как предупреждал
   потребитель. Исправлено вручную пределом `-1`; поведение сохранено, потому
   что пустая часть не совпадает ни с одним искомым сегментом.

### Что нашлось в JavaScript

Пять находок, из них одна — настоящий мусор в подписи: `closeRelease` принимал
`today` и не пользовался им. Дата нужна завершающему шагу, который пишет
`released-on`, а первый шаг только ставит тег. Аргумент убран у объявления и у
всех двенадцати вызовов: подпись обещала, что дата влияет на закрытие.

Остальные четыре — неиспользуемый аргумент в `sortKey`, неиспользуемый
аргумент теста и два образца с непосчитанными пробелами.

### Цена

`mise run check` целиком — 42 с, в пределах «минут, а не десятков минут»
(`REQ-QUALITY-002`). Java с разбором — 15 с против 9 с без него.

## Чем закреплено

Четыре проверки читают состояние самого ядра: что `check` содержит разбор, что
Java роняет сборку на предупреждениях и подключает разбор исходников, что разбор
объявлен **у каждого** npm-пакета, а не у одного, и что разбор TypeScript
пользуется типами. Третья написана именно в этой форме, потому что попались обе
стороны одинаково: разбор был у одного компонента, остальные молчали.

Различающая сила проверена двумя пробами: снятием разбора из набора `check` и
снятием разбора у одного пакета из двух — каждая уронила свою проверку. Сами
разборы проверены пробами в коде: возврат `split` без предела уронил сборку
Java, `var` с неиспользуемой переменной — разбор JavaScript, `any` — разбор
TypeScript.

## Откуда пришла задача

Заявка потребителя [issue #15](https://github.com/apocarteres/platform/issues/15);
состояние ядра проверено при разборе заявки.
