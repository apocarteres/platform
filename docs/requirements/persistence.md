# Слой доступа к данным

[Карта требований](../REQUIREMENTS.md) · [Решение](../decisions/ADR-0002-persistence-contracts.md)

## Каталог запросов

1. <a id="REQ-PERSISTENCE-001"></a> **REQ-PERSISTENCE-001** — SQL хранится в ресурсах, а не строками в коде: один файл — один запрос, каталог `classpath:sql/<область>/` соответствует одной доменной области, имя файла без расширения является именем запроса.
2. <a id="REQ-PERSISTENCE-002"></a> **REQ-PERSISTENCE-002** — Отсутствующий каталог, пустой файл запроса и повторяющееся имя запроса являются ошибками конфигурации и отказывают при первом обращении к каталогу.
3. <a id="REQ-PERSISTENCE-003"></a> **REQ-PERSISTENCE-003** — Обращение по неизвестному имени запроса отказывает и называет перечень доступных имён.
4. <a id="REQ-PERSISTENCE-004"></a> **REQ-PERSISTENCE-004** — Имя каталога нормализуется по ведущим и завершающим разделителям; пустое имя, повторный разделитель и обход по дереву каталогов отклоняются.
5. <a id="REQ-PERSISTENCE-005"></a> **REQ-PERSISTENCE-005** — Каталог читается с диска один раз за время жизни приложения; повторное обращение возвращает тот же экземпляр.

## Доступ к данным

6. <a id="REQ-PERSISTENCE-016"></a> **REQ-PERSISTENCE-016** — Объектно-реляционное отображение не применяется: ни ORM, ни надстройки над ней, ни отображение по аннотациям сущностей. Доступ к данным — DAO поверх шаблона JDBC и каталога запросов (`REQ-PERSISTENCE-001`). Это посылка всего документа, а не вкус: каталог запросов имеет смысл ровно потому, что другого пути нет; ORM рядом с ним даёт два пути к одним и тем же данным, и это хуже любого из них по отдельности — правило о хранении SQL перестаёт что-либо гарантировать, а запрос, порождённый отображением, не виден ни в ресурсах, ни в обзоре изменений. Решение владельца от 2026-09-12.
7. <a id="REQ-PERSISTENCE-017"></a> **REQ-PERSISTENCE-017** — Метод DAO выполняет один оператор к базе и отображает его результат. В DAO нет ветвления между операторами, повторного чтения ради ответа и суждения об исходе сверх того, что вернул сам оператор. Несколько обращений к базе — это уже деловая операция: она принадлежит прикладному слою, где видна целиком, а не слою доступа, где распадается на скрытые шаги. DAO, собравший из трёх операторов одно решение, прячет деловое правило там, где его никто не ищет, и повторно использовать его нельзя ни в одной другой операции. Решение владельца от 2026-09-12.
8. <a id="REQ-PERSISTENCE-018"></a> **REQ-PERSISTENCE-018** — Граница транзакции объявляется в прикладном слое и только там: ни в транспортном слое, ни в DAO. Транзакция принадлежит деловой операции, а не способу её вызова: объявленная у контроллера, она исчезает, когда ту же операцию вызывает планировщик, команда сопровождения или другой сервис. Запрет относится и к объявлению признаком, и к программному управлению транзакцией; наборы тестов под него не подпадают — там откат служит изоляции проверки, а не деловой операции. При соблюдении `REQ-PERSISTENCE-017` у DAO транзакция и не нужна: одиночный оператор атомарен сам по себе. Решение владельца от 2026-09-12.
9. <a id="REQ-PERSISTENCE-019"></a> **REQ-PERSISTENCE-019** — Принадлежность класса прикладному слою проект объявляет сам — пакетом, стереотипом или перечнем — и проверка опирается на это объявление, а не на суффикс имени. Имя не удостоверяет роль: класс с суффиксом слоя доступа, вызывающий три DAO и складывающий из них ответ, относится к прикладному слою, а прикладная логика с именем обработчика от правила не освобождается. Проверка по имени превращает имя в пропуск: её обходит переименование, и она же ложно срабатывает на верном коде.
10. <a id="REQ-PERSISTENCE-020"></a> **REQ-PERSISTENCE-020** — К каталогу запросов обращается только слой доступа к данным. Ограничение не следует из модульной модели само: каталог поставляется ядром, для модульной проверки его пакет внешний и потому доступен любому классу проекта — включая контроллер. Границу держит отдельная проверка, иначе подключение ядра снимает её молча.
11. <a id="REQ-PERSISTENCE-021"></a> **REQ-PERSISTENCE-021** — Обобщённый DAO не вводится: ни базового класса с операциями над произвольным типом, ни отображения по описанию полей. Это путь, которым отображение возвращается под своим именем — сначала общий поиск по идентификатору, затем общее сохранение, затем описание полей аннотацией, — и заканчивается он собственной ORM, у которой нет ни сообщества, ни документации, ни чужих исправлений.

## Условная запись

12. <a id="REQ-PERSISTENCE-006"></a> **REQ-PERSISTENCE-006** — Исход условной записи выражается типом с закрытым перечнем вариантов: запись применена, записи нет, версия изменена параллельно, запись отклонена доменным условием оператора.
13. <a id="REQ-PERSISTENCE-007"></a> **REQ-PERSISTENCE-007** — Различие между отсутствием записи и конфликтом версий определяется повторным чтением по идентификатору, а не сообщением драйвера.
14. <a id="REQ-PERSISTENCE-008"></a> **REQ-PERSISTENCE-008** — Операция, для которой неприменённая запись означает нарушение инварианта вызывающего, получает состояние через явный запрос с сообщением об отказе.

## Сериализация команд

15. <a id="REQ-PERSISTENCE-009"></a> **REQ-PERSISTENCE-009** — Команда DAO сериализуется в JSON отдельным портом слоя persistence с датами в ISO-8601; настройки сериализации веб-слоя на неё не влияют.
16. <a id="REQ-PERSISTENCE-010"></a> **REQ-PERSISTENCE-010** — Несериализуемая команда является ошибкой программиста и отказывает с указанием типа команды.

## Точность времени

19. <a id="REQ-PERSISTENCE-013"></a> **REQ-PERSISTENCE-013** — Время хранится с точностью до микросекунд: типы времени распространённых баз наносекунды не хранят. Момент времени приводится к точности хранилища перед записью, поэтому прочитанное значение всегда равно записанному.
20. <a id="REQ-PERSISTENCE-014"></a> **REQ-PERSISTENCE-014** — Код и тесты, сравнивающие моменты времени, используют то же приведение, а не значение системных часов напрямую. Иначе исход сравнения зависит от точности часов операционной системы.
21. <a id="REQ-PERSISTENCE-015"></a> **REQ-PERSISTENCE-015** — Время записи строки задаёт приложение, а не выражение базы вида `now()` или `CURRENT_TIMESTAMP`. Иначе в одной строке оказываются два источника времени — часы приложения в доменных полях и часы базы в служебных, — и порядок событий по служебным полям восстановить нельзя. Момент берётся у порта часов и приводится к точности хранилища: для этого есть `StoredInstant.offsetOf`, принимающий момент или сами часы.

## Регистрация

17. <a id="REQ-PERSISTENCE-011"></a> **REQ-PERSISTENCE-011** — Порты регистрируются автоконфигурацией; бин, объявленный потребителем, имеет приоритет над бином по умолчанию.
18. <a id="REQ-PERSISTENCE-012"></a> **REQ-PERSISTENCE-012** — Порт сериализации команд регистрируется только при наличии Jackson 2 на classpath; его отсутствие не мешает работе каталогов запросов.
