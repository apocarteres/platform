# Хранение секретов

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: хранение секретов любым сервисом.** Требования не зависят от предметной области и от того, чей это секрет.

**Уровень требования: директива.**

## Что хранится зашифрованным

1. <a id="REQ-SECRETS-001"></a> **REQ-SECRETS-001** — Секрет, попадающий в хранилище сервиса, лежит там зашифрованным: ключи доступа, токены, пароли внешних служб, содержимое профилей доступа. Открытое хранение допустимо только для значений, разглашение которых ничего не даёт — и тогда это не секрет. Шифрование выполняется средством платформы, а не реализацией сервиса: параметры шифра — один выбор на все сервисы, а копия параметров расходится с оригиналом молча.
2. <a id="REQ-SECRETS-002"></a> **REQ-SECRETS-002** — Секрет шифрования приходит из окружения (`REQ-CONFIG-001`) и имеет длину не менее 32 знаков: стойкость ключа задаёт он сам. Ключ выводится из секрета хешированием без соли и растяжения — это верно для настроечного секрета высокой энтропии и неверно для пароля, выбранного человеком: пароли этим средством не защищаются.
3. <a id="REQ-SECRETS-003"></a> **REQ-SECRETS-003** — Шифртекст связан с идентификатором записи: значение, перенесённое в другую запись, расшифровке не поддаётся. Неподтверждённая расшифровка отличается от поломки окружения отдельным видом отказа: первое означает чужой секрет, чужую запись или подмену, второе — что шифрование вообще не выполнено.

## Границы

4. <a id="REQ-SECRETS-004"></a> **REQ-SECRETS-004** — Средство платформы шифрует секреты, а не персональные данные. Обработка персональных данных имеет собственный режим — основание обработки, сроки хранения, порядок удаления по запросу (152-ФЗ), — и шифрование поля его не заменяет.
5. <a id="REQ-SECRETS-005"></a> **REQ-SECRETS-005** — Ротация ключа шифрования средством пока не поддержана: смена секрета делает прежние шифртексты нечитаемыми. Сервис, которому ротация нужна, ставит вопрос заявкой в ядро (`REQ-ADOPTION-019`), а не заводит вторую реализацию шифра.
