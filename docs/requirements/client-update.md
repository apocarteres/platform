# Клиент: новая сборка и устаревший API

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: одностраничный клиент на Angular и его служба на Spring Boot.** После раската открытая вкладка работает на прежней сборке; отказ загрузки куска человек видит как ошибку сети, хотя помогает только перезагрузка. Отдельно от этого прежний клиент может перестать понимать новый API. Обе задачи решает ядро целиком — сервер и логику клиента; проекту остаётся вид уведомлений. Решение владельца от 2026-09-24, основание — заявка потребителя, решавшего обе задачи сам: своя служба опроса, своя плашка и сравнение версий, написанное дважды, на Java и на TypeScript.

**Уровень требования: директива.**

## Объявление

1. <a id="REQ-CLIENT-UPDATE-001"></a> **REQ-CLIENT-UPDATE-001** — Клиент объявляет механизм один раз — `provideAppUpdate({ apiVersion, available, required })` из пакета `@apocarteres/app-update` — и обязан решить оба события. `available` — компонент проекта, который сообщает о новой сборке, либо явная заглушка `UPDATE_IGNORED`: заглушка видна в коде по имени и находится поиском, а молчание не принимается за решение. `required` — компонент, который сообщает, что клиент устарел; его показ не отключается, потому что устаревший клиент со своим сервером больше не работает. Объявление без решения отказывает при запуске и называет недостающее. Показывает и убирает компоненты ядро; разметка, текст и оформление принадлежат проекту, перезагрузку компонент получает от службы `AppUpdate`.

## Новая сборка

2. <a id="REQ-CLIENT-UPDATE-002"></a> **REQ-CLIENT-UPDATE-002** — Новая сборка обнаруживается без действий человека: клиент сверяет отпечаток точки входа — набор ссылок на скрипты и стили в `index.html` — с тем, что запомнил при старте. Любая сборка, включая правку одних стилей, меняет эти ссылки: имена файлов несут отпечаток содержимого. Разбор имени `main-*.js` и отдельный маркер сборки не нужны. Сверка идёт раз в 5 минут и сразу при возврате на вкладку; в скрытой вкладке опроса нет. Точка входа запрашивается мимо кэша и без версии API. Недоступная точка входа и страница без ссылок новой сборкой не считаются: ответ обслуживания или ошибка сети не должны предлагать перезагрузку.
3. <a id="REQ-CLIENT-UPDATE-003"></a> **REQ-CLIENT-UPDATE-003** — Клиент не перезагружается сам: перезагрузку вызывает компонент проекта по действию человека. Автоматическая перезагрузка стирает несохранённое, и решать, когда её можно предложить, должен тот, кто знает, что на странице несохранено.
4. <a id="REQ-CLIENT-UPDATE-004"></a> **REQ-CLIENT-UPDATE-004** — Отказ загрузки куска вызывает сверку сразу, не дожидаясь опроса: отказ перехода маршрутизатора — сам, блок `@error` отложенной загрузки — директивой `apcrChunkFailure` на его содержимом. При сменившейся сборке человек видит `available`, а не ошибку сети: помочь ему может только перезагрузка, и сказать ему это честнее, чем предложить повтор.

## Устаревший API

5. <a id="REQ-CLIENT-UPDATE-005"></a> **REQ-CLIENT-UPDATE-005** — Служба подключает starter ядра `platform-api-version` и задаёт настройку `platform.api.min-supported-version` — минимальную версию API, которую сервер принимает от клиента. Настройка обязательна: без неё и с неразборчивым значением служба не стартует и называет настройку. Значения по умолчанию нет, потому что его выбор — решение о том, каких клиентов служба ещё обслуживает.
6. <a id="REQ-CLIENT-UPDATE-006"></a> **REQ-CLIENT-UPDATE-006** — Клиент добавляет версию API к каждому запросу своего источника заголовком `X-Api-Version`; к чужим источникам заголовок не уходит. Перехватчик `appUpdateInterceptor` подключается к `provideHttpClient` рядом с объявлением механизма. Сервер отказывает запросу с неразборчивым заголовком и с версией ниже минимальной — от кого бы он ни пришёл — и запросу **браузера** без заголовка: `426` и ошибка ядра с кодом `client-outdated` (`REQ-API-011`). Признак браузера — заголовок `Sec-Fetch-Site`, а где браузер его не шлёт (адрес не по `https` и не `localhost`, старый браузер) — `Referer`. Запрос без заголовка версии и без признака браузера проходит: машинного клиента — агента, интеграцию, служебный скрипт — проверка не касается, и перечислять его пути не нужно. Умолчание выбрано по направлению ошибки: пропущенный признак оставляет устаревшую вкладку без предупреждения, а запрет по умолчанию клал бы на производственной среде каждый забытый машинный вызов; путь к тому же не различает вызывающих — один путь зовут и браузер с сессией, и скрипт с токеном. Клиент, объявивший механизм, заголовок шлёт всегда. Клиент, получив код, показывает `required`: он важнее `available`, заменяет его и остаётся до перезагрузки. Проверяются обработчики контроллеров; точки `actuator` проверкой не охвачены. Пути, которые нужно освободить и от браузера, перечисляет `platform.api.version-exempt-paths` — шаблоны `PathPattern` Spring MVC, например `/hooks/**`. Уточнено 2026-09-24 по заявке потребителя. Версия API — целое число, которое проект поднимает, когда прежний клиент перестаёт понимать API; обычный выпуск клиента её не трогает, и такой выпуск старые вкладки не блокирует, а получает мягкое `available`.
7. <a id="REQ-CLIENT-UPDATE-007"></a> **REQ-CLIENT-UPDATE-007** — Запись и сравнение версии — одно правило для обеих сторон: целое число от 1 до 999999999, в заголовке — десятичной записью без знака, пробелов и ведущих нулей; клиент принят, когда его версия не ниже минимальной. Общие примеры лежат в `platform-api-version/src/test/resources/api-version-vectors.json`, и по ним проверяются и Java, и TypeScript: правило, написанное дважды, расходится молча, а общий набор примеров роняет ту сторону, которая разошлась.

## Проверка

8. <a id="REQ-CLIENT-UPDATE-008"></a> **REQ-CLIENT-UPDATE-008** — Правило `client-update` находит приложение Angular, в исходниках которого нет `provideAppUpdate` или `appUpdateInterceptor`, и службу, которая зависит от веб-слоя Spring без зависимости `platform-api-version`. Приложение — проект вида `application` в `angular.json`; служба — `pom.xml` с зависимостью `spring-boot-starter-web` или `spring-boot-starter-webmvc` вне области `test`. Перехватчик засчитывается в списке `withInterceptors([...])`, записанном на месте: имя в строке импорта подключением не является, а список, собранный в переменной, правило не прослеживает — ограничение записано здесь. Правило видит объявление, а не его исполнение: объявление без решения отказывает при запуске (`REQ-CLIENT-UPDATE-001`, `REQ-CLIENT-UPDATE-005`).
9. <a id="REQ-CLIENT-UPDATE-009"></a> **REQ-CLIENT-UPDATE-009** — Правило `defer-error` находит блок `@defer` без `@error`. Отложенная загрузка — такая же загрузка куска, как переход по маршруту, и её отказ после раската неизбежен; блок без `@error` показывает на месте содержимого пустоту. Это тот же приём, что с `Escape` у модальных окон: молчание не принимается за решение. Правило читает шаблоны в `.html` и `.ts` и видит блоки, записанные синтаксисом управления потоком; комментарий шаблона со скобками внутри блока может сбить разбор — ограничение записано здесь. Отказ загрузки через `loadComponent` правило не ищет: его обрабатывает механизм обновления (`REQ-CLIENT-UPDATE-004`). Вызов `import()` без обработки отказа правило тоже не ищет: такой поиск дал бы много ложных находок. Основание — заявка потребителя от 2026-09-24.

## Совместимость

10. <a id="REQ-CLIENT-UPDATE-010"></a> **REQ-CLIENT-UPDATE-010** — Отказ устаревшему клиенту — не слой совместимости в смысле `REQ-COMPATIBILITY-003` и `REQ-COMPATIBILITY-005`: сервер не обслуживает прежний контракт, а называет его неподдерживаемым. Минимальная версия ниже текущей не разрешает серверу держать ветки для прежнего API; она лишь говорит, до какой версии изменения API были совместимы сами по себе.
