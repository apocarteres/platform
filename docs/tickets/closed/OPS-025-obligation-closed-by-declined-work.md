# Обязательство ядра закрывается отказом от работы

## Проблема

Обязательства ядра остались на перечне терминальных статусов, тогда как
вопрос, на который они отвечают, — «результат получен», а не «задача ушла из
работы». Это та же подмена понятий, что закрыта в `OPS-023` для состава
выпуска, но в обязательствах она обходится дороже: `REQ-RELEASE-015` прямо
запрещает тихо выбросить обязательство.

Проявляется в двух местах.

`satisfyObligation` (`lib/release/cycle.mjs:183`) принимает доказательством
задачу в любом терминальном статусе. Собственное сообщение той же проверки
говорит «обязательство закрывается только выполненной работой», то есть
проверка и её объяснение расходятся. Отменённая задача — запись отказа от
работы — принимается как доказательство её выполнения.

Открытие выпуска (`lib/release/cycle.mjs:288`) считает отменённую
задачу-заготовку завершённой: обязательство не переносится в следующий выпуск
по `REQ-RELEASE-021` и не материализуется заново по `REQ-RELEASE-013`, потому
что задача с этим полем уже существует. Срок при этом продолжает считаться:
он считается в выпусках от появления обязательства, а не по задачам.

Нормативный текст участвует в дефекте: `REQ-RELEASE-019` требует, чтобы
задача-доказательство была «в терминальном статусе». Починка требует правки
требования, а не только кода.

## Чем подтверждено

Прогоны 2026-09-10 на ядре после `OPS-023`, фикстурный проект с одним
объявленным обязательством уровня директива и сроком 1 выпуск.

**Обязательство закрыто отменённой задачей.** Задача `QUAL-009` в статусе
`cancelled` с разделом «Почему не делаем» («Решили не делать: обходимся
текущим поведением»):

```
$ conventions release satisfy sample-duty --ticket QUAL-009
Обязательство sample-duty закрыто задачей QUAL-009
- задача-заготовка TICKET-SAMPLE-DUTY-2026-09-10 удалена: работа уже выполнена
```

Код возврата 0. Запись в `.conventions/obligations.json`:

```
"closed": { "sample-duty": { "release": "RELEASE-2026-09-1", "ticket": "QUAL-009" } }
```

Обязательство значится исполненным, доказательство — отказ от работы, а
задача-заготовка удалена с объяснением «работа уже выполнена».

**Отменённая заготовка уносит обязательство из плана, но не из срока.**
Материализованная задача обязательства переведена в `cancelled`. После
закрытия выпуска:

| Наблюдение | Значение |
| --- | --- |
| Упоминаний обязательства в составе нового выпуска | 0 |
| Задача обязательства в проекте | отсутствует |
| Запись `closed` в состоянии обязательств | пусто — обязательство открыто |
| `releaseCount` против `seen` | 1 против 0 — срок исчерпан |

Следующее закрытие выпуска отказывает:

```
- Обязательство sample-duty просрочено: срок 1 выпуск(ов), прошло 1
```

Открытой задачи по этому обязательству в проекте нет ни одной: потребитель
получает жёсткую блокировку закрытия и ни одной работы, за которую можно
взяться.

## Последствия при сохранении текущего поведения

1. Обязательство уровня директива закрывается отказом от работы, и запись об
   этом неотличима от законной: в состоянии стоит `closed` со ссылкой на
   задачу. Ровно то, что `REQ-RELEASE-015` называет недопустимым.
2. Отмена задачи-заготовки — обычное действие, если потребитель считает
   обязательство неприменимым — приводит к блокировке, которую нечем снять:
   задачи нет, перенос по `REQ-RELEASE-014` требует записи с причиной, а
   причину привязывать не к чему.
3. Сообщение проверки утверждает правило, которого проверка не применяет:
   читающий код и читающий вывод получают разные обещания.

## Ожидаемый результат

1. Обязательство закрывается только выполненной работой: доказательством
   служит задача в статусе `done`.
2. `REQ-RELEASE-019` говорит то же, что и проверка.
3. Отменённая задача-заготовка не уносит обязательство из плана молча:
   состояние обязательства и наличие задачи по нему согласованы в любой
   момент.
4. Сообщения об отказе называют, что именно не так с задачей-доказательством:
   отсутствует, не завершена или завершена отказом.

## Критерии приёмки

- `release satisfy` с отменённой или замещённой задачей-доказательством
  отказывает и состояния обязательств не меняет.
- `release satisfy` с выполненной задачей закрывает обязательство, как сейчас.
- Отмена задачи-заготовки не приводит к состоянию, в котором обязательство
  открыто, срок идёт, а задачи по нему нет.
- Правила прямо называют, какой статус задачи закрывает обязательство и что
  происходит с отменённой заготовкой.
- Случаи закреплены проверками пакета.

## Открытые вопросы

1. **Что делать с отменённой задачей-заготовкой?** Варианты: материализовать
   заготовку заново при открытии следующего выпуска, считая отмену не
   относящейся к обязательству; запретить отмену задачи обязательства,
   направляя потребителя к переносу с причиной по `REQ-RELEASE-014`; либо
   считать отмену заявкой на перенос и требовать причину на месте. Выбор
   меняет реализацию, поэтому задача до ответа в работу не берётся.

   Ответ владельца 2026-09-10: второй вариант — отмену задачи обязательства
   запретить. Обязательство объявлено ядром, и решение не делать его принимает
   не потребитель в одиночку: для этого есть перенос с причиной
   (`REQ-RELEASE-014`), где причина записана и видна. Первый вариант молча
   воскрешал бы задачу, которую человек сознательно закрыл; третий смешивает
   два действия в одном.

## Ход выполнения

### Шаг 1 (2026-09-10)

Доказательство обязательства теперь проверяется признаком `shipsResult` —
тем же, которым `OPS-023` определил состав выпуска: закрывает обязательство
только задача в статусе `done`. Сообщение об отказе называет фактический
статус: `Задача QUAL-009 не выполнена (cancelled)`. Прежнее сообщение обещало
«только выполненной работой», а проверка принимала любой терминальный статус —
теперь обещание и проверка совпадают.

Отмена задачи обязательства запрещена проверкой документов по ответу
владельца: задача с полем `obligation` в статусе `cancelled` — отказ, который
называет средство (`release defer` с причиной). Запрет живёт в проверке
задачи, а не в контуре выпуска, потому что отмена — правка документа, а не
вызов команды.

Перенос обязательства приведён в соответствие с текстом `REQ-RELEASE-021`
(«не выполненное к закрытию»): задача-заготовка перестаёт переноситься только
когда выполнена, а не когда ушла из работы. Прежний код останавливал перенос
на любом терминальном статусе, из-за чего срок продолжал идти без задачи.

Нормативный текст: `REQ-RELEASE-032` (задача обязательства не отменяется,
отказ выражается переносом) и уточнённый `REQ-RELEASE-019` (доказательством
служит выполненная задача, отменённая — запись отказа от работы).

### Результаты проверок (2026-09-10)

Оба сценария подтверждения прогнаны заново на тех же фикстурах.

| Сценарий | До починки | После починки |
| --- | --- | --- |
| `release satisfy` с отменённой задачей | код 0, обязательство закрыто, заготовка удалена | `Задача QUAL-009 не выполнена (cancelled)`, код 1, состояние обязательств пусто, заготовка на месте |
| Отмена задачи-заготовки | принималось молча, обязательство уходило из плана, срок шёл | отказ проверки документов с указанием `release defer` |

| Прогон | Результат |
| --- | --- |
| `mise run check` | 106 документов, 271 положение, правила соблюдены, Java-сборка успешна |
| Тесты пакета | 133 из 133 (было 130) |

Каждый из трёх новых тестов проверен на различающую силу откатом своей части
кода. Первая редакция теста переноса оказалась вакуумной: заготовка в статусе
`blocked` переносилась и прежним кодом, поэтому тест переписан на `superseded`,
где прежнее и новое поведение расходятся.

Отдельно устранён след отладки: проба, которой я искал причину отказа теста,
изменила строку в существующем тесте переноса и ослабила её проверкой на
`null`; строка возвращена в исходный вид.

### Что не покрыто

Проверка документов печатает отказ по задаче дважды. Воспроизводится и для
существующего правила про раздел «Почему не делаем», то есть к этой починке
не относится и причина не установлена: в фикстуре файл задачи один,
дублирующих копий нет. Отдельной задачей не оформлено.

## Откуда пришла задача

Побочная находка при починке `OPS-023`: разведя понятия «результат вышел» и
«задача ушла из работы» в составе выпуска, та же подмена обнаружилась в
обязательствах, где нормативный текст закрепляет именно ошибочное прочтение.
