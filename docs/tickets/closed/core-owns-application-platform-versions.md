# Закрепление версии компонента платформы у потребителя молча перестало действовать

## Проблема

Ядро импортирует набор версий платформы приложений, а не наследует её
родительский POM. При импортированном наборе свойство версии в POM
потребителя не переопределяет управляемую версию: побеждает значение внутри
набора. Пока сервис наследовался от родителя платформы приложений,
переопределение работало; после перевода на родителя ядра оно стало мёртвым,
не изменившись ни на строку.

## Подтверждение

Задача потребителя `TICKET-BACKEND-TOMCAT-PIN-LOST-2026-09-08`: сервис
объявлял версию Tomcat `11.0.25`, а в исполняемом артефакте оказался
`tomcat-embed-core` **11.0.24** — версия по умолчанию платформы приложений.
Сканер зависимостей потребителя нашёл в ней уязвимости уровня CRITICAL,
исправленные в 11.0.25, и набор `verify` стал красным.

Замер после переноса закрепления в ядро: в артефакте потребителя
`tomcat-embed-core-11.0.25.jar` без единой строки о версиях в его POM.

## Последствия при сохранении текущего поведения

Молчаливо не действует любое закрепление версии компонента платформы у
потребителя, включая закрепления по требованию безопасности. Расхождение
объявленного и фактического не видно ни в POM, ни в проверках — только
сканером и только задним числом.

## Решение владельца от 2026-09-08

Ядро — источник истины по версии платформы приложений и версиям её
компонентов; потребитель ими не управляет. Ядро обязано предоставлять
средства контроля конфликтов зависимостей.

## Ожидаемый результат

Версии компонентов закреплены в ядре явными записями управления
зависимостями. Потребитель не объявляет их вовсе, а попытка объявить или
оставить мёртвое свойство версии роняет проверку правил до сборки артефакта.

## Критерии приёмки

- [x] Версия Tomcat закреплена в ядре явными записями управления зависимостями — свойство импортированного набора у потребителя не действует (`REQ-DEPS-005`)
- [x] Набор версий Spring Modulith перешёл в ядро: это компонент платформы приложений, а его версию объявлял потребитель
- [x] Правило `dependency-versions` роняет проверку на мёртвом свойстве версии и на версии артефакта, которым управляет ядро; перечень групп расширяется полем `managedGroups`
- [x] Средства контроля конфликтов разделены: шлагбаум на каждой сборке (повторная версия зависимости, зависимость на неопубликованную версию) и отчёт по требованию профилем `dependency-conflicts`, который сборку не роняет (`REQ-DEPS-006`, `REQ-DEPS-007`)
- [x] Замер в потребителе: шлагбаум проходит чисто, отчёт называет 5 расхождений в дереве зависимостей
- [x] Тесты: мёртвое свойство, чужая версия, наследование группы у POM ядра; 94 теста пакета проходят. Обратный опыт: без проверки ссылок на свойство падает один тест
- [x] Требование [REQ-DEPS](../../requirements/dependencies.md) объявляет источник истины, порядок повышения версии и роль двух средств контроля
