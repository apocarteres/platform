# Совместимость и переходы

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

## Устаревшие API

1. <a id="REQ-COMPATIBILITY-001"></a> **REQ-COMPATIBILITY-001** — Использовать deprecated API запрещено в любом виде: в рабочем коде, тестах, временных решениях, fallback-ветках, слоях совместимости, примерах и документации новых решений.
2. <a id="REQ-COMPATIBILITY-002"></a> **REQ-COMPATIBILITY-002** — Если актуального API нет или он не подходит, работа останавливается, блокер фиксируется явно, и вместо использования deprecated API проектируется поддерживаемый контракт.

## Обратная совместимость

3. <a id="REQ-COMPATIBILITY-003"></a> **REQ-COMPATIBILITY-003** — Запрещены адаптеры совместимости, fallback-ветки, legacy dual-write и dual-read, скрытые преобразования старой модели в новую и любая неочевидная логика обратной совместимости, где бы она ни находилась.
4. <a id="REQ-COMPATIBILITY-004"></a> **REQ-COMPATIBILITY-004** — Максимально допустимый механизм перехода — явная миграция данных в хранилище.
5. <a id="REQ-COMPATIBILITY-005"></a> **REQ-COMPATIBILITY-005** — Любая совместимость со старым контрактом во время работы является отдельным архитектурным решением и появляется только после явного разрешения владельца.
6. <a id="REQ-COMPATIBILITY-006"></a> **REQ-COMPATIBILITY-006** — Обнаружив старые данные или старый контракт при изменении кода, исполнитель либо снимает зависимость от них, либо предлагает явную миграцию данных. Восстанавливать новые сущности из старых полей автоматически и по своей инициативе запрещено.
