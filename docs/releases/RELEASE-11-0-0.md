## Несовместимые изменения

- Обязательство ядра `backups` (`REQ-BACKUPS-009`): проект со службой, хранящей данные, объявляет копии и проходит `conventions backups --check` на рабочей среде в срок 3 выпусков; по истечении срока закрытие выпуска отказывает.

## Проверка видит больше

- Правило `backups` (`REQ-BACKUPS-001`) называет изъяны объявленного раздела `backups`: бессрочное хранение, хранилище того же хоста, поле, похожее на учётные данные, неверный вид или срок. Пока раздела нет, правило молчит.
- Составляющая с `enable` не булевым значением или без места установки отвергается (`REQ-BACKUPS-005`).

## Миграция

1. Открытие выпуска заведёт задачу обязательства `backups`. Проекту без данных — закрыть её задачей, которая это называет (`REQ-RELEASE-019`).
2. Объявить раздел `backups`: каждый набор данных службы — вид, расписание, конечный срок хранения, внешнее хранилище, путь квитанции. Образец — [RUN-SERVICE-BACKUPS](../runbooks/service-backups.md).
3. Задание копии своей базы (`pg_dump` своей базы, не кластера) и файлов после отправки в хранилище пишет квитанцию `conventions backups --receipt <копия> --file <файл>`.
4. Таймер задания — составляющей с `"enable": true`; скрипт развёртывания включает помеченное по пятому столбцу `conventions components --full`. Скрипт, читающий четыре столбца, получает пятый только у составляющих с `enable`.
5. После развёртывания рабочей среды — `conventions backups --check`; восстановление проверить и записать `conventions backups --restored --note "<чем>"`.
6. В соглашении назвать срок хранения копий: удалённые по запросу субъекта данные уходят из копий с истечением срока (152-ФЗ).
