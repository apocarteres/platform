# Модальное окно явно решает, что делать по Escape

## Проблема

`Escape` в модальных окнах почти никто не обрабатывает. Молчание при этом не
решение, а его отсутствие: окно, которое забыли научить закрываться, неотличимо
от окна, которое решили не закрывать.

`ADR-0004` записал поведение модальных окон 12 сентября и прямо отослал
обязательное в требования отдельной задачей. Задача заведена не была: ни
положений, ни пакета, ни контрактного набора. Замер того же решения —
у одного потребителя стек `Escape` есть, у другого нет.

## Чем подтверждено

Наблюдение владельца от 2026-09-24. У zavpn общий сервис стека `Escape` есть, но
действует только для окон, которые в нём зарегистрированы: незарегистрированное
окно молча игнорирует нажатие.

## Решение владельца

Решение обязательно, пустое решение допустимо, но явно. Вариант с правилом
`check` по признаку окон, который объявляет сам проект. Решение владельца от
2026-09-24.

## Что сделано

Документ `client-modals.md`, положения `REQ-CLIENT-MODAL-001…004`.

**Пакет `@apocarteres/modal`.** Директива `apoModal` с обязательным входом
`[apoModalEscape]`; именованный отказ обрабатывать — `ESCAPE_IGNORED`; сервис
уровня приложения, у которого `Escape` решает только верхнее окно и дальше не
идёт. Разметки и оформления в пакете нет.

Две защиты. Сборка со строгой проверкой шаблонов отказывает окну без решения —
`NG8008: Required input 'apoModalEscape' from directive ApoModal must be
specified`; при запуске директива отказывает сама, на случай сборки без строгой
проверки.

**Правило `modal-escape`.** Проект объявляет признак своих окон —
`"modal": {"selector": ".modal-card"}`, класс, атрибут или элемент, — и правило
требует `apoModal` на каждом элементе с этим признаком в `.html` и во
встроенных шаблонах `.ts`. Имя признака выбирает проект: ядро не диктует имён
классов. Признак, навешенный динамической привязкой, правило не видит — это
записано в положение.

Обязательство `modal-escape`, срок три выпуска. `ADR-0004` получил раздел об
исполнении первого инварианта.

## Что нашлось по ходу

Сигнальный обязательный вход `input.required()` распознаётся только
компилятором сборки: в проверках без него привязка не находилась вовсе, а
декоратор поля в проверках не работает при стандартных декораторах. Вход
объявлен в метаданных директивы — `inputs: [{ name, required: true }]`: это
работает и в сборке, и в проверках, а отказ сборки остаётся тем же.

Обещание «сборка откажет» не оставлено словами: постоянная проверка
компилирует шаблон потребителя строгим компилятором и ждёт отказа `NG8008` на
забытом окне и чистой сборки на решённом.

## Почему это старшая версия

Новое правило уровня директивы по `REQ-PUBLISHING-004` несовместимо: проверка
потребителя может стать красной. Правило молчит, пока проект не объявил признак
окон, поэтому у нынешних потребителей обновление ничего не красит; краснеть
начнёт при исполнении обязательства, и это работа интеграции, а не цена
обновления. Правило, принятое накануне, применено как есть в первый же раз,
когда оно сработало.

## Чем закреплено

Пакет: пять проверок поведения и проверка сборки строгим компилятором.
Правило: три проверки и закладки на обеих формах эталонного потребителя.
Положения документа внесены в перечень проверки «сначала запуск»: каждое
подкреплено проверкой.

Различающая сила проверена четырьмя возвратами: необязательный вход, `Escape`
для всех окон, вход без директивы как директива — каждый роняет свою проверку.
