# Цикл выпуска

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: выпуски любого сервиса и самого ядра.** Требования не зависят от языка и состава компонентов.

**Уровень требования: директива.**

## Одна команда

1. <a id="REQ-RELEASE-001"></a> **REQ-RELEASE-001** — Выпуск закрывается одной командой. Команда выполняет всё по порядку и при любом отказе не меняет ни документы, ни теги: проверки, закрытие текущего выпуска, тег на проверенный коммит, открытие следующего выпуска.
2. <a id="REQ-RELEASE-002"></a> **REQ-RELEASE-002** — Команда отказывает при непустом рабочем дереве. Иначе тег утверждал бы проверенное состояние, а помечал другое.
3. <a id="REQ-RELEASE-003"></a> **REQ-RELEASE-003** — Команда требует расписки о пройденном наборе `verify` для текущего коммита. Расписка содержит идентификатор коммита и момент прохождения; при её отсутствии команда выполняет `verify` сама.
4. <a id="REQ-RELEASE-018"></a> **REQ-RELEASE-018** — Расписка лежит вне версионируемых файлов: она свидетельство машины, а не часть истории. Каталог расписок исключён из контроля версий, иначе сама расписка делала бы рабочее дерево грязным и закрытие выпуска стало бы невозможным.

## Номер и тег

5. <a id="REQ-RELEASE-004"></a> **REQ-RELEASE-004** — Номер выпуска сервиса состоит из года, месяца и порядкового номера в месяце: идентификатор документа `RELEASE-YYYY-MM-N`, тег `YYYY.MM.N`. Номер выпуска ядра равен версии его артефактов по semver, тег `vX.Y.Z`: у ядра выпуск и версия артефактов — одно и то же событие.
6. <a id="REQ-RELEASE-005"></a> **REQ-RELEASE-005** — Тег ставится ровно на тот коммит, для которого получена расписка, и только один раз. Номер не переиспользуется, тег не переписывается.
7. <a id="REQ-RELEASE-006"></a> **REQ-RELEASE-006** — Закрытый выпуск неизменен. Ошибка в выпущенном состоянии исправляется следующим выпуском, а не правкой закрытого документа или тега.

## Состав

8. <a id="REQ-RELEASE-007"></a> **REQ-RELEASE-007** — Состав выпуска — запись сделанного, а не план: задача, перешедшая в терминальный статус после предыдущего выпуска, включается в состав закрываемого автоматически. Назначать задачи в выпуск заранее не требуется.
9. <a id="REQ-RELEASE-008"></a> **REQ-RELEASE-008** — Исключение — обязательства ядра: они планируются заранее и попадают в состав следующего выпуска при его открытии.
10. <a id="REQ-RELEASE-009"></a> **REQ-RELEASE-009** — Выпуск с пустым составом не закрывается: нечего выпускать.
11. <a id="REQ-RELEASE-010"></a> **REQ-RELEASE-010** — Открытый выпуск всегда ровно один. Открытие следующего — часть закрытия предыдущего, поэтому состояния «без открытого выпуска» не существует. Номер следующего выпуска сервиса выводится из даты, номер следующего выпуска ядра задаётся при закрытии явно: из содержания изменений он не выводится.
12. <a id="REQ-RELEASE-011"></a> **REQ-RELEASE-011** — Раздел результата закрытого выпуска заполняется из расписки, а не пересказом по памяти: коммит, момент, набор выполненных проверок.

## Обязательства ядра

13. <a id="REQ-RELEASE-012"></a> **REQ-RELEASE-012** — Ядро объявляет обязательства потребителя машинно-читаемым перечнем, который доставляется пакетом правил. Обязательство содержит идентификатор, ссылку на требование, уровень, версию ядра, в которой появилось, срок в выпусках и заготовку задачи.
14. <a id="REQ-RELEASE-013"></a> **REQ-RELEASE-013** — При открытии выпуска каждое незакрытое обязательство уровня директива материализуется задачей потребителя и строкой состава. Повторное открытие не создаёт вторую задачу для того же обязательства.
15. <a id="REQ-RELEASE-014"></a> **REQ-RELEASE-014** — Срок обязательства считается в выпусках потребителя от того, в котором обязательство появилось. Пока срок не истёк, обязательство переносится записью с причиной; по истечении срока закрытие выпуска блокируется.
16. <a id="REQ-RELEASE-015"></a> **REQ-RELEASE-015** — Состояние обязательств потребителя хранится в его репозитории: какое закрыто какой задачей и в каком выпуске, какое перенесено и почему. Тихо выбросить обязательство нельзя.

17. <a id="REQ-RELEASE-019"></a> **REQ-RELEASE-019** — Обязательство, которое потребитель выполнил до его объявления, закрывается ссылкой на уже выполненную задачу, а не новой задачей-пустышкой. Ссылка проверяется: задача должна существовать в проекте и быть в терминальном статусе.

18. <a id="REQ-RELEASE-021"></a> **REQ-RELEASE-021** — Обязательство, запланированное в выпуск и не выполненное к его закрытию, переносится в следующий выпуск вместе со своей задачей: срок считается в выпусках, а не в документах. Задача-заготовка при этом не создаётся второй раз.

## Документ выпуска

19. <a id="REQ-RELEASE-022"></a> **REQ-RELEASE-022** — Документы выпуска пишет команда цикла, а не человек: открытие создаёт скелет, закрытие заполняет состав, результат и критерии выхода. Ручная правка документа выпуска допустима только в разделах, которые команда не заполняет.
20. <a id="REQ-RELEASE-023"></a> **REQ-RELEASE-023** — Метаданные выпуска: `type: release`; `id` из `RELEASE-` и групп заглавных латинских букв и цифр через дефис, имя файла — `<id>.md`; `status` из `draft`, `in_progress`, `blocked`, `released`, `cancelled`; `opened-on` — дата открытия. Для `released` обязательны `released-on` и `commit`, в остальных состояниях они запрещены.
21. <a id="REQ-RELEASE-024"></a> **REQ-RELEASE-024** — Обязательные разделы документа: цель, состав, критерии выхода, границы выпуска и результат. Состав — таблица «Задача | Причина включения», где текст ссылки точно совпадает с идентификатором задачи, а каждая задача перечислена один раз.
22. <a id="REQ-RELEASE-025"></a> **REQ-RELEASE-025** — Критерий выхода записывается флажком `- [ ]` или `- [x]`; у выпущенного документа каждый критерий отмечен и содержит подтверждение после « — ». Сводка выпусков генерируется и вручную не правится.

23. <a id="REQ-RELEASE-026"></a> **REQ-RELEASE-026** — Ссылки закрытого документа приводятся в соответствие, когда их цель переехала или перестала существовать: это ремонт навигации, а не изменение записи о выпуске. Состав, результат, тег и даты закрытого выпуска при этом неизменны (`REQ-RELEASE-006`).

## Принятие цикла

24. <a id="REQ-RELEASE-020"></a> **REQ-RELEASE-020** — Репозиторий, принявший цикл после начала работы, помечает уже закрытые задачи значением `before-cycle`: их результат выпущен до появления цикла, и первый выпуск не объявляет их своим составом. Принятие выполняется один раз и только при отсутствии выпусков.

## Связь с развёртыванием

25. <a id="REQ-RELEASE-016"></a> **REQ-RELEASE-016** — Развёртывается тег выпуска. Развёртывание проверяет, что коммит помечен тегом выпуска, и отказывает иначе; развёртывание непомеченного коммита выполняется явным ключом и записывается в журнал развёртывания как исключение.
26. <a id="REQ-RELEASE-017"></a> **REQ-RELEASE-017** — Тег выпуска существует только у коммита с распиской о пройденном `verify`, поэтому требование `REQ-DEPLOYMENT-009` выполняется механически: непроверенный коммит невозможно пометить, а значит невозможно и развернуть штатным путём.
