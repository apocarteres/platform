# Статический разбор назван и доставляется, а не выводится каждым заново

## Проблема

`REQ-QUALITY-002` требует, чтобы `check` содержал «статический разбор с отказом
на предупреждениях», и на этом останавливается: ни набора, ни порядка внедрения,
ни того, что делать с существующими находками. Каждый потребитель выводит это
заново и выводит по-разному.

У потребителя требование не выполнялось для двух компонентов из трёх и
обнаружилось это разговором, а не проверкой. У ядра оно не выполняется ни для
одного — см. `CORE-QUAL-011`.

## Чем подтверждено

Заявка потребителя [issue #15](https://github.com/apocarteres/platform/issues/15),
ядро 1.19.0, задача потребителя `ZAVPN-QUAL-075`. Потребитель внедрил разбор
целиком на 688 файлах и 46 829 строках Java и показал, что настройка от его
засева не зависит: с убранным файлом исключений разбор байт-кода выдаёт 610
находок, с убранным файлом подавлений разбор TypeScript выдаёт свои.

## Решение владельца 2026-09-15

Ядро называет набор и доставляет настройку. Потребитель волен не пользоваться
тем или иным языком, но если пользуется — требования к качеству для этого языка
определяет ядро, а не проект.

Это тот же принцип, что для компонентов ядра: пользоваться не обязан, но если
пользуется — инварианты гарантирует ядро.

Отсюда следствие, которое надо записать прямо: язык, которого ядро пока не
поддерживает, — повод для заявки, чтобы ядро его поддержало, а не повод проекту
выводить свой набор. Иначе правило возвращается туда, откуда пришло: каждый
выводит заново и выводит по-разному.

Поддерживаемые языки на 2026-09-15: Java, TypeScript, Rust. Rust добавлен
решением владельца того же дня: язык будет использоваться в проектах шире.

## Что делать

1. Назвать в `REQ-QUALITY-002`, что считается статическим разбором для каждого
   поддерживаемого языка и с какой строгостью, и назвать перечень
   поддерживаемых языков: проект пользуется языком или не пользуется, но набор
   для него определяет ядро.
2. Сослаться из `REQ-QUALITY-002` на право засева (`REQ-QUALITY-007`): без него
   отказ на предупреждениях неисполним, и потребитель это показал счётом.
3. Записать, что автоматическая правка разбора — предложение, а не исправление:
   она проходит разбор изменения наравне с рукописной правкой.
4. Доставить настройку: для Java — `platform-service-parent`, для TypeScript и
   Rust — механизмом доставки пакета правил.
5. Раздать исключение для свода запросов централизованно: разбор видит
   переменную вместо литерала в вызовах вида `jdbc.query(sql.get("имя"), …)` и
   сообщает о внедрении SQL. Этот вид кода потребитель пишет потому, что
   `REQ-DATA-ACCESS` его обязывает, — значит исключение должно приходить оттуда
   же, откуда обязанность.

## Открытые вопросы

1. У Cargo нет наследования настройки из удалённого родителя, как у Maven.
   Настройка Rust доставляется файлом через пакет правил, а соблюдение
   проверяется правилом. Решение принято исполнителем; при возражении
   владельца пересматривается.
2. Ядро своего кода на Rust не имеет, поэтому доставляемую настройку Rust
   проверять не на чем. Предлагается дать эталонному потребителю крейт на Rust.
   Это слабее, чем для Java и TypeScript, где ядро прогоняет разбор на
   собственном коде, и слабость названа здесь прямо.
3. Поддержка Rust статическим разбором не исчерпывается: у ядра есть
   `java-clock.md`, `typescript-clock.md`, `java-naming.md`, `java-modules.md` и
   нет их соответствий для Rust. По решению о плане А это пробел ядра, а не
   свобода проекта. Вопрос владельцу — закрывать его в этом же выпуске или
   отдельной работой; исполнитель предлагает отдельной, чтобы разбор не ждал
   правил именования.
