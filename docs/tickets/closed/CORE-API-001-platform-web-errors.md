# Starter `platform-web-errors`: единый контракт ошибок API

## Цель

Общий `@RestControllerAdvice` с контрактом RFC 9457 `ProblemDetail` и расширением `code`, метриками ошибок и портом локализации сообщений. Оба проекта переходят на него одним релизом каждый.

## Основание

1. Решение о контракте принято 2026-09-06 ([ADR-0001](../../decisions/ADR-0001-shared-core.md), раздел 6).
2. zavpn: `config/ApiExceptionHandler` с `ApiError(code, message)`, `ApiErrorMetrics` с нормализацией URI, `ApiErrorMessageLocalizer`; отдельный advice для Client API с полем `requestId`.
3. clanlog: глобального advice нет, около тринадцати локальных `@ExceptionHandler` однотипно отображают `NoSuchElementException` в 404 и `IllegalArgumentException` в 400; коды ошибок передаются строкой в сообщении исключения и разбираются клиентом в `shared/http-error.ts`.

## Последствия при сохранении текущего поведения

Два несовместимых формата ошибок в одном проекте (zavpn) и дублирование обработчиков в другом (clanlog); контракт кодов держится на совпадении литералов и ничем не проверяется.

## Требуется

1. `ProblemDetail` с полями `type`, `title`, `status`, `detail`, `instance` и расширениями `code`, при необходимости `requestId`.
2. Порт `ErrorCodeResolver`: проект сопоставляет свои исключения кодам и статусам; порт `ErrorMessageLocalizer` с реализацией по умолчанию, не раскрывающей внутренние сообщения.
3. Метрики ошибок с нормализацией URI по лучшему совпадению шаблона, как в zavpn.
4. Angular-пакет `@apocarteres/http`: разбор `ProblemDetail`, интерсептор санитизации, интерсептор истёкшей сессии.
5. Переход каждого проекта одним изменением: серверный контракт и клиентский разбор вместе, без поддержки старого формата.

## Критерии приёмки

- В обоих проектах не остаётся локальных `@ExceptionHandler` для общих исключений и собственных типов тела ошибки.
- Контрактные тесты starter проверяют каждый статус и форму тела; e2e-сценарии clanlog и live-тесты zavpn, читающие ошибки, проходят.
- Список кодов ошибок проекта проверяется тестом на соответствие словарю клиента.

## Ход выполнения

### Шаг 1 (2026-09-11)

Появился модуль `platform-web-errors`: starter с одним советом по ошибкам,
двумя портами и метрикой.

Публичная часть — `ErrorCode` (код и статус), порт `ErrorCodeResolver`
(сопоставление исключений проекта) и порт `ErrorMessages` (текст `detail`).
Внутренняя — совет `ApiErrorAdvice`, реализации по умолчанию
`UnresolvedErrorCodes` и `StatusErrorMessages`, метрика `ErrorMetrics`.

Порт назван `ErrorMessages`, а не `ErrorMessageLocalizer`, как в постановке:
`REQ-JAVA-NAMING-001` запрещает имена на `-er` вне двух перечней, и
`Localizer` в них не входит — он называет действие. Расширять перечень ради
одного имени значило бы ослаблять правило, что запрещает `REQ-ADOPTION-006`.

Неопознанное исключение отдаётся как `500` с кодом `unexpected`, но исключение
платформы приложений сохраняет свой статус, а код выводится из него:
`404` даёт `not-found`, `400` — `bad-request`. Иначе общий совет на
`Throwable` превращал бы отказы клиента в отказы сервера — это было бы хуже
тринадцати локальных обработчиков, которых он заменяет.

Метрика считает ошибки по коду, статусу и шаблону пути из лучшего совпадения
обработчика; адрес без шаблона попадает в ряд `untemplated`, а не конкретным
путём — иначе число рядов растёт с числом запросов.

Нормативный текст: новый документ `REQ-API` с шестью положениями, объявлен
доставляемым потребителю. `REQ-API-006` отдельно оговаривает, что совет
объявлен для сервлетного рантайма намеренно и правила `REQ-QUALITY-012` этим
не обходит.

Потребителям объявлено обязательство `web-errors` (директива, `REQ-API-001`,
с 1.5.0, срок 2 выпуска).

### Результаты проверок (2026-09-11)

| Прогон | Результат |
| --- | --- |
| `mise run check` | 115 документов, 285 положений, правила соблюдены, сборка успешна |
| Тесты модуля | 8: проводка 4, контракт тела 4 |
| Тесты пакета правил | 143 из 143 |

Контрактные тесты проверяют форму тела для разрешённого кода, для
неопознанного исключения, для рамочного исключения со своим статусом и
нормализацию пути в метрике: два запроса `/players/17` и `/players/42` дают
один ряд `/players/{id}` со значением 2.

Тест на неопознанное исключение отдельно утверждает, что сообщение исключения
в ответ не попадает: исключение брошено с текстом про пароль администратора,
и ответ его не содержит.

Проверка проводки (`REQ-QUALITY-012`) закрепляет и обратное: вне
сервлетного веб-приложения совет не регистрируется.

### Что не сделано и почему

Пункт 4 требуемого — Angular-пакет `@apocarteres/http` — вынесен в
`CORE-API-002`. В ядре нет ни одной Angular-библиотеки, поэтому клиентская
половина требует сначала решить, как такая библиотека собирается,
публикуется и проверяется; у задачи два открытых вопроса.

Пункт 5 — переход каждого проекта одним изменением — работа в репозиториях
потребителей, которую ядро по `REQ-ADOPTION-004` не выполняет. Средством
служит объявленное обязательство `web-errors`.

Расширение `requestId`, названное в первом пункте требуемого словами «при
необходимости», не сделано: для него нужен хук добавления свойств в
`ProblemDetail`, а имя и форма такого хука — отдельное решение. Проект, которому
`requestId` нужен сейчас, добавляет его своим советом поверх контракта.

Критерии приёмки про оба проекта потребителей и их e2e-сценарии этой задачей не
закрываются: они исполняются обязательством в их репозиториях.
