# Миграция имён не проставляет префикс проекта

## Проблема

`REQ-NAMING-012` вводит префикс проекта в идентификаторе задачи и прямо
называет средство перехода: «переход выполняется миграцией имён». Обязательство
`ticket-prefix` повторяет это заготовкой задачи. Но `conventions naming migrate`
префикс не проставляет: `lib/naming-migration.mjs` строит новый идентификатор
как `${area}-${NNN}`, а идентификаторы прежней формы считает корректными и
оставляет на месте.

## Чем подтверждено

Случай в проекте `zavpn` 2026-09-11. После объявления `ticketPrefix` проверка
правил потребовала новую форму у 149 задач, а `conventions naming plan` показал
`Переименований: 0`. Потребитель выполнил миграцию разовым сценарием: переименование
файлов, правка `id`, сохранение прежнего идентификатора в `legacy-id` и правка
ссылок в 193 файлах.

## Последствия при сохранении текущего поведения

Обязательство называет средство, которого нет. Каждый потребитель пишет свой
сценарий миграции и сам отвечает за полноту правки ссылок: пропущенная ссылка
обнаружится только проверкой документов, а в коде и в состоянии обязательств —
вообще не обнаружится.

## Ожидаемый результат

`conventions naming migrate` приводит идентификаторы к объявленному префиксу:
переименовывает файлы, правит `id`, сохраняет прежний идентификатор в
`legacy-id` и обновляет ссылки во всех текстовых файлах, включая состояние
обязательств.

## Критерии приёмки

- На репозитории с объявленным `ticketPrefix` и задачами прежней формы
  `naming plan` показывает переименования, а `naming migrate` их выполняет.
- После миграции проверка правил и проверка документов проходят без правок
  руками.
- Прежний идентификатор сохранён и ссылки на него ведут к той же задаче.

## Ход выполнения

### Шаг 1 (2026-09-11)

`plan` принимает префикс проекта из настройки: правильной формой считается
`<ПРЕФИКС>-<ОБЛАСТЬ>-<NNN>`, новые идентификаторы строятся с префиксом, а счёт
номеров области ведётся по обеим формам сразу. `migrate` передаёт префикс
дальше; переименование файлов, правка `id`, сохранение `legacy-id` и обновление
ссылок уже работали и не менялись.

По пути нашлась ловушка, которой не было в постановке: ссылки правились
подстрочной заменой. Строка, уже содержащая `ZAVPN-OPS-013` от прошлого
прогона, при переименовании `OPS-013` получала бы `ZAVPN-ZAVPN-OPS-013` —
молчаливая порча ссылок в середине миграции. Замена теперь идёт по границе
идентификатора и не срабатывает там, где префикс уже стоит.

### Результаты проверок (2026-09-11)

| Прогон | Результат |
| --- | --- |
| `mise run check` | 126 документов, 294 положения, правила соблюдены, Java-сборка успешна |
| Тесты пакета правил | 151 из 151 (было 149) |

Сквозная проверка на фикстуре потребителя с объявленным `ticketPrefix: ZAVPN`:
`naming plan` показал два переименования (задача с префиксом осталась на
месте), `naming migrate` их выполнил и поправил ссылки в трёх файлах, включая
ссылку из уже переименованной задачи. Двойных префиксов нет.

Оба новых теста проверены на различающую силу: без префикса в новом
идентификаторе падает первый, при возврате подстрочной замены — он же на
проверке двойного префикса.

### Что не покрыто

Состояние обязательств (`.conventions/obligations.json`) правится наравне с
прочими текстовыми файлами — отдельной обработки у него нет. Для ссылки вида
`"ticket": "OPS-012"` этого достаточно; если формат записи изменится, миграцию
придётся сверить заново.

## Откуда пришла задача

Задача `ZAVPN-OPS-031` проекта `zavpn`: исполнение обязательства `ticket-prefix`
потребовало собственного сценария миграции.
