# ADR-0001: выделение общего ядра

Дата анализа: 2026-09-06. Часть решений принята владельцем и записана в разделе «Решения». После снятия оставшихся вопросов решение получает статус `accepted`.

## Контекст

Несколько сервисов на общем стеке — Java со Spring Boot и клиент на Angular — вели одинаковую инфраструктуру и одинаковый порядок работы каждый у себя. Инвентаризация 2026-09-06 показала три вида дублирования:

- **Код инфраструктуры.** Слой доступа к данным, доставка почты, ограничение частоты запросов, конфигурация безопасности, проверка секретов, база интеграционных тестов и правила архитектурных проверок существовали копиями. Копии успели разойтись в мелочах, а исправление в одной не доходило до другой.
- **Правила и требования.** Порядок ведения задач и выпусков, правила кода и требования к интерфейсу были записаны в каждом проекте отдельно. Один и тот же раздел требований, перенесённый копированием, за несколько месяцев разошёлся так, что общих строк почти не осталось.
- **Проектируемая функциональность.** Подсистема уведомлений проектировалась параллельно в нескольких проектах: каждому нужны были шаблоны, локализация, история отправок и канал доставки.

Перечень конкретных копий и их расхождений сохранён в истории изменений этого документа и в задачах проектов-потребителей. В самом ядре он не хранится: ядро не привязано к заранее известному перечню потребителей.

## Что ядром быть не может

Ограничения, которые ядро обязано уважать, иначе потребитель его не примет:

1. **Триггеры фоновой работы.** Требования потребителей могут запрещать планировщики и автономные триггеры. Ядро экспортирует команды, а не триггеры; источник вызова выбирает потребитель.
2. **Обратная совместимость.** Слои совместимости и переходные ветки запрещены. Несовместимое изменение выходит мажорной версией с описанной миграцией.
3. **Операции чтения.** Методы чтения не имеют побочных эффектов; это распространяется и на API ядра.
4. **Границы модулей.** Внешние библиотеки не входят в граф модулей потребителя, поэтому правило «инфраструктура не знает о домене» переезжает из проверок потребителя в структуру самого ядра.
5. **Неймспейс.** Пространство имён любого потребителя для ядра не годится: нужен нейтральный groupId и npm scope.

## Форма

Рассмотрены три варианта:

| Вариант | Итог |
|---|---|
| Монорепозиторий потребителей с общими модулями | Отклонён: слияние репозиториев с разной историей, сборкой и развёртыванием, общий релизный цикл несвязанных продуктов |
| Общий каталог через git subtree или submodule | Отклонён: нет версионирования, конфликтные обновления, для правил и инструментов не решает сверку |
| **Отдельный репозиторий, версионируемые пакеты** | **Выбран**: явные версии, независимый темп обновления потребителей, правило и его проверка приезжают одной версией |

## Состав

- **Java:** BOM и набор Spring Boot starters с автоконфигурацией и портами для расширения проектом.
- **Angular:** пакеты в одном npm scope: контракт модальных окон, перехватчики HTTP, форматирование, постраничность, локализация.
- **Процесс:** пакет правил с проверками, генераторами сводок и нормативными документами, которые он доставляет потребителю.
- **Уведомления:** отдельный сервис, а не библиотека: конструктор и хранилище шаблонов, каналы доставки, рассылки, история. Потребители становятся его клиентами. Границы и цена определяются [исследованием](../tickets/CORE-ARC-001-notification-service-research.md).

## Решения

1. **Формат метаданных документов.** YAML front matter либо строки шапки в свободном виде.
   Решение владельца, 2026-09-06: **YAML front matter.** Типизирован, проверяется тестами, поддерживает `depends-on`, `related`, `superseded-by`. Отменённая задача обязана содержать раздел «Почему не делаем», что проверяется.
2. **Контракт ошибок API.** RFC 9457 `ProblemDetail` с расширением `code` либо собственная пара «код и сообщение».
   Решение владельца, 2026-09-06: **`ProblemDetail`.** Реализация — [CORE-API-001](../tickets/closed/CORE-API-001-platform-web-errors.md).
3. **Где рендерятся уведомления.** Сервер, сборка из клиентского кода либо отдельный сервис.
   Решение владельца, 2026-09-06: **отдельный сервис**, потребители становятся его клиентами. Заведено [исследование](../tickets/CORE-ARC-001-notification-service-research.md).
4. **Имена и registry.** Решение владельца, 2026-09-06: groupId `io.github.apocarteres.platform`, npm scope `@apocarteres`, публикация в GitHub Packages. Настройка — [CORE-OPS-007](../tickets/closed/CORE-OPS-007-github-packages-publishing.md). Часть про registry заменена решением [ADR-0003](ADR-0003-local-artifact-publishing.md): публикация выполняется локально, координаты артефактов не изменились.
5. **Правила не копируются потребителю.** Решение владельца, 2026-09-06: нормативный текст существует в одном месте, потребитель получает ссылку и читает доставленный пакетом документ. Закреплено требованием [REQ-RULE-DISTRIBUTION](../requirements/rule-distribution.md).
6. **Наследование правил.** Решение владельца, 2026-09-06: правила проекта действуют поверх правил платформы, соблюдаются оба набора, ослабить правило платформы проект не может. Закреплено требованием [REQ-PROJECT-RULES](../requirements/project-rules.md).

## Открытые вопросы

**Вопросы:** открыты

1. **Версии Node у потребителей.** Потребители могут находиться на разных мажорных версиях Node. Пакеты платформы собираются под все используемые версии или потребители выравниваются?
   Ответ 2026-09-07: потребители выравниваются. Требование `REQ-BUILD-004` закрепляет версии инструментов и требует одинаковых версий на всех машинах; ядро закрепило те же версии, что первый потребитель: Java 21, Node 22.22.3. Пакет правил объявляет минимально поддерживаемую версию Node в `engines`, и потребитель с более старой версией получает отказ установки, а не молчаливую несовместимость.

## Порядок внедрения

Порядок по соотношению выигрыша и риска. Каждый этап заканчивается удалением копий у потребителей, без переходного периода.

1. Пакет правил: единые проверки, нормативные документы, доставка потребителю.
2. Чистый перенос кода: слой доступа к данным, деньги, сериализация, база тестов.
3. Инфраструктура web: контракт ошибок, сессии и безопасность, ограничение частоты, аудит, токены действий.
4. Сервис уведомлений: исследование, решение, сервис и клиентская библиотека.
5. Пакеты Angular после стабилизации серверной части.

## Персональные данные

Уведомления и рассылки означают обработку адресов и сетевых адресов пользователей. Это персональные данные в смысле 152-ФЗ, и сервис уведомлений становится оператором их хранения. До реализации рассылок в требованиях должны появиться основание обработки, согласие на рассылку и его отзыв, сроки хранения истории и порядок удаления по запросу.
