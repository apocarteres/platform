# У Rust нет языковых документов, которые есть у Java и TypeScript

## Проблема

Rust объявлен поддерживаемым языком ядра решением владельца 2026-09-15, и
статический разбор для него ядро теперь называет и доставляет
(`CORE-QUAL-010`). Прочих языковых документов у него нет.

| Предмет | Java | TypeScript | Rust |
|---|---|---|---|
| Работа со временем | `java-clock.md` | `typescript-clock.md` | — |
| Именование | `java-naming.md` | — | — |
| Модульность | `java-modules.md` | — | — |

По решению о плане А это пробел ядра, а не свобода проекта: если проект
пользуется языком, требования к нему определяет ядро. Сейчас проект на Rust
получает от ядра разбор и не получает ничего остального — и выведет остальное
сам, то есть ровно то, против чего план А и принят.

## Чем подтверждено

Заявка потребителя [issue #15](https://github.com/apocarteres/platform/issues/15)
и решение владельца 2026-09-15 о поддержке Rust. Пробел найден при исполнении
`CORE-QUAL-010` и вынесен отдельной задачей по `REQ-TICKETS-012`: закрывать
`CORE-QUAL-010` с неразрешённым вопросом нельзя.

## Открытые вопросы

1. Какие из трёх документов Rust вообще нужны. Работа со временем — почти
   наверняка да: запрет на чтение часов мимо порта не зависит от языка.
   Модульность в Rust выражается иначе, чем в Java: у крейта есть своя видимость
   и своё дерево модулей, и требование `REQ-JAVA-MODULES` может оказаться либо
   излишним, либо требующим другой формулировки. Ответ: —
2. Нужен ли ядру собственный код на Rust. Сейчас его нет, и доставляемая
   настройка проверяется на крейте эталонного потребителя. Для разбора этого
   хватает; для правил именования и модульности — вряд ли. Ответ: —
3. Проверяются ли правила Rust правилом ядра, как `platform-arch-rules`
   проверяет Java, и чем: своим разбором исходников или настройкой clippy.
   Ответ: —

## Откуда пришла задача

Исполнение `CORE-QUAL-010`; пробел назван там же открытым вопросом 3.
