# Ключ доступа — второй способ аутентификации ядра

## Проблема

Аутентификация ядра знала один способ — сессию в cookie с защитой от
подделки запроса. Программному клиенту (серверу инструментов, скрипту,
агенту) удостовериться было нечем, а второй способ мимо ядра — ровно то,
против чего аутентификация вынесена в ядро (`CORE-ARC-013`).

## Подтверждение

Заявка потребителя [issue #60](https://github.com/apocarteres/platform/issues/60)
(clanlog, ядро 12.1.0). Сверено 2026-09-27 по цепочке безопасности
`platform-auth`: входа по заголовку нет.

## Последствия при сохранении текущего поведения

Потребитель пишет свой вход по ключу, и у ядра появляется второй, не
проверенный ядром путь к учётной записи.

## Решение владельца

Решение владельца от 2026-09-27: по ключу открыто только разрешённое проектом
(разрешающий перечень, а не запрещающий); ключи включаются настройкой —
совместимо, младшая версия.

## Требуется

`REQ-AUTH-028`–`REQ-AUTH-034`: включение, выпуск и отзыв, запрос по ключу,
разрешённые точки, признак в контексте, пределы на ключ, последнее
использование и очистка.

## Критерии приёмки

- Тесты первыми: `AccessKeyFlowTest` (7 сценариев), `KeySettingsTest`,
  контракт с точками ключей, клиент `AuthSession`. Красный прогон до
  реализации: контекст не поднимался без `AccessKeys`, пути контракта не
  совпадали, настройки не читались. Тест «без настройки Bearer ничего не
  удостоверяет» проходил сразу — он закрепляет прежнее поведение.

## Что сделано

- Требования `REQ-AUTH-028`–`034`; инструкция
  [подключения ключей доступа](../../runbooks/access-keys.md).
- `platform-auth`: `AccessKeys`, `KeyAccess`, `AccessKey`, `IssuedKey`,
  `UsedKey`, `CurrentAccount.key()`; коды `key-rejected`, `key-closed`,
  `key-request-rejected`; таблица `platform_access_key` (образец
  `create-access-key.sql`); фильтр перед CSRF, без сессии; точки
  `/api/auth/keys`; очистка истёкших в `purgeTokens`.
- Контракт `platform-auth` и клиент `@apocarteres/auth`: `keys()`,
  `issueKey()`, `revokeKey()`, `revokeKeys()`; генератор типов понимает поле,
  которое бывает `null`.
- Пробы: 16 на Java — j15 «неподтверждённая запись принимается» прошла,
  добавлен случай ключа неподтверждённой записи, после этого поймана; три
  пробы переписаны, потому что Error Prone не собирал их. 4 на клиенте —
  пойманы. Обходные пути к `/api/auth/**` (`//`, `./`, `../`) закреплены
  тестом: их отвергает цепочка безопасности.
