# Документация platform

Точка входа в требования, архитектурные решения, эксплуатационные инструкции, задачи и выпуски общего ядра.

## Источники истины

1. Действующие документы из [требований](REQUIREMENTS.md) задают обязательное поведение ядра и его контракты.
2. Манифесты пакетов (`pom.xml`, `package.json`) задают фактические версии; версии не дублируются в инструкциях для агентов.
3. [Архитектурные решения](decisions/INDEX.md) объясняют причины выбора и альтернативы, но не заменяют требования.
4. [Эксплуатационные инструкции](runbooks/INDEX.md) описывают публикацию пакетов и обновление потребителей.
5. [Задачи](tickets/INDEX.md) описывают планы и состояние реализации и не являются источником требований.

## Метаданные документов

Все Markdown-документы каталога начинаются с YAML front matter с обязательными полями `id`, `type`, `status`, `scope`, `authority`. Необязательные поля `depends-on`, `supersedes`, `superseded-by`, `related` содержат идентификаторы документов через запятую. Поле `clause-id-prefix` включает стабильные идентификаторы положений нормативного документа. Поля задач `priority`, `release`, `questions` описаны в [документе задачи](requirements/tickets.md), поля выпусков `opened-on`, `released-on`, `commit` — в [цикле выпуска](requirements/release-cycle.md). Дата изменения не хранится: её источник — Git.

| Тип | Состояния |
|---|---|
| `index` | `active` |
| `requirement` | `draft`, `active`, `superseded` |
| `decision` | `proposed`, `accepted`, `rejected`, `superseded` |
| `runbook` | `active`, `retired` |
| `ticket` | `backlog`, `in_progress`, `blocked`, `done`, `cancelled`, `superseded` |
| `release` | `draft`, `in_progress`, `blocked`, `released`, `cancelled` |
| `reference` | `active`, `retired`, `superseded` |

Роли `authority`: `normative`, `supporting`, `historical`, `navigation`.

## Правила изменения

1. Один документ имеет одну ответственность; один нормативный пункт описывает одно проверяемое правило.
2. Инварианты хранятся в требованиях, причины выбора в решениях, порядок реализации в задачах.
3. Нерешённый вопрос не оформляется как действующее требование: он живёт в решении со статусом `proposed` или в задаче.
4. Заменённый документ получает статус `superseded` и ссылку на актуальный; его текст не используется как альтернативный контракт.
5. Технические факты по возможности выражаются машинным контрактом, тестом или манифестом, а не копируются между Markdown-файлами.
6. Новые нормативные документы используют стабильные идентификаторы положений вида `<id>-NNN`.

## Проверка

`mise run docs-check` запускает тесты инструментов, затем проверяет метаданные, уникальность идентификаторов, локальные ссылки, якоря и точное соответствие сводок исходным документам. Этот же инструментарий планируется опубликовать как пакет процессных правил для проектов-потребителей.
