# Клиент узнаёт о новой сборке и об устаревшем API: готовая реализация ядра

## Проблема

После раската открытая вкладка работает на прежней сборке. Отказ загрузки
куска человек видит как ошибку сети, хотя помогает только перезагрузка;
перезагружать самому нельзя — пропадёт несохранённое. Отдельно от этого
старый клиент может перестать понимать новый API, и сервер должен уметь его
остановить. Каждый проект решает обе задачи сам: в заявке — своя служба
опроса, своя плашка и сравнение версий, написанное дважды, на Java и на
TypeScript.

## Решение владельца

Решение владельца от 2026-09-24:

- Ядро поставляет реализацию целиком — сервер и логику клиента. Потребитель
  определяет только вид уведомлений.
- Механизм обязателен: клиент обязан обработать оба события. Отказ от показа
  выражается явной заглушкой, видной в коде по имени.
- Два независимых сигнала:
  - **новая сборка клиента** — любая, включая исправление одной строки или
    одних стилей; номеров и настроек не требует, показ мягкий;
  - **устаревший API** — сравнивается версия API (целое число, которое проект
    поднимает, когда ломает API), а не номер выпуска; показ блокирующий и
    важнее первого.

## Требуется

**Клиент** — пакет `@apocarteres/app-update`, один вызов:

```ts
provideAppUpdate({
  apiVersion: 3,
  available: UpdateBanner,   // или UPDATE_IGNORED
  required: UpdateBlocker,
})
```

1. Компоненты потребителя — только вёрстка; `reload()` получают от ядра,
   показывает и убирает их ядро. Сам клиент не перезагружается никогда.
2. Новая сборка обнаруживается сверкой отпечатка `index.html`, запомненного
   при старте, с текущим, запрошенным без кэша: раз в 5 минут и при возврате
   на вкладку; в скрытой вкладке опроса нет.
3. Отказ загрузки куска (переход по маршруту, `@defer`) вызывает сверку сразу;
   при сменившейся сборке показывается `available`, а не ошибка сети.
4. К каждому запросу добавляется заголовок с версией API; отказ сервера с
   кодом `client-outdated` показывает `required`.

**Сервер** — starter ядра:

5. Настройка `platform.api.min-supported-version` обязательна: без неё служба
   не стартует и называет настройку.
6. Запрос с версией ниже минимальной либо без заголовка отказывает
   стандартной ошибкой ядра с кодом `client-outdated`. Точка состояния и
   объявленные в настройке пути освобождены.
7. Правило сравнения версий одно, с общими тестовыми примерами для Java и
   TypeScript.

**Обязательность:**

8. Правило-директива `client-update`: `check` отказывает клиенту без
   `provideAppUpdate` и службе без starter-а. Обязательство ядра со сроком
   в выпусках потребителя. Выпуск — старшая версия.
9. Положения: требование `REQ-CLIENT-UPDATE`; отказ старому клиенту — не слой
   совместимости в смысле `REQ-COMPATIBILITY-003/005`.
