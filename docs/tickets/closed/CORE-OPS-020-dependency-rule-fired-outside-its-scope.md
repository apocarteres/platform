# Правило версий срабатывало там, где ядро версиями не управляет

## Проблема

Правило `dependency-versions` проверяло любой POM потребителя, не различая,
наследует ли он родителя ядра. Пока проект наследует чужого родителя, версиями
платформы приложений управляет он сам: свойство версии там действует, а
управление версиями ядром не действует вовсе.

## Подтверждение

Замер в третьем репозитории 2026-09-09, наследующем родителя платформы
приложений напрямую: три находки, из которых две ложные.

1. `свойство java.version ни на что не влияет` — влияет: его читает
   унаследованный родитель, а не импортированный набор.
2. `версией platform-bom управляет ядро` — версию ядра потребитель обязан
   закреплять сам (`REQ-BUILD-007`); иначе непонятно, какое ядро подключено.
3. `версией spring-modulith-bom управляет ядро` — верно по сути, но
   неисполнимо: не наследуя родителя ядра, проект не получит эту версию
   ниоткуда, и удаление записи сломало бы сборку.

## Последствия при сохранении текущего поведения

Правило учит обходить себя: две находки из трёх нельзя исправить, поэтому
единственный доступный ответ — заморозить их храповиком. Настоящий же разрыв —
что проект не на родителе ядра — правило не называет вовсе.

## Ожидаемый результат

Проверка применяется к тому, кто наследует родителя ядра. Проект вне его
получает одну находку, называющую именно это; следствия перечислять
бессмысленно, пока не устранена причина. Версия самого ядра из перечня
управляемых исключена.

## Критерии приёмки

- [x] `REQ-DEPS-009` объявляет область действия раздела, `REQ-DEPS-002` исключает версию ядра из перечня
- [x] Проект вне родителя ядра получает одну находку вместо трёх — тест на POM с чужим родителем
- [x] Версия `platform-bom` у потребителя на родителе ядра нарушением не считается — отдельный тест
- [x] Замер по трём репозиториям: ядро и потребитель на родителе ядра чисты, третий репозиторий получает одну находку о причине
- [x] 112 тестов пакета проходят
