# Хранилище задач и выпусков

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: любой проект.** Правило не зависит от стека.

Происхождение и расчёты — идея `CORE-IDEA-003` репозитория ядра.

## Две реализации

1. <a id="REQ-STORE-001"></a> **REQ-STORE-001** — Задачи и выпуски проекта лежат в хранилище, у которого две реализации: файлы репозитория (`docs/tickets`, `docs/releases`) и внешнее хранилище по контракту ядра. Реализацию выбирает поле `store` в `.conventions.json`; без него действуют файлы, и поведение пакета правил прежнее. У проекта одна реализация: задача не ведётся в двух местах сразу.
2. <a id="REQ-STORE-002"></a> **REQ-STORE-002** — Внешнее хранилище объявляется полями `kind: external`, `url`, `readKeyEnv`, `writeKeyEnv`, `idPattern`. Неизвестный ключ, отсутствие адреса, шаблона номера или имени переменной с ключом — отказ команды, а не молчаливый переход на файлы.
3. <a id="REQ-STORE-003"></a> **REQ-STORE-003** — Ключ хранилища берётся только из переменной окружения, имя которой названо в `.conventions.json`. Ключа нет ни в конфигурации, ни в адресе, ни в аргументах процессов, ни в выводе команд (`REQ-PROJECT-PROCESS-016`). Ключ на чтение — для `pre-push` и CI; ключ записи — тому, кто исполняет операции выпуска.
4. <a id="REQ-STORE-004"></a> **REQ-STORE-004** — Каждый ответ хранилища несёт версию контракта `contract`. Версию, которой пакет правил не знает, команда отвергает с названием требуемой версии. Пакет правил знает одну версию (`REQ-PUBLISHING-005`) и называет её в каждом запросе заголовком `X-Store-Contract`: хранилище, которое ведёт потребителей на разных версиях ядра, отвечает в названной версии, и переходный период между контрактами — его забота, а не ядра. Текущая версия — 3 (`REQ-STORE-025`).

## Чтения

5. <a id="REQ-STORE-005"></a> **REQ-STORE-005** — Чтений три, и ни одно не зависит от длины истории проекта: рабочий набор `GET {url}/tickets/working` — задачи в нетерминальном статусе и выполненные, чей выпуск ещё не вышел или не назначен, с прямыми целями `depends-on` вне набора; поиск `POST {url}/tickets/lookup` — не больше 500 номеров за запрос, по номеру и по псевдониму; открытый выпуск `GET {url}/releases/open` вместе с учётом обязательств. Ни одна команда не запрашивает все задачи или все выпуски проекта. Рабочий набор отвечает `ETag` и `304` на повтор.
6. <a id="REQ-STORE-006"></a> **REQ-STORE-006** — Задача приходит в одной форме: `id`, `aliases`, `title`, `url`, `status`, `priority`, `scope`, `release`, `questions`, `dependsOn`, `related`, `obligation`, `supersededBy`, `conditions`, `sections`. Словарь статусов и приоритетов — ядра (`REQ-TICKETS-006`, `REQ-TICKETS-007`); перевод из своих состояний — забота хранилища. `sections` несёт признаки наличия разделов «Почему не делаем» и «Открытые вопросы» и тексты разделов развёртывания (`REQ-TICKETS-023`), а не тело задачи.

## Операции и разделение исполнения

7. <a id="REQ-STORE-007"></a> **REQ-STORE-007** — Операция над выпуском — один запрос `POST {url}/operations` с именем операции и её аргументами на одном уровне и одна транзакция хранилища. Заголовок `Idempotency-Key`: повтор с тем же ключом возвращает первый ответ. Отказ — `application/problem+json` с полем `code` и текстом причины в поле `reason`; без него команда печатает `detail`.
8. <a id="REQ-STORE-008"></a> **REQ-STORE-008** — Операции над данными выпуска исполняет хранилище: открытие, снятие задачи, отмена, учёт коммита, отметка действия развёртывания, перенос и закрытие обязательства. С доски хранилища, через его API и командой пакета правил они действуют одинаково: команда при внешнем хранилище вызывает операцию и своих проверок поверх не добавляет, а отказ хранилища печатает его кодом и его текстом. Шлагбаум закрытия (`REQ-RELEASE-001`) и тег исполняет ядро: первый шаг закрытия, перезакрытие и завершающий шаг выполняются только командой пакета правил.
9. <a id="REQ-STORE-009"></a> **REQ-STORE-009** — Инварианты данных хранилище держит при любой правке и отказывает с кодом: `release-already-open`, `release-id-taken`, `release-not-open`, `release-closing`, `release-closed`, `ticket-missing`, `ticket-in-release`, `ticket-is-obligation`, `reason-required`, `evidence-not-done`, `obligation-overdue`, `whynot-required`, `questions-open`, `dependency-cycle`, `release-is-derived`. Поле `release` задачи меняют только операции над выпуском.

## Закрытие выпуска

10. <a id="REQ-STORE-010"></a> **REQ-STORE-010** — Первый шаг закрытия и перезакрытие идут в таком порядке: проверки, которым хранилище не нужно, — чистое дерево и расписка; заморозка выпуска операцией `freezeRelease`; чтение замороженных данных и остальные проверки шлагбаума; тег; одна операция `closeRelease` либо `recloseRelease`. Отказ проверки и не вставший тег снимают заморозку операцией `unfreezeRelease` — если заморозил выпуск сам первый шаг закрытия. Выпуск, замороженный до команды закрытия — шагом `release freeze` либо прерванным закрытием без тега, — закрывается без повторной заморозки, и отказ проверки его не размораживает (`REQ-STORE-026`). Пока выпуск заморожен, хранилище отказывает во всех операциях над ним и в смене статуса задач его состава.
11. <a id="REQ-STORE-011"></a> **REQ-STORE-011** — Тег выпуска при внешнем хранилище несёт в аннотации манифест: номер выпуска, коммит, состав с заголовками задач и их условиями выпуска (`REQ-STORE-025`) на момент закрытия, действия развёртывания, ревизию рабочего набора и расписку. Повтор команды, заставший выпуск замороженным, доводит запись в хранилище по манифесту тега и второго тега не ставит; если тега с манифестом этого закрытия нет — снимает заморозку и закрывает заново.
12. <a id="REQ-STORE-012"></a> **REQ-STORE-012** — Учёт обязательств ядра при внешнем хранилище — данные хранилища, а не файл `.conventions/obligations.json`. Незакрытые обязательства берёт в работу первая команда выпуска с ключом записи и закрытие: операция `takeObligations` заводит задачу обязательства и запись учёта. Каталог обязательств и сроки по-прежнему объявляет ядро. Сообщение о долгах (`REQ-RELEASE-035`) печатают `release status` и шлагбаум закрытия; `conventions check` к сети не обращается и долгов не называет.
13. <a id="REQ-STORE-013"></a> **REQ-STORE-013** — Порог открытых вопросов (`REQ-RELEASE-047`) при внешнем хранилище проверяется шлагбаумом закрытия, а не открытием выпуска: выпуск, открытый с доски, закрывается тем же путём, что и открытый командой.

## Проверки и сеть

14. <a id="REQ-STORE-014"></a> **REQ-STORE-014** — Проверка коммитов при внешнем хранилище берёт формат номера из `idPattern`, а существование задачи — из поиска по номерам, названным коммитами диапазона. Найденные номера запоминаются в игнорируемом каталоге `target/store`: известный номер проходит без сети. Номер, который проверить не удалось, даёт предупреждение, а с ключом `--strict` — отказ; CI проекта с внешним хранилищем запускает `conventions commits --strict`. Шаблон этапа плана и запись о задаче (`REQ-RELEASE-040`) при внешнем хранилище не действуют.
15. <a id="REQ-STORE-015"></a> **REQ-STORE-015** — Проверка документации при внешнем хранилище к нему не обращается. Сводки задач и выпусков не требуются; документ типа `ticket` или `release` в репозитории — отказ; ссылка поля метаданных на номер, подходящий под `idPattern`, принимается без поиска; поле `ticket` идеи сверяется с `idPattern`. Команда `tickets-index` собирает только сводку идей.
16. <a id="REQ-STORE-016"></a> **REQ-STORE-016** — Команды, работающие только с файлами задач и выпусков, — `releases-index`, `tickets-renumber`, `naming`, `release adopt`, `release full-run` — при внешнем хранилище отказывают с названием причины.
17. <a id="REQ-STORE-017"></a> **REQ-STORE-017** — Команда `conventions store --check` сверяет хранилище проекта с контрактом: формы ответов, версию, границы рабочего набора, `304`, поиск по номеру и псевдониму. С ключом `--operations` она между выпусками открывает пробный выпуск, проверяет повтор операции, отказы по инвариантам и заморозку и отменяет его; форма условий выпуска задач (`REQ-STORE-025`) проверяется и без ключа; номер пробного выпуска остаётся занятым.
18. <a id="REQ-STORE-018"></a> **REQ-STORE-018** — Поля проекта типа `ticket` (`REQ-PROJECT-PROCESS-024`) действуют для файлов задач. При внешнем хранилище ядро их не читает и хранилищу не передаёт: то, что держит выпуск, хранилище выражает условием выпуска (`REQ-STORE-025`). Так ядро не знает модели данных хранилища. До контракта 3 хранилище получало копию определений операцией `defineFields`, а шлагбаум сверял значения полей с условием `done`.
19. <a id="REQ-STORE-019"></a> **REQ-STORE-019** — Историю выпусков команды при внешнем хранилище не запрашивают: прошлый тег и коммиты вышедших выпусков берутся из тегов git.

## Как читаются требования о файлах

20. <a id="REQ-STORE-020"></a> **REQ-STORE-020** — Требования, говорящие о файлах задач и выпусков, при внешнем хранилище действуют для данных хранилища: документ выпуска (`REQ-RELEASE-004`, `REQ-RELEASE-006`) — запись выпуска в хранилище, а неизменяемая запись о выпущенном — манифест тега; состав (`REQ-RELEASE-007`, `REQ-RELEASE-031`, `REQ-RELEASE-033`) — поле `release` задач; состояние обязательств (`REQ-RELEASE-013`, `REQ-RELEASE-015`) — учёт хранилища; сводки (`REQ-PROJECT-PROCESS-013`) и расположение файла задачи (`REQ-TICKETS-013`) не действуют; номер новой задаче выдаёт хранилище, и перенос номера (`REQ-TICKETS-022`) не нужен; существование задачи, названной коммитом (`REQ-PROJECT-PROCESS-023`), — по `REQ-STORE-014`.

## Переход проекта

21. <a id="REQ-STORE-021"></a> **REQ-STORE-021** — Проект переходит с файлов на внешнее хранилище командой `conventions store --move` между выпусками: открытого выпуска нет. Команда отказывает до любых изменений, если выпуск открыт, хранилище не исполняет контракт, номер задачи не подходит под `idPattern` или в каталогах задач и выпусков лежит документ иного типа. Она передаёт хранилищу выгрузку проекта, сверяет, что каждая задача и каждый выпуск приняты под прежним номером, и только после этого заменяет ссылки на файлы задач и выпусков в остальных документах номером в обратных кавычках, убирает `docs/tickets`, `docs/releases` и `.conventions/obligations.json` и записывает `store` в `.conventions.json`. Ссылка в строке кода и в блоке кода не заменяется: её называет проверка документации, и правит человек. Переход фиксируется одним коммитом; тем же изменением CI получает `conventions commits --strict`.
22. <a id="REQ-STORE-022"></a> **REQ-STORE-022** — Выгрузка `conventions store --export` несёт задачи в форме контракта с полным текстом, выпуски с их документами, учёт обязательств, число вышедших выпусков и определения полей проекта; значения полей задач выгружаются как есть, и хранилище переводит их в условия выпуска по своим правилам (`REQ-STORE-025`). Хранилище принимает её по адресу `POST {url}/import` частями: задачи — не больше 200 за запрос; повтор импорта ничего не удваивает, вышедшие и отменённые выпуски хранятся как есть. Срок обязательства после перехода равен сроку до него.

## Чтения для скриптов проекта

23. <a id="REQ-STORE-023"></a> **REQ-STORE-023** — Скрипт проекта читает хранилище командами пакета правил, а не своим клиентом контракта: `conventions store --lookup <номер,номер>`, `conventions store --working` и `conventions store --open` печатают ответ чтения (`REQ-STORE-005`) в JSON в форме контракта и ключа записи не требуют. Поиск с ключом `--body` передаёт хранилищу признак `withBody` и получает у каждой задачи поле `body` — её текст в Markdown, для задачи без текста пустую строку; без признака поля `body` в ответе нет, и в рабочем наборе его нет никогда. Разделы проекта в тексте разбирает проект: ядро их не знает. `conventions release status --json` печатает открытый выпуск, тег, состав с условиями выпуска, действия развёртывания с отметками и препятствия: до первого шага закрытия — закрытию, после него — завершению. Отметок до первого шага закрытия нет: действие отмечается после него (`REQ-RELEASE-049`). Условия выпуска задач на момент закрытия записаны в манифесте тега (`REQ-STORE-011`).

## Состав при внешнем хранилище

24. <a id="REQ-STORE-024"></a> **REQ-STORE-024** — При внешнем хранилище слияние работы задачу не закрывает: выполненной её делает выход выпуска. Поэтому состав открытого выпуска, кроме указанных при открытии задач (`REQ-RELEASE-007`), подбирает задачи без выпуска, которые выполнены либо названы коммитом диапазона закрытия — их работа слита в `main` после прежнего выпуска, — в любом статусе, кроме отменённой и замещённой (`REQ-RELEASE-031`). Снятая из состава задача (`REQ-RELEASE-033`) подбором не возвращается, и её коммиты держат закрытие (`REQ-RELEASE-036`). Закрытие не требует статуса «выполнена» и называет указанную при открытии задачу без слитой работы. Завершающий шаг (`REQ-RELEASE-034`) статус задач не проверяет: операция `finishRelease` хранилища переводит задачи состава, кроме отменённых и замещённых, в выполненные, а обязательство закрывается задачей состава, которая не отменена (`REQ-RELEASE-019`). Подбор не учитывает задачу, последний коммит которой в диапазоне снимает работу меткой `!revert` (`REQ-RELEASE-037`), и коммиты старше порога `commitRuleSince`. У задачи, которую выпуск сделает выполненной, закрытие держит невыполненное условие выпуска `before-release` (`REQ-STORE-025`). Решение владельца от 2026-11-19. Это меняет обязанность хранилища, поэтому версия контракта — 2 (`REQ-STORE-004`): хранилище, которое ставит «выполнена» в `finishRelease`, отвечает `contract: 2`, а хранилище контракта 1 команда отвергает с названием требуемой версии — иначе выпуск молча оставил бы задачи невыполненными. Выпуск ядра — 19.0.0; контракт 3 (`REQ-STORE-025`) эту обязанность сохраняет.

## Условия выпуска задачи

25. <a id="REQ-STORE-025"></a> **REQ-STORE-025** — Задача контракта 3 несёт условия выпуска `conditions` — перечень `{key, phase, state}`: `key` — имя условия, которое выбирает хранилище, у задачи без повторов; `phase` — `before-release` либо `after-release`; `state` — `pending`, `done` либо `not-required`. Откуда условия берутся — из маршрута задачи, этапов или иначе — решает хранилище: ядро модели его данных не знает. Шлагбаум закрытия держит выпуск, пока у задачи состава, которую выпуск выпускает, есть условие `before-release` в состоянии `pending`, и называет задачу и ключ условия. Условия `after-release` закрытие и завершающий шаг не держат — это работа после развёртывания, как действия раздела «После развёртывания» (`REQ-RELEASE-049`); `release status` показывает условия задач состава, а их состояние дальше ведёт хранилище. Условие выпуска — не обязательство ядра (`REQ-RELEASE-008`): его вводит хранилище, и долгом потребителя перед ядром оно не является. Решение владельца от 2026-11-19 по модели, проект изменений — [ADR-0009](../decisions/ADR-0009-store-contract-3-release-conditions.md); выпуск ядра — 20.0.0.

## Выпуск по шагам

26. <a id="REQ-STORE-026"></a> **REQ-STORE-026** — Проект, у которого порядок шагов выпуска ведёт хранилище, вызывает каждый шаг отдельной командой: `release open --task <задача>` открывает выпуск, который ведёт задача выпуска (аргумент `task` операции `openRelease`); `release freeze` замораживает состав (`freezeRelease`) после сведения обязательств; `release unfreeze --reason` снимает заморозку (`unfreezeRelease`); `release record-e2e --commit <полный хеш>` записывает зелёный e2e выпуска на коммите (операция `recordE2e`, допустимая и у замороженного выпуска; новая запись заменяет прежнюю); `release close` закрывает замороженный выпуск. Открытый выпуск в ответе хранилища несёт `task` — задачу выпуска либо `null` — и `e2e` — `{commit, at}` либо `null`; `release status --json` показывает оба поля. Выпуск, который ведёт задача выпуска, закрывается только на коммите, где записан зелёный e2e: шлагбаум закрытия проверяет это до тега и называет команду записи, а хранилище отказывает `closeRelease` кодом `release-commit-unchecked`. Поля и операция необязательны для хранилища: проект, который их не вызывает, работает, как прежде; хранилище, которое их не знает, отказывает своим кодом. При файлах задач команды отказывают: выпуск ведёт документ выпуска. Заявка потребителя (DRIAD-791, `CORE-OPS-135`); проект изменений — [ADR-0010](../decisions/ADR-0010-release-steps.md); выпуск ядра — 20.2.0.
27. <a id="REQ-STORE-027"></a> **REQ-STORE-027** — Заморозка проверяет, что выпуск можно будет закрыть. `release freeze` и шаг заморозки в `release close` проходят тот же шлагбаум, что и закрытие, кроме частей, привязанных к закрываемому коммиту: расписки о verify и e2e. Если шлагбаум находит хоть одну проблему, заморозка отказывает и перечисляет все: просроченное обязательство, отменённую задачу или задачу без слитой работы в составе, неучтённый коммит, зависимость, открытый вопрос, занятый тег. Условие выпуска может нести необязательное поле `due: "freeze"`, и только при `phase: "before-release"`. Такое условие должно быть выполнено до заморозки состава, и пока оно `pending`, заморозка отказывает с названием задачи и ключа. Какие условия так помечать, решает хранилище: например, этап, который держит внешний исполнитель или владелец. Ядро не знает, кто держит условие. Прочие условия `before-release` заморозку не держат: их выполняют, пока выпуск заморожен, и закрытие держит их, как прежде (`REQ-STORE-025`). Ключа обхода у заморозки нет: всё, на чём она отказывает, держит и закрытие, так что обход только перенёс бы отказ на закрытие. Заявка потребителя DRIAD-825 (`CORE-OPS-136`). Зелёный e2e переносится через правки вне сборки. У выпуска, который ведёт задача выпуска (`REQ-STORE-026`), e2e может быть записан не на закрываемом коммите, а на его предке. Тогда закрытие и перезакрытие принимают такой e2e, если каждый файл, изменённый между этими коммитами, лежит вне сборки. Вне сборки лежат `docs/`, каталог состояния и пути из `e2e.outsideBuild` в `.conventions.json`; пути задаются префиксами от корня, как в `verify.parts`. Перечень вне сборки — утверждение проекта о том, что эти файлы не попадают в собранное и развёрнутое. Перед тегом команда записывает перенос операцией `recordE2e {commit, from}`, где `from` — коммит прогона, а манифест тега несёт `e2e: {commit, from}`. Если изменён хоть один файл сборки или коммит прогона не предок закрываемого, команда отказывает. Отказ называет первые такие файлы и команду записи прогона. Поле `from` для хранилища необязательно: хранилище, которое его знает, хранит происхождение записи. Расписку о verify перенос не затрагивает: она переносится только по дереву кода (`REQ-RELEASE-045`). Заявка потребителя DRIAD-826 (`CORE-OPS-136`); проект изменений — [ADR-0011](../decisions/ADR-0011-freeze-gate-e2e-carry.md); выпуск ядра — 20.3.0.
28. <a id="REQ-STORE-028"></a> **REQ-STORE-028** — Проект без e2e объявляет это в `.conventions.json`: `"e2e": {"required": false, "reason": "<причина>"}`; причина обязательна, `outsideBuild` рядом с таким объявлением отвергается — переносить нечего (`REQ-STORE-027`). Объявление действует на весь проект, а не на отдельный выпуск: ключ команды открытия позволил бы проекту со стендом пропустить e2e в спешке, а строка в репозитории проходит ревью и видна в истории. `release open --task` такого проекта передаёт в `openRelease` `e2eRequired: false` и `e2eReason`; хранилище держит их у выпуска, ответ о выпуске несёт `e2eRequired` (нет поля — `true`), а `closeRelease` и `recloseRelease` такого выпуска не отказывают кодом `release-commit-unchecked`. Шлагбаум закрытия требует e2e (`REQ-STORE-026`) только у выпуска с задачей, у которого `e2eRequired` не `false`, — то есть читает выпуск, а не объявление: выпуск, открытый до объявления или на доске хранилища без него, по-прежнему требует e2e. Манифест тега такого выпуска несёт `e2eRequired: false`; `release status --json` показывает `e2eRequired`. Выпуск без задачи объявления не читает и закрывается, как прежде. Поле и аргументы необязательны для хранилища (расширение контракта 3); хранилище вправе отказать в `e2eRequired: false` проекту, у которого знает стенд. Заявка потребителя DRIAD-830 (`CORE-OPS-137`): проект без QA-стенда не мог выпускаться выпуском с задачей; выпуск ядра — 20.4.0.
