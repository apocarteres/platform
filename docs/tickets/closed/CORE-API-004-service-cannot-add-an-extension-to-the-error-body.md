# Сервис не может добавить расширение в тело ошибки

## Проблема

`REQ-API-001` называет состав тела ошибки: `type`, `title`, `status`, `detail`,
`instance` и расширение `code`. Тело формирует совет ядра, а своих форм сервис
вводить не вправе — и это верно. Но у публичного API есть сведение, которое
принадлежит ответу, а не сообщению: корреляционный идентификатор запроса.
Клиент цитирует его в обращении в поддержку, и по нему находят строку в логах.

Портов для этого нет: `ErrorCodeResolver` отдаёт код и статус,
`ErrorMessages` — текст. Расширение `ProblemDetail` добавить неоткуда.

## Чем подтверждено

Случай в проекте `zavpn` 2026-09-11. Его клиентский API отдаёт ошибку с полями
`code`, `message` и `requestId`; последний записан в требованиях проекта как
часть публичного контракта. При переходе на `ProblemDetail` поле исчезает: тело
собирает `ApiErrorAdvice`, и добавить в него расширение сервис не может.
Потребитель выпускает изменение контракта с потерей поля и записывает это как
известное расхождение.

## Последствия при сохранении текущего поведения

Либо сервис теряет корреляционный идентификатор в ответе, либо возвращает свою
форму тела и нарушает `REQ-API-001`. Первое ухудшает разбор обращений, второе
ломает единый контракт — то есть правило подталкивает к выбору между двумя
плохими вариантами.

## Ожидаемый результат

Сервис может добавить в тело ошибки свои расширения, не вводя своей формы: порт
расширений, вызываемый советом ядра, либо расширение, которое ядро добавляет
само, если сервис объявляет источник корреляционного идентификатора. Состав
обязательных полей при этом остаётся за `REQ-API-001`.

## Критерии приёмки

- Сервис добавляет в тело ошибки расширение, не подменяя совет ядра.
- Обязательные поля `ProblemDetail` остаются неизменными.
- Правила называют, что делать с корреляционным идентификатором запроса.

## Ход выполнения

### Шаг 1 (2026-09-11)

Совет по ошибкам возвращает `ResponseEntity<ProblemDetail>` вместо голого тела
и собирает ответ из трёх источников: обязательные поля и `code` — ядро, поля
расширения — порт `ErrorExtensions`, заголовки — заголовки исключения
платформы приложений плюс порт `ErrorHeaders`. Без объявленных портов ответ
прежний.

Портов сделано два, а не один: заголовок и поле тела — разные части ответа, и
сервису, которому нужен только `Retry-After`, незачем объявлять порт,
говорящий о теле.

Нормативный текст: `REQ-API-007` (поля расширения) и `REQ-API-008`
(заголовки). Заодно уточнён `REQ-API-005` по замечанию заявителя: запрет
касается обработчика, который отображает исключение в статус или вводит свою
форму тела; обработчик, добавлявший то, чего контракт не выражал, запретом не
охватывался — и теперь не нужен.

### Результаты проверок (2026-09-11)

| Прогон | Результат |
| --- | --- |
| Тесты модуля | 12 в трёх файлах, из них 4 новых на порты |
| `mise run check` | 128 документов, 296 положений, правила соблюдены, сборка успешна |
| Тесты пакета правил | 151 из 151 |

Новые тесты проверяют: порт заголовков ставит `Retry-After` на `429`;
заголовки рамочного исключения доходят без порта; порт расширений кладёт
`requestId` и `available` рядом с `code`; без портов ответ прежний, и тип
содержимого остаётся `application/problem+json`.

### Что до потребителей

Случай `zavpn` с корреляционным идентификатором закрывается портом
`ErrorExtensions`: сервис объявляет бин и возвращает `requestId` в карте. Ту же
потребность независимо прислал `clanlog` — складские подробности отказа
списания, https://github.com/apocarteres/platform/issues/1

## Откуда пришла задача

Задача `API-001` проекта `zavpn`: переход на контракт ошибок ядра потребовал
убрать `requestId` из тела ошибки публичного клиентского API.
