# ADR-0009: контракт хранилища 3 — условия выпуска задачи вместо полей проекта

## Контекст

При внешнем хранилище шлагбаум закрытия проверяет поля проекта задачи
(`REQ-PROJECT-PROCESS-024`, `REQ-STORE-018`): хранилище отдаёт значения полей
`fields`, ядро сверяет их с условием `done` из `.conventions.json`. Так ядро
знает модель данных трекера: имена полей, их значения, какие из них держат
выпуск. Трекер Driada-Lab переходит к задаче как к статусу, маршруту (шаблону
конвейера) и записям этапов; поля `manual-qa`, `qa-level`, `pre-deploy`,
`post-deploy`, `maintenance`, `team-action` уходят (TR-173). Каждая правка
маршрута в трекере требовала бы правки ядра.

Заявка Manager 2026-11-19 (`CORE-OPS-132`) со ссылкой на решение владельца:
хранилище отдаёт по задаче перечень того, что должно быть сделано до выпуска и
после него, а ядро решает только по состоянию пунктов. Изменение мажорное, с
новой версией контракта. Открытые вопросы — имя, переход, файлы задач, манифест
тега — заявка оставила проекту изменений.

## Решение

Решение владельца от 2026-11-19 по модели; вопросы ниже решены проектом
изменений 2026-11-20.

1. **Имя — «условие выпуска», а не «обязательство».** В словаре ядра
   «обязательство» — долг потребителя перед ядром (`REQ-RELEASE-008`,
   `docs/terms/DEFINITIONS.md`), и у задачи уже есть поле `obligation` — номер
   обязательства ядра, которое она исполняет. Пункт перечня задачи — другое
   понятие: его вводит хранилище, а не ядро, и долгом перед ядром он не
   является. Одно слово для двух понятий смешало бы учёт обязательств с
   воротами задачи. Поле контракта — `conditions`.
2. **Форма.** Задача контракта 3 несёт `conditions` — перечень
   `{key, phase, state}`: `key` — имя условия, которое выбирает хранилище;
   `phase` — `before-release` либо `after-release`; `state` — `pending`, `done`
   либо `not-required`. Поле `fields` из формы задачи уходит, как и
   `fieldsDigest` рабочего набора и операция `defineFields`: ядро больше не
   передаёт хранилищу определения полей и не сверяет их значения.
3. **Ворота.** Шлагбаум закрытия держит выпуск, пока у задачи состава, которую
   выпуск выпускает, есть условие `before-release` в состоянии `pending`, и
   называет задачу и ключ условия. Условия `after-release` закрытие и
   завершающий шаг не держат: это работа после развёртывания, как действия
   раздела «После развёртывания» (`REQ-RELEASE-049`). `release status`
   показывает условия задач состава, хранилище ведёт их состояние дальше.
   Отменённая и замещённая задача не выпускается, и её условия ворот не держат.
4. **Переход — одним шагом.** Пакет правил знает одну версию контракта
   (`REQ-PUBLISHING-005`: без переходного периода с двумя контрактами). Чтобы
   потребители одного хранилища поднимали ядро не в один день, пакет правил
   называет свою версию в каждом запросе заголовком `X-Store-Contract`, а
   хранилище, которое ведёт потребителей на разных версиях ядра, отвечает в
   названной версии. Переходный период — забота хранилища, а не ядра.
5. **Файлы задач не меняются.** При хранилище в файлах поля проекта и их
   условие `done` действуют, как прежде: у файла задачи нет перечня условий,
   и замены полям в нём не нужно. Объявления полей типа `ticket` при внешнем
   хранилище ядро не читает; переход с файлов (`conventions store --move`)
   выгружает значения полей как есть, и хранилище переводит их в условия
   по своим правилам.
6. **Манифест тега** несёт условия задач состава на момент закрытия вместо
   значений полей проекта. Повтор закрытия по манифесту хранилищу их не
   передаёт: состояние условий — данные хранилища.

## Последствия

- Выпуск ядра — мажорный, 20.0.0, с миграцией в документе выпуска.
- Хранилище контракта 2 пакет правил 20.0.0 отвергает отказом
  `contract-version`; хранилище контракта 3 отвергается пакетом правил 19.
- Поля проекта при внешнем хранилище больше ничего не держат: то, что они
  держали, хранилище выражает условием `before-release`.
- `conventions store --check` проверяет форму условий.
