# Тест первым, пробы поломкой — итоговой проверкой набора

## Мысль

Рекомендовать потребителям порядок работы, который ядро сначала проверит на
себе:

1. **Дефект — тест первым.** Тест воспроизводит отказ на текущем коде и падает;
   потом исправление, и тот же тест проходит. Это исполняет `REQ-QUALITY-011`
   прямо, а не задним числом.
2. **Новая возможность — тест первым на каждое положение требования.** Для
   быстрых тестов — по одному; для медленных, с контейнерами, — пачкой: тесты
   на несколько положений, один прогон с ожидаемым отказом, затем реализация.
3. **Пробы намеренной поломкой — итоговой проверкой всего набора**, а не
   заменой красного шага: они находят то, о чём автор тестов не подумал, —
   дубли проверок, мёртвые ветки, отказ по чужой причине.

## Почему

Решение владельца от 2026-09-25 — сначала на ядре. Основание — работа над
выпусками 9.2–11.3, где тесты писались вслед за кодом, а пробы находили в них
дыры: тест письма смотрел через соединение открытой транзакции и не видел
письма до фиксации; предел в 5000 записей закрывался пределом объёма; тест
обёртки `fetch` не проверял, что доходят свои заголовки; тест команды
отказывал по другой причине. Каждая дыра — тест, написанный под уже
работающий код. Там, где тест шёл первым (исправление CORE-OPS-094), отдельная
проба не понадобилась.
