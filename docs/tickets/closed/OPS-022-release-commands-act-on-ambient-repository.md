# Команды выпуска действуют на репозиторий из окружения

## Проблема

Команды выпуска обращались к git через одну обёртку
`packages/project-conventions/lib/release/git.mjs`, вызывая
`git -C <корень> …` с наследованием окружения процесса. Git разрешает
переменной `GIT_DIR` перебивать ключ `-C`, а git-хуку git эту переменную
экспортирует всегда. Значит внутри любого хука команда выпуска работала не с
тем корнем, который ей передали, а с репозиторием хука: `headCommit` читал
чужой `HEAD`, `workingTreeClean` оценивал чужое дерево, `createTag` ставил тег
в чужом репозитории.

Тот же наследованный `GIT_DIR` ломал тесты пакета: их фикстуры собирают
временный репозиторий вызовами `git -C <временный каталог> init | add |
commit`, и под хуком эти вызовы уходили в настоящий репозиторий.

## Чем подтверждено

Случай 2026-09-10 в самом ядре. Отправка ветки была отклонена хуком
`pre-push`, выполняющим `mise run check`: шаг `conventions-test` дал 5 отказов
с одинаковой причиной.

```
Command failed: git -C /var/folders/.../conventions-Hihdjz add -A
fatal: this operation must be run in a work tree
```

Вне хука тот же набор проходил целиком. Зависимость от переменной измерена
прогоном набора с подставленным `GIT_DIR`:

| `GIT_DIR` | Отказов |
| --- | --- |
| не задан | 0 |
| `platform/.git` | 2 |
| `platform/.git/worktrees/<рабочее дерево>` | 5 |

Последствия оказались тяжелее заблокированной отправки. Прогон с `GIT_DIR`,
указывающим на живой каталог git, выполнил фикстурные `init`, `config` и
`commit` в настоящем репозитории:

1. Ветка `main` уехала с выпускного коммита на фикстурный: пять коммитов
   «состояние» от автора `Test <test@example.test>`, удаляющих документы.
2. В общей конфигурации репозитория оказалось `core.bare = true`; основной
   рабочий каталог перестал отвечать даже на `git status`
   (`fatal: this operation must be run in a work tree`).
3. В ту же конфигурацию записалась фикстурная личность `user.name = Test`,
   `user.email = test@example.test`.
4. Появился фикстурный тег `2026.09.1` от теста закрытия выпуска.

Файлы на диске при этом не пострадали, в `origin` ничего не ушло. Состояние
восстановлено: конфигурация приведена в исходный вид, `main` возвращён на
выпускной коммит обычным (не `--hard`) сбросом, фикстурный тег удалён.

Порча произошла при диагностике: набор был запущен вручную с `GIT_DIR`,
направленным на рабочий каталог git, чтобы воспроизвести отказ хука. Это и
есть мера дефекта — воспроизведение оказалось разрушительным.

## Последствия при сохранении текущего поведения

1. Шлагбаум `REQ-QUALITY-004` неработоспособен: отправка невозможна, пока
   отказ не обойдут ключом `--no-verify`, то есть проверки перестают
   выполняться именно там, где они обязательны.
2. Команда закрытия выпуска, вызванная из хука, ставит тег в чужом
   репозитории и читает чужой `HEAD`. Тег выпуска перестаёт означать
   проверенный коммит — основание `REQ-RELEASE-003` теряется.
3. Прогон тестов пакета в подходящем окружении переписывает рабочую ветку и
   конфигурацию репозитория. Это потеря данных, а не неудобство, и она
   происходит молча.

## Требуется

1. Git выполняется без наследования переменных, задающих репозиторий: ключ
   `-C` остаётся единственным источником корня.
2. Вычистка делается в одном месте, через которое проходят все команды
   выпуска, а не в каждом вызове.
3. Фикстуры тестов собирают временные репозитории тем же способом.
4. Инвариант закреплён тестом, который различает подмену репозитория.

## Критерии приёмки

- Команда выпуска, получившая корень, читает `HEAD` этого корня при заданном
  `GIT_DIR`, указывающем на другой репозиторий.
- Набор тестов пакета проходит под окружением git-хука.
- Отправка проходит с включённым хуком `pre-push`, без `--no-verify`.
- Прогон набора с подставленным `GIT_DIR` не оставляет следов в том
  репозитории: ветка, конфигурация и перечень тегов не меняются.

## Ход выполнения

### Шаг 1 (2026-09-10)

В `lib/release/git.mjs` добавлена `environmentWithoutGit`, отдающая окружение
без переменных с приставкой `GIT_`; обёртка `git` передаёт её дочернему
процессу. Правка в одном месте покрывает все команды выпуска: `headCommit`,
`workingTreeClean`, `tagExists`, `createTag`.

Фикстуры `test/cli.test.mjs` и `test/release-cycle.test.mjs` переведены на
локальный помощник `git`, вызывающий ту же функцию, вместо прямого
`run('git', …)`.

Первая редакция регрессионного теста проходила и без починки продукта: два
фикстурных репозитория выходили байт-идентичными — одно дерево, одно
сообщение, одна секунда — и давали один и тот же SHA, поэтому подмена
репозитория ничего не меняла в ответе. Тест переписан на различающиеся
репозитории и проверен в обе стороны: без вычистки он читает `HEAD` чужого
репозитория, с вычисткой — переданного.

### Результаты проверок (2026-09-10)

| Прогон | Результат |
| --- | --- |
| `node --test test/*.test.mjs` | 124 из 124 |
| То же с `GIT_DIR` окружения хука (было 5 отказов) | 124 из 124 |
| `mise run check` | 99 документов, правила соблюдены, Java-тесты 19 и 9, сборка успешна |
| `git push` с включённым хуком | пройден |
| Прогон с подставленным `GIT_DIR` после починки | следов в репозитории нет |

Достаточность проверок подтверждена по `REQ-TICKETS-015`: критерий про
отсутствие следов проверялся не тестом, а осмотром ветки, конфигурации и
перечня тегов после прогона, потому что тест по построению не может
засвидетельствовать отсутствие записи в чужой репозиторий.

### Что не покрыто

Команда расписки запускает набор проверок потребителя
(`bin/conventions.mjs`, `spawn` с `cwd: root`) с полным наследованием
окружения — иначе задача менеджера окружения не поднимется. Значит `GIT_DIR`
доходит до самого набора, и вызов git внутри задачи потребителя остаётся его
ответственностью. Нормативного правила об этом не вводится: ядро не знает,
чем потребитель наполняет набор.

Задача `OPS-021` этим изменением не затронута: она о составе шлагбаума —
о том, что `check` по построению не видит отказов уровня подъёма приложения, —
и остаётся открытой.
