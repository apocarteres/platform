# Исследование: правила ядра проверяются только на ядре

## Цель

Определить, как проверять правила, обращённые к потребителю, до выпуска, а не
после него. Итог — решение (ADR) с выбранным средством и оценкой его цены.

## Основание

За 2026-09-11 и 2026-09-12 потребители подали восемь заявок. Пять из них —
дефекты в механизмах, которые ядро ввело само и на себе проверило вхолостую:
проверка проходила, потому что у ядра нет той структуры, к которой правило
обращено.

| Задача | Что не сработало | Почему ядро не увидело |
|---|---|---|
| `CORE-OPS-033` | диапазон коммитов выпуска брался по порядку имён файлов | у ядра были выпуски `1.0.0`–`1.7.0`, где порядок имён совпадает с порядком номеров |
| `CORE-DATA-003` | порт сериализации регистрировался по наличию чужой библиотеки | в сборке ядра библиотека была на classpath у тестов и бин всегда поднимался |
| `CORE-OPS-037` | обязательство ссылалось на недоставляемый документ | ядро читает свой репозиторий, где доступны все документы |
| `CORE-OPS-040` | граница реализации проверялась по пакету, а не по модулю | у модулей ядра корневой пакет к своему `internal` не обращается: автоконфигурация регистрируется файлом ресурса |
| `CORE-QUAL-007` | принадлежность выпуску устанавливалась по пути файла задачи | у ядра порядок работы иной: сводки перегенерируются сразу, и разрыв не успевает проявиться |

Общее у всех пяти: проверка отказывает только там, где её применяют, и молчит
там, где её пишут. `CORE-OPS-040` — крайний случай: 655 нарушений у потребителя
и ноль у ядра на том же правиле.

Средство частично есть: проверки цикла выпуска уже испытываются на подставном
репозитории с чужим префиксом задач. Именно поэтому дефекты цикла ловились
тестами, а дефекты, зависящие от формы проекта — числа выпусков, состава
classpath, устройства пакетов, границы поставки, — не ловились.

## Последствия при сохранении текущего поведения

Каждое новое правило ядра проверяется у потребителя в производственной среде.
Цена — заявка, выпуск и переход, умноженные на число потребителей; при этом
`REQ-ADOPTION-004` обещает, что ядро не требует немедленного соответствия, а на
деле потребитель получает отказ проверки на своём коде и останавливается.

## Открытые вопросы

Ответ записывается рядом с вопросом с датой. Рекомендация исполнителя решением
не является.

1. Что считать «формой потребителя». Разбор 2026-09-12: перечень выведен из
   случившихся дефектов, для каждого свойства названа задача, которая на нём
   поймалась бы.

   | Свойство формы | Дефект, который на нём ловится | Есть ли в нынешних подставных репозиториях |
   |---|---|---|
   | порядковый номер выпуска из двух знаков | `CORE-OPS-033` | нет |
   | classpath без библиотек, которых проект не объявлял | `CORE-DATA-003` | нет |
   | правила видны только доставленным перечнем документов | `CORE-OPS-037` | нет |
   | несколько Java-модулей: контракт в корне, реализация в `internal`, обращение из корня к своей | `CORE-OPS-040` | нет |
   | выполненная задача переезжает в `closed/` при открытом выпуске | `CORE-QUAL-007` | нет |
   | объявленный префикс задач | `CORE-OPS-034` | да |
   | коммит, меняющий только документы задач | `CORE-OPS-039` | да, добавлено при разборе заявки |
   | слияние веток в истории | `CORE-OPS-038` | да, добавлено при разборе заявки |

   Три свойства из восьми уже есть — и все три появились после того, как
   соответствующий дефект нашёл потребитель, а не до. Пять отсутствуют.
   Ответ: —
2. Средство. Ответ владельца 2026-09-12: один эталонный репозиторий-потребитель,
   постоянный, а не по фикстуре на дефект. Сделано: `test/reference-consumer.mjs`
   строит его, `test/reference-consumer.test.mjs` проверяет на нём правила, и оба
   входят в набор `check`.

   Ловит задним числом, проверено возвратом каждой правки:

   | Дефект | Возврат правки роняет |
   |---|---|
   | `CORE-OPS-033` | закрытие выпуска: «Коммит … относится к задаче REF-QUAL-010 вне состава» |
   | `CORE-OPS-038` | то же закрытие на коммите слияния |
   | `CORE-OPS-039` | то же закрытие на коммите-записи |
   | `CORE-QUAL-007` | проверку документов на задаче, переехавшей в `closed` |
   | `CORE-OPS-037` | проверку обязательств (`project-rules.test.mjs`) |
   | `CORE-OPS-040`, `CORE-DATA-003` | проверки java-части: подставные модули и сборка без чужих библиотек |
3. Что делать с правилами, которые нельзя испытать на подставном репозитории.
   Разбор 2026-09-12: доставляемые правила делятся на три класса — форма проекта
   (проверяется эталоном), сборка и среда потребителя (`REQ-BUILD`,
   `REQ-QUALITY`, `REQ-DEPS`, `REQ-CONFIG` — проверяется только у потребителя,
   у ядра его сборки нет), обращённые к человеку (`REQ-PROJECT-PROCESS`,
   `REQ-AGENT-WORK`, канал заявок — машиной не проверяются вовсе). Правило
   второго и третьего класса называет свой класс в своём тексте
   (`REQ-PUBLISHING-013`).
4. Нужно ли ядру запускать свои проверки на настоящем репозитории потребителя
   перед выпуском. Ответ владельца 2026-09-12: нет, только подставной. Результат,
   зависящий от того, что лежит на машине выпускающего, воспроизводимым не
   является, а `REQ-BUILD-002` запрещает сборке ходить в сеть.
5. Правило «правило, проверенное только на ядре, считается непроверенным».
   Ответ владельца 2026-09-12: вводится требованием к ядру —
   `REQ-PUBLISHING-012`, во внутреннем документе: потребителя оно не обязывает,
   а обязывает того, кто выпускает правила.
6. Чего это стоит. Замер 2026-09-12: эталон занимает 4,5 с из 13 с прогона
   тестов пакета правил — треть. Сопровождает его тот, кто меняет доставляемое
   правило: свойство формы добавляется вместе с правилом (`REQ-PUBLISHING-013`).

## Границы

Исследование не заменяет канал заявок (`REQ-ADOPTION-019`): потребитель
остаётся источником находок, которых не предвидели. Предмет — дефекты, которые
ядро может найти у себя до выпуска, а сейчас не находит.

## Критерии приёмки

- Перечень свойств «формы потребителя» записан и обоснован дефектами из
  основания: для каждого свойства названа задача, которая на нём поймалась бы.
- Средство выбрано, его цена названа.
- Записано решение (ADR); при отказе причина записана там же.

## Откуда пришла задача

Наблюдение по итогам восьми заявок 2026-09-11 и 2026-09-12: пять дефектов
одного узора — правило ядра, проверенное на коде, к которому оно не обращено.

## Что сделано

Эталонный репозиторий-потребитель построен: `test/reference-consumer.mjs` строит
его, `test/reference-consumer.test.mjs` проверяет на нём правила, оба входят в
набор `check`.

Форма эталона: десять выпусков одного месяца, так что десятый по имени идёт
раньше девятого; у каждого выпуска свой коммит и свой тег; объявленный префикс
задач; правила видны только доставленным перечнем документов; Java-модуль, чей
корневой пакет пользуется своей реализацией; слияние ветки; коммит, меняющий
только документы задач; задача, переезжающая в `closed` при открытом выпуске.

Проверено возвратом каждой правки — эталон роняет проверку на пяти дефектах из
таблицы основания; два оставшихся ловятся java-частью.

Честно о том, как это строилось: фикстура трижды оказывалась враньём, и каждый
раз это находило утверждение, а не чтение. Первая версия засеяла выпуски другим
месяцем — порядковый номер сбросился, и двузначности не было. Вторая дала всем
тегам один коммит — диапазон между ними пуст, подмена сравнения ничего не
меняла. Третья ничего не утверждала о проверке документов, а когда потребовал
пустой список ошибок, выяснилось, что у «потребителя» нет ни входной сводки, ни
требований, ни каталога решений.

Требования: `REQ-PUBLISHING-012` — правило, проверенное только на ядре, считается
непроверенным; `REQ-PUBLISHING-013` — правило, не проверяемое эталоном, называет
свой класс, а эталон растёт вместе с правилами.
