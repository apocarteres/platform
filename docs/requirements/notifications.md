# Уведомления внутри приложения: колокольчик

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: служба на Spring Boot с аутентификацией ядра и её одностраничный клиент, подключившие уведомления.** Ядро поставляет колокольчик библиотекой: starter `platform-notifications` и пакет клиента `@apocarteres/notifications`. Колокольчик, как на многих сайтах, показывает число непрочитанного, а по щелчку — короткий список последних уведомлений. Как с модальными окнами, проект рисует только вид. Решение владельца от 2026-09-25 (`CORE-ARC-018`), пересмотр `ADR-0001`: отдельного сервиса уведомлений пока нет. Модуль необязателен.

**Уровень требования: директива.**

## Уведомление

1. <a id="REQ-NOTIFICATIONS-001"></a> **REQ-NOTIFICATIONS-001** — Уведомление принадлежит учётной записи ядра (`REQ-AUTH`). Таблицу создаёт журнал ядра `platform/changelog/platform-notifications.yaml`, который проект подключает в свой главный журнал Liquibase (`REQ-DATA-ACCESS-007`); образец `sql/platform-notifications/create-notification.sql` — справка; удаление учётной записи (`REQ-AUTH-024`) стирает её уведомления вместе с ней.
2. <a id="REQ-NOTIFICATIONS-002"></a> **REQ-NOTIFICATIONS-002** — Уведомление создают проект и модули ядра Java API `Notifications.notify(account, kind, params, link)`. Вид — строчные латинские буквы и цифры с точкой или дефисом, до 64 знаков, например `support.answered`; параметров — не больше 20, имя — латиница и цифры до 32 знаков, значение — строка до 200 знаков без управляющих; ссылка — путь сайта от корня, до 500 знаков, а не адрес: чужой адрес в колокольчике — открытое перенаправление. Нарушение — отказ вызова. Создание идёт в транзакции вызывающего: откатилась работа — уведомления нет.
3. <a id="REQ-NOTIFICATIONS-003"></a> **REQ-NOTIFICATIONS-003** — Ядро хранит вид, параметры и ссылку, а текст на нужном языке собирает клиент проекта по виду: у ядра нет перевода и бренда, а язык человека может смениться после уведомления. Параметры — то, чем текст собирается: номер, название, число, — а не почта, телефон и свободный текст человека: уведомление живёт отдельно от данных, к которым ведёт, и копировать в него персональные данные незачем.

10. <a id="REQ-NOTIFICATIONS-010"></a> **REQ-NOTIFICATIONS-010** — Созданные уведомления проект правит Java API `Notifications.revise(kind, link, change)`: уведомления вида `kind` со ссылкой `link` — она обязательна, уведомление без ссылки не правится — у всех учётных записей проходят через `change`, который получает параметры уведомления и возвращает новые — по правилам `REQ-NOTIFICATIONS-002`, — те же, тогда уведомление не меняется, или `null`, тогда уведомление убирается. Прочитанность и время создания не меняются; возвращается число изменённых и убранных. Нарушение правил в параметрах любого из уведомлений — отказ вызова без частичной правки. Правка идёт в транзакции вызывающего: откатилась работа — уведомления прежние; строки заняты до её конца, поэтому `change` — чистая функция параметров, без ввода-вывода. Вне транзакции правка не атомарна: каждое изменение фиксируется отдельно. Так проект убирает из колокольчика то, что исправил или удалил в источнике: иначе прежние параметры видны до конца срока хранения (`REQ-NOTIFICATIONS-006`). Основание — заявка потребителя от 2026-11-13 (`CORE-ARC-029`).

## Колокольчик

4. <a id="REQ-NOTIFICATIONS-004"></a> **REQ-NOTIFICATIONS-004** — Точки под `/api/notifications` — только вошедшему и только о своих уведомлениях: число непрочитанного (`/unread`), последние **непрочитанные** свежими сверху вместе с числом — список панели колокольчика (по умолчанию 20, `platform.notifications.list-size`, не больше 50); прочитанное из панели уходит и видно на странице уведомлений (`REQ-NOTIFICATIONS-009`) — прочтение одного — повторное прочтение не ошибка, чужое — `notification-not-found`, — и прочтение всех. Правила доступа модуль объявляет `ModuleApiAccess` (`REQ-AUTH-022`).
5. <a id="REQ-NOTIFICATIONS-005"></a> **REQ-NOTIFICATIONS-005** — Клиент объявляет колокольчик один раз — `provideNotifications({ base, limit })` — и получает `NotificationBell`: сигналы `unread` и `items`, `open()` по щелчку, `read(id)` и `readAll()`. `items` — непрочитанные: `read(id)` убирает уведомление из списка и перечитывает число, `readAll()` список опустошает. `page(page, size, unread)` читает страницу уведомлений (`REQ-NOTIFICATIONS-009`) той же службой, поэтому прочтение на странице проекта уменьшает число в колокольчике. Панель «только непрочитанные» — решение владельца от 2026-09-28 по заявке потребителя: короткая панель показывает то, что ждёт человека, а полный перечень — страница. Число спрашивается при запуске и раз в минуту; без входа — ноль и пустой список. Вид колокольчика и текст по виду рисует проект. Доставка — опросом: SSE и WebSocket — позже, если понадобятся.
9. <a id="REQ-NOTIFICATIONS-009"></a> **REQ-NOTIFICATIONS-009** — Все свои уведомления, прочитанные и нет, читаются постранично: `GET /api/notifications/page?page=&size=&unread=` — свежими сверху, с числом всего (`total`), номером и размером страницы; `unread=true` — только непрочитанные. Номер — от 0, размер — от 1 до 50, по умолчанию `platform.notifications.list-size`; вне пределов — `notification-page-rejected`. Постраничность по номеру, а не курсором: страничному переключателю нужно число всего, а уведомлений у одного человека немного — они не старше срока хранения (`REQ-NOTIFICATIONS-006`). Основание — заявка потребителя от 2026-09-28: всё, что старше последних 50, человек прежде не видел никогда.

## Хранение

6. <a id="REQ-NOTIFICATIONS-006"></a> **REQ-NOTIFICATIONS-006** — Уведомление хранится 90 дней от создания; проект переопределяет срок `platform.notifications.keep` в обе стороны, но только положительным — бессрочного хранения нет. Стирание по сроку — явная команда `Notifications.purgeExpired()` из планировщика проекта; удаление по запросу субъекта по 152-ФЗ — `Notifications.erase(account)`.

## Модули ядра

7. <a id="REQ-NOTIFICATIONS-007"></a> **REQ-NOTIFICATIONS-007** — Модуль ядра звонит в колокольчик, когда проект подключил `platform-notifications`, и молчит без него: колокольчик — решение проекта, а модуль, требующий его всегда, навязал бы таблицу. Центр поддержки (`REQ-SUPPORT-015`) звонит автору с учётной записью — `support.answered`, и операторам — `support.arrived`.

## Доставка за пределы приложения

11. <a id="REQ-NOTIFICATIONS-011"></a> **REQ-NOTIFICATIONS-011** — Уведомления выходят за пределы приложения через каналы: модуль доставки объявляет бин `NotificationChannel` — имя канала и `deliver(DeliveryNotice)` — либо бин `NotificationChannels`, когда число каналов задают настройки, как у ботов Telegram. Имя — строчные латинские буквы, цифры и дефис, до 32 знаков, у каждого канала своё; неверное или повторённое имя останавливает запуск. Без канала поведение прежнее: очередь не пишется, команда отправки ничего не делает. Первый канал ядра — Telegram (`REQ-TELEGRAM-014`). Добавлено 2026-11-16, `CORE-ARC-031`.
12. <a id="REQ-NOTIFICATIONS-012"></a> **REQ-NOTIFICATIONS-012** — `notify` в одной транзакции с уведомлением ставит в очередь доставки строку на каждый канал — таблица `platform_notification_delivery` журнала ядра. Откат транзакции, в которой вызван `notify`, откатывает и доставку, а строку очереди отправка видит только после фиксации. Канал получает уведомление в его состоянии на момент отправки: правленое (`REQ-NOTIFICATIONS-010`) уходит правленым; убранное правкой, стёртое (`REQ-NOTIFICATIONS-006`) и удалённое вместе с учётной записью не уходит — строка очереди стирается вместе с уведомлением; прочитанное в колокольчике до отправки не уходит: человек его уже видел.
13. <a id="REQ-NOTIFICATIONS-013"></a> **REQ-NOTIFICATIONS-013** — Отправка — явная команда `NotificationDelivery.deliverPending()`: проект вызывает её из своего планировщика, ядро фоном не шлёт. За вызов команда берёт до `platform.notifications.delivery.batch` строк — по умолчанию 25, от 1 до 100 — и возвращает числа по исходам. Строки захватываются отдельной фиксацией, с блокировкой `SKIP LOCKED` и сроком захвата 5 минут: одновременные запуски, в том числе на разных экземплярах службы, и повторный запуск одну строку не шлют. Захват, не завершённый за срок, — служба упала посреди отправки — отправляется снова: в этом случае повтор возможен, а потеря — нет.
14. <a id="REQ-NOTIFICATIONS-014"></a> **REQ-NOTIFICATIONS-014** — Канал возвращает исход `Delivery`: `DELIVERED`, `SKIPPED` — отправлять некуда или нечего, `FAILED` — отправка невозможна, — и строка уходит из очереди; `RETRY` — следующая попытка через срок канала либо через 1, 2, 4… минуты, не больше часа, всего не больше 8 попыток, после чего строка уходит с записью в журнал службы; `LATER` — предел частоты получателя: попытка через срок канала и не засчитывается. Исключение канала — `RETRY`. Отказ отправки не откатывает работу проекта: она зафиксирована раньше. Журнал называет канал, вид уведомления, число попыток и класс исключения — без учётной записи, параметров и текста.

## Контракт

8. <a id="REQ-NOTIFICATIONS-008"></a> **REQ-NOTIFICATIONS-008** — Точки описаны контрактом `platform-notifications/src/main/resources/openapi/platform-notifications.openapi.json`, копия лежит в пакете клиента, типы клиента выводятся из него; тест держит контроллер в соответствии, а цена обновления сверяет контракт между версиями (`REQ-PUBLISHING-015`).
