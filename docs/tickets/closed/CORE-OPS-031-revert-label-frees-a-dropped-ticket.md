# Отменённая работа продолжает удерживать выпуск

## Проблема

`REQ-RELEASE-036` роняет закрытие, если в диапазоне есть коммиты задачи, снятой
из состава. Выход назван — отменить работу обратными коммитами. Но проверка
отмены не видит: после `git revert` коммиты снятой задачи остаются в
диапазоне, и закрытие продолжает их называть.

Выход из этого положения оставался ручным: либо вернуть задачу в состав, чего
владелец не хотел, либо переписать историю, что запрещено.

## Чем подтверждено

Записано непокрытым при закрытии `CORE-OPS-030` 2026-09-11: «отмена работы
обратными коммитами проверкой не отслеживается: после отмены коммиты снятой
задачи остаются в диапазоне, и закрытие будет их называть».

## Последствия при сохранении текущего поведения

1. Снять задачу из выпуска нельзя доведя дело до конца: отмена сделана, а
   выпуск всё равно не закрывается.
2. Единственным работающим выходом остаётся вернуть задачу в состав — то есть
   выпустить работу, которую решили не выпускать.

## Решение владельца от 2026-09-11

Отменяющий коммит несёт текстовую метку `!revert` сразу после идентификатора
задачи: `CORE-SEC-001 !revert ...`.

## Ожидаемый результат

Задача вне состава выпуска не роняет закрытие, если её работа в диапазоне
отменена. Метка отличает отменяющий коммит от обычного, и проверка это видит.

## Критерии приёмки

- Отменяющий коммит распознаётся по метке `!revert` сразу после идентификатора.
- Задача вне состава, чья работа в диапазоне заканчивается отменой, закрытие не
  роняет.
- Задача вне состава с работой после отмены роняет закрытие снова.
- Правило записано требованием и объявлено потребителям.

## Ход выполнения

### Шаг 1 (2026-09-11)

Отменяющий коммит распознаётся по метке `!revert` сразу после идентификатора
задачи. Проверка группирует коммиты диапазона по задачам и для задачи вне
состава смотрит её последний коммит: если он отменяющий, работа считается
отозванной и закрытие проходит.

Взят именно последний коммит задачи, а не счёт отмен: один обратный коммит
способен отменить три, и требовать отмену на каждый значило бы дробить откат
искусственно. Работа той же задачи после отмены роняет закрытие снова — отмена
относится к тому, что было до неё, а не выдаёт задаче постоянного пропуска.

Нормативный текст: `REQ-RELEASE-037`, плюс упоминание метки в
`REQ-PROJECT-PROCESS-023` рядом с правилом о начале сообщения. Обязательство
`commit-ticket-id` дополнено: снятие задачи сопровождается отменяющим коммитом
с меткой.

### Результаты проверок (2026-09-11)

| Прогон | Результат |
| --- | --- |
| `mise run check` | 121 документ, 288 положений, правила соблюдены, Java-сборка успешна |
| Тесты пакета правил | 147 из 147 (было 146) |

Новый тест проходит сценарий целиком: задача указана в выпуск, по ней сделана
работа, задача снята с причиной, работа отменена коммитом с меткой — закрытие
её больше не называет; затем по той же задаче сделан новый коммит — закрытие
называет её снова. Проверен на различающую силу: без учёта метки падает.

### Что не покрыто

Проверка читает сообщения, а не изменения: она утверждает, что отмена
объявлена, и не берётся судить, отменено ли содержимое. Коммит с меткой
`!revert`, ничего не отменяющий, проверку пройдёт — как и коммит с чужим
идентификатором в заголовке, о чём сказано в `CORE-OPS-030`.
