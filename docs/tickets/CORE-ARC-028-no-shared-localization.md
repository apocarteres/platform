# У ядра нет общей локализации

## Проблема

Оба потребителя ядра строят локализацию сами или её не имеют. В clanlog — свой
сервис `t(key)` с ленивыми словарями, ошибки сервера кодами, письма шаблоном
на язык и свои проверки ключей; zavpn хочет того же (заявка ZAVPN-IDEA-005 от
2026-10-23) и иначе скопирует реализацию clanlog. Письма входа ядро отдаёт
порту `AuthLetters` с локалью запроса, но правила выбора языка письма у
каждого потребителя свои.

## Последствия при сохранении текущего поведения

Две копии одной механики с разными ошибками и разными проверками; у нового
потребителя локализации нет из коробки.

## Ожидаемый результат

1. Клиентский пакет локализации: сервис `t(key)` (словарь языка → язык по
   умолчанию → ключ), словари по языкам загружаются отдельными кусками во
   время работы, выбор языка, `<html lang>`, сохранение выбора; текст кода
   ошибки API (`REQ-API`) — тем же сервисом.
2. Правило языка письма в ядре: язык учётной записи, затем язык запроса,
   затем язык по умолчанию проекта; `AuthLetters` получает выбранный язык.
3. Проверки в правилах проекта: одинаковый набор ключей у всех языков,
   у каждого кода ошибки есть текст, строк интерфейса вне словаря нет.
4. clanlog переходит на пакет ядра.

## Открытые вопросы

1. Где хранить язык учётной записи — в учётной записи ядра или в профиле
   проекта.

## Критерии приёмки

1. Потребитель включает локализацию пакетом ядра без своей реализации.
2. Проверка находит ключ, которого нет в одном из языков.
