# Вход не умеет второй шаг после пароля

## Проблема

`POST /api/auth/login` проверяет почту и пароль и сразу ставит контекст
безопасности в сессию (`AuthController.login`). Между проверкой пароля и
сессией нет точки расширения: проект не может потребовать второй фактор, не
выпустив сессию с ролями. Классы `AuthService` и `AuthController` закрыты,
подменить их проект не может; фильтр проекта после цепочки может только
отказывать уже выданной сессии, которая видна в `/api/auth/session`.

## Подтверждение

Потребитель ядра (заявка из аудита безопасности 2026-10-23) хочет второй
фактор TOTP для роли администратора; без правки ядра — только «шлюз после
входа» с уже выданной сессией администратора.

## Последствия при сохранении текущего поведения

Учётная запись с широкими правами защищена одним паролем; второй фактор
проекту недоступен.

## Ожидаемый результат

1. Порт `SecondFactor` (пакет `auth`): `required(Account)` — нужен ли второй
   шаг этой учётной записи, `verify(UUID account, String code)` — подходит ли
   код. Порт необязателен: без бина вход прежний.
2. Если порт требует второй шаг, `login` после верного пароля не ставит
   контекст безопасности: кладёт в сессию ожидающий вход (учётная запись и
   срок — 5 минут), меняет идентификатор сессии и отказывает кодом
   `second-factor-required` (401). Время входа и сброс счётчика неудач —
   только после второго шага.
3. `POST /api/auth/login/second-factor` `{code}` завершает вход: берёт
   ожидающий вход из сессии, проверяет код портом, неудачи считает тем же
   пределом неудач входа, что и пароль (`REQ-AUTH-012`), на успех ставит
   контекст как `login` и отдаёт `Me`. Без ожидающего входа или по истечении
   срока — отказ `second-factor-expired`; неверный код — `second-factor-rejected`.
4. Клиент `@apocarteres/auth`: `login` отклоняется кодом
   `second-factor-required`, `AuthSession.secondFactor(code)` завершает вход.
5. Контракт OpenAPI и `REQ-AUTH` описывают второй шаг.

## Критерии приёмки

1. Без бина `SecondFactor` поведение входа и контракт для потребителя не
   меняются.
2. С бином: после пароля `/api/auth/session` отдаёт пустую учётную запись,
   защищённые пути отвечают 401; после верного кода — вход выполнен.
3. Неверные коды упираются в предел неудач входа.
