# Развёртывание службы без простоя: второй экземпляр и переключение

## Проблема

Порядок развёртывания ядра — установка и проверка работоспособности
(`REQ-DEPLOYMENT-006`) — подразумевает перезапуск: всё время старта новой
версии служба недоступна. У потребителя это 21–22 с на обычном развёртывании
и 37 с с переходами базы. О развёртывании без простоя ядро не говорит ничего.

Потребитель перешёл на два экземпляра на одном хосте и переключение
веб-сервера: недоступность 0 с на 1285 запросах. Для этого пришлось решить
то, чего ядро не нормирует: переходы базы, годные обеим версиям сразу;
фоновые работы, которые в окне наложения шли бы дважды; сбор журналов и
метрик с двух экземпляров.

## Решение владельца

Решение владельца от 2026-09-24:

- Все пункты ниже приняты.
- Две версии одной службы вправе работать с одной схемой в окне наложения —
  разрешение по `REQ-COMPATIBILITY-005`. Разрешена только форма «расширить —
  сузить следующим выпуском», без кода совместимости в приложении.
- Временная совместимость не остаётся навсегда: каждый `expand` — долг со
  сроком, учитываемый как обязательство.

## Требуется

1. **Порядок развёртывания без простоя** в `deployment.md` — рекомендация,
   выбор проекта наряду с перезапуском. Инварианты для выбравшего:
   - новый экземпляр проверяется по своему адресу до переключения; не поднялся
     — переключения нет;
   - переключение атомарно, настройка веб-сервера проверяется до применения;
   - прежний экземпляр живёт заданное окно отката, откат — обратное
     переключение;
   - адрес активного экземпляра — состояние среды: установка настройки
     веб-сервера (`REQ-DEPLOYMENT-020`) его не перетирает;
   - порт нового экземпляра, занятый чужим процессом, — отказ развёртывания.
2. **Метки переходов базы** — директива для выбравших развёртывание без
   простоя. Каталог переходов и формат метки проект объявляет в
   `.conventions.json`; переход без метки — отказ `check`. Метки:
   - `additive` — чистое добавление, долга нет;
   - `expand` — старое оставлено ради прежней версии, открывает долг;
   - `contract: <переход>` — удаление старого, обязано назвать закрываемый
     `expand`;
   - `breaking` — несовместимо: развёртывание идёт порядком с простоем, и
     простой назван заранее.
3. **Срок долга `expand`** — 2 выпуска проекта по умолчанию; проект задаёт свой
   срок настройкой, от 1 выпуска, бессрочный не допускается. Выпуски
   считаются по тегам, как для обязательств ядра (`REQ-RELEASE-014`). Пока срок
   идёт, долг называется на каждой проверке; по истечении `check` краснеет и
   закрытие выпуска блокируется до парного `contract`.
4. **Положение о совместимости**: форма `expand`/`contract` записывается
   разрешённой рядом с `REQ-COMPATIBILITY-003/005`, чтобы потребитель не
   оформлял исключение сам.
5. **Замок фоновых работ** в `platform-persistence`: взятие одной условной
   записью со сроком (`REQ-PERSISTENCE-006`), второй экземпляр работу
   пропускает. Таблицу проект заводит в своих переходах по образцу ядра.
   Замок разрешает выполнить работу, а не запускает её: ядро по-прежнему не
   владеет планировщиком.
6. **Команды ядра об экземплярах**: `conventions health` уже проверяет любой
   адрес; `conventions deployed` сверяет артефакт активного экземпляра;
   `conventions manifest` записывает, какой экземпляр стал активным.

## Что сделано

- Положения `REQ-DEPLOYMENT-025` (порядок без простоя и его инварианты,
  раздел `deployment.withoutDowntime`), `REQ-DEPLOYMENT-026` (метки),
  `REQ-DEPLOYMENT-027` (срок долга `expand`), `REQ-DEPLOYMENT-028` (замок),
  `REQ-COMPATIBILITY-008` (разрешённая форма «расширить — сузить»).
- Правило `migration-labels`: переход без метки, с неизвестной меткой,
  `contract` без пары или к не-`expand`, `contract` раньше выпуска со своим
  `expand`.
- Долг `expand` считается по документам выпущенных выпусков: выпуск несёт
  переход, если файл есть в его коммите. Долг называется на каждой проверке, по
  истечении роняет `check` и держит закрытие выпуска. Ограничителем долг не
  фиксируется — засеянный он был бы бессрочным.
- `JdbcJobLock` в `platform-persistence`: SQL в каталоге
  `sql/platform-job-lock/`, образец таблицы `create-table.sql`, зависимость
  `spring-jdbc` необязательная. Автонастройки нет: замок строит сам проект, и
  условного бина на чужой бин не появляется (`REQ-QUALITY-012`).
- `conventions manifest --instance <имя>`; при объявленных экземплярах без
  ключа манифест не пишется. `health` уже проверял любой адрес, `deployed` —
  любой путь установки.
- `conventions migrations --unreleased` (`REQ-DEPLOYMENT-029`): переходы, которых
  нет ни в одном выпущенном выпуске, с метками и порядок `order=switch` или
  `order=downtime`. Добавлено при сверке с заявкой перед выпуском: без команды
  каждый скрипт разбирал бы метки сам. `deployed` не расширялась — путь
  установки экземпляра называет скрипт, сверка по пути уже есть.

## Чем закреплено

- Тесты меток и пар, долга по выпускам (выпуск до перехода и незавершённый
  выпуск в счёт не идут), закрытия выпуска и `check` с просроченным долгом,
  замка на встроенной H2, манифеста с экземпляром.
- Пробы намеренной поломкой: восемь по модулю переходов (две сначала не
  различали — добавлены выпуск до перехода и незавершённый выпуск), шесть по
  замку, по одной на подключение к закрытию и к `check` (подключение к `check`
  сначала не держалось ничем — добавлен тест командной строки).
