# Принятие цикла теряет номер выпуска и падает трассировкой

## Проблема

`conventions release adopt` в проекте со схемой номеров `semver` не может
завершиться успешно ни при каких аргументах.

Обработчик подкоманды `releaseAdopt(root)`
(`packages/project-conventions/bin/conventions.mjs:393`) не читает ни одного
ключа и вызывает `adoptCycle(root, { scheme, today })`. Библиотечная
`adoptCycle` (`lib/release/cycle.mjs:233`) номер принимает — параметр `version`
объявлен и передаётся в `openNext` — но CLI его не подставляет. Для схемы
`semver` номер обязателен: `nextReleaseId`
(`lib/release/documents.mjs:68`) бросает исключение при его отсутствии.

Исключение никем не перехвачено, поэтому команда завершается трассировкой
Node, а не названным отказом. Прочие отказы принятия цикла выводятся строкой
«Цикл выпусков не принят» с перечнем причин.

Ключ `--version` подкомандой `adopt` молча игнорируется: его читает только
`open` (`--version`), закрытие читает `--next-version`, а `adopt` — ничего.

## Чем подтверждено

Прогон 2026-09-10 на ядре 1.1.0, фикстурный проект с
`"release": { "scheme": "semver" }`.

```
$ conventions release adopt --root <проект>
Error: Для схемы semver нужен номер версии: --version X.Y.Z
    at nextReleaseId (lib/release/documents.mjs:68:25)
    at openNext (lib/release/cycle.mjs:253:31)
    at async adoptCycle (lib/release/cycle.mjs:243:18)
    at async releaseAdopt (bin/conventions.mjs:397:18)
```

Код возврата 1. Тот же результат с `--version 0.1.0`: ключ до библиотеки не
доходит.

Более тяжёлое следствие измерено отдельно. `adoptCycle` помечает закрытые
задачи значением `before-cycle` **до** открытия выпуска, поэтому падение
оставляет проект наполовину принятым. Фикстура с одной задачей `QUAL-001` в
статусе `done` и `release: unassigned`:

| После падения `adopt` | Значение |
| --- | --- |
| `release` у `QUAL-001` | `before-cycle` — запись сделана |
| `docs/releases/` | пусто — выпуск не открыт |
| Рабочее дерево | грязное, изменён документ задачи |

## Почему не поймано проверками

Проверка CLI принятия цикла (`test/cli.test.mjs:161`) задаёт фикстуре
`"release": {"scheme": "date"}`, где номер выводится из даты и ключ не нужен.
Проверки цикла (`test/release-cycle.test.mjs`) вызывают `adoptCycle`
напрямую, то есть на уровне библиотеки, где `version` можно передать
аргументом. Ни одна не проходит по пути CLI со схемой `semver`.

## Последствия при сохранении текущего поведения

1. Новый проект, нумерующий выпуски по semver — а по `REQ-RELEASE-004` так
   нумеруется всякий проект, у которого выпуск и версия артефактов одно
   событие, — цикл принять не может.
2. Отказ не называет ни причины, ни средства: потребитель разбирается по
   трассировке. Это тот же класс, что закрытая `DOC-001`.
3. Неудачное принятие оставляет репозиторий в состоянии, которого не должно
   существовать: задачи помечены как выпущенные до цикла, а цикла нет.
   Принятие выполняется один раз (`REQ-RELEASE-020`), поэтому цена
   неполного принятия выше цены обычной ошибки команды.

## Ожидаемый результат

1. `adopt` принимает номер первого выпуска тем же ключом, что и `open`.
2. Отсутствие обязательного номера — названный отказ с указанием ключа, а не
   трассировка; код возврата отличает отказ от аварии.
3. Неудачное принятие не оставляет изменений: пометки `before-cycle` без
   открытого выпуска не возникает.

## Критерии приёмки

- `release adopt` в проекте со схемой `semver` и явным номером открывает
  первый выпуск и завершается с кодом 0.
- `release adopt` без номера в таком проекте печатает названный отказ,
  трассировки не выводит.
- После отказа `adopt` рабочее дерево не изменено: ни одна задача не получила
  `before-cycle`.
- Все три случая закреплены проверками пакета на уровне CLI, а не только
  библиотеки.

## Ход выполнения

### Шаг 1 (2026-09-10)

Обработчик `releaseAdopt` читает `--version` и передаёт номер в `adoptCycle`;
подкоманда `adopt` в разборе аргументов получает тот же ключ, что и `open`.
Отсутствие обязательного ключа — ошибка вызова: названное сообщение и код
возврата 2, как у закрытия выпуска при отсутствии `--next-version`.

Защита от неполного принятия сделана не в CLI, а в библиотеке: `adoptCycle`
проверяет номер до того, как пометит задачи `before-cycle`, и возвращает отказ
перечнем причин. Та же проверка стоит в `openNext` до первой записи, поэтому
`release open` под semver тоже отказывает названно, а не трассировкой. Проверка
в CLI отвечает за код возврата, проверка в библиотеке — за то, что отказ ничего
не меняет; вторая переживёт правки первой.

Нормативный текст: `REQ-RELEASE-030` — принятие цикла и открытие выпуска
отказывают названно и при отказе не меняют ничего, а отсутствие обязательного
ключа отличимо кодом возврата от отказа по состоянию проекта.

### Результаты проверок (2026-09-10)

Исходный сценарий на фикстуре со схемой `semver` и одной задачей `done`:

| Вызов | До починки | После починки |
| --- | --- | --- |
| `release adopt` без ключа | трассировка Node, код 1, задача помечена `before-cycle` | `Схема semver: номер выпуска задаётся ключом --version X.Y.Z`, код 2, задача не тронута |
| `release adopt --version 0.1.0` | трассировка Node, код 1 | открыт `RELEASE-0-1-0`, задача помечена `before-cycle` |

| Прогон | Результат |
| --- | --- |
| `mise run check` | 105 документов, 269 положений, правила соблюдены, Java-сборка успешна |
| Тесты пакета | 128 из 128 (было 124) |

Каждый из четырёх новых тестов проверен на различающую силу: при откате
проводки ключа падают два теста CLI, при откате отказа в CLI — тест кода
возврата, при откате библиотечной проверки — тест неизменности состояния.

Достаточность проверок подтверждена по `REQ-TICKETS-015`: критерий про
неизменность рабочего дерева закреплён на двух уровнях, потому что тест CLI
проверяет его лишь пока в CLI стоит отказ, а гарантию даёт библиотека.

## Границы починки

Сведение имён ключей к одному в задачу не входило. Сейчас `open` читает `--version`, `close` —
`--next-version`, и это различие осмысленно: номер открываемого выпуска против
номера следующего. Задача принимает существующее имя `--version` для `adopt` и
имён не меняет; вопрос единого имени, если он нужен, ставится отдельно.
