# Задачи и выпуски проекта во внешнем хранилище по контракту ядра

## Проблема

Пакет правил читает и меняет задачи и выпуски только как файлы `docs/tickets`
и `docs/releases`: цикл выпуска, проверка коммитов и проверка документации
другого источника не знают. Проект, который ведёт работу в трекере, вынужден
держать задачу в двух системах — файлом и карточкой. Они расходятся, а деление
полей между ними людям непонятно: карточку на доске можно перетащить, а её
состояние записано в другом месте.

## Подтверждение

Точная ссылка на код, `project-conventions` 17.3.1:

- все чтения задач идут через `tickets(root)`, выпусков — через
  `releases(root)` в `lib/release/documents.mjs`: файлы `docs/tickets`,
  `closed/`, этапы планов, `docs/releases`;
- проверка коммитов ищет задачу через `git ls-tree` по `docs/tickets`
  (`ticketIdsAt`, `lib/release/commits.mjs`), а формат номера
  `ПРЕФИКС-ОБЛАСТЬ-NNN` зашит в выражение;
- команды цикла пишут документ выпуска, поле `release` в файлы задач и
  `.conventions/obligations.json` (`lib/release/cycle.mjs`,
  `lib/release/composition.mjs`).

Проект legacy-store переносит задачи в трекер; синхронизация «репозиторий →
трекер» затирает правки, сделанные на доске.

## Последствия при сохранении текущего поведения

Проект с трекером либо не может подключить цикл выпуска ядра, либо ведёт две
записи одной задачи и одного выпуска и сверяет их руками.

## Решение владельца

Решение владельца от 2026-11-10 — идея
[CORE-IDEA-003](../ideas/CORE-IDEA-003-external-ticket-store.md) принята:

- постановка задачи целиком живёт в хранилище;
- задачи и выпуски, включая закрытые, в репозитории не остаются;
- операции над выпуском исполняет хранилище — с доски и через API одинаково;
  шлагбаум закрытия и тег исполняет ядро, кнопка закрытия запускает ту же
  команду ядра в CI;
- команды остаются точкой входа и при внешнем хранилище вызывают его API.

Контракт, расчёт числа запросов и перечень модулей — в идее; здесь только
то, что требуется сделать. Переход проекта на хранилище — отдельная задача
[CORE-OPS-127](CORE-OPS-127-project-moves-to-external-store.md).

## Требуется

1. Хранилище задач и выпусков с двумя реализациями: файлы (по умолчанию,
   поведение не меняется) и внешнее по HTTP-контракту ядра. Выбор — `store` в
   `.conventions.json` с `url`, `readKeyEnv`, `writeKeyEnv`, `idPattern`.
2. Единая форма задачи и выпуска для обеих реализаций; команда получает
   рабочий набор и открытый выпуск один раз.
3. Чтения, не зависящие от длины истории: рабочий набор, поиск задач по
   номерам, открытый выпуск. Прошлый тег и коммиты прошлых выпусков — из
   тегов git.
4. Команды `release open`, `drop`, `cancel`, `mark`, `account`, `defer`,
   `satisfy` при внешнем хранилище — тонкие клиенты его операций без своих
   проверок.
5. Первый шаг закрытия, перезакрытие и завершающий шаг: заморозка выпуска на
   время закрытия, проверки ядра, тег с манифестом в аннотации, одна операция
   хранилища; повтор после сбоя воспроизводит операцию по манифесту либо
   снимает заморозку.
6. Порог открытых вопросов и материализация обязательств при внешнем
   хранилище выполняются не при открытии, а первой командой ядра и закрытием.
7. Учёт обязательств при внешнем хранилище — данные хранилища;
   `.conventions/obligations.json` не используется.
8. Проверка коммитов берёт формат номера из `idPattern`, существование — из
   поиска по номерам, названным коммитами; найденные номера запоминает, без
   сети предупреждает о неизвестном номере, с ключом `--strict` отказывает.
9. Проверка документации при внешнем хранилище к нему не обращается, сводок
   задач и выпусков не требует и отвергает файл задачи или выпуска в
   репозитории.
10. Команда `store --check` прогоняет сценарии цикла на хранилище проекта:
    формы ответов, операции, их повтор, инварианты с кодами отказов.
11. `tickets-index`, `releases-index`, `tickets-renumber`, `naming-migration`
    и `release adopt` при внешнем хранилище отказывают с названием причины.
12. Требования переписываются с файлов на хранилище и получают пункты о
    контракте и разделении исполнения: `REQ-PROJECT-PROCESS-013`, `-023`,
    `REQ-TICKETS-005`, `-009`, `-013`, `-022`, `REQ-RELEASE-001`, `-007`,
    `-013`, `-015`, `-031`, `-033`, `-035`, `-040`, `-047`.
13. Определения полей проекта типа `ticket` публикуются в хранилище, когда
    его отпечаток расходится с `.conventions.json`.

## Критерии приёмки

- Проект без `store` проходит прежние сценарии цикла без изменений в
  поведении и в документах.
- Один набор сценариев цикла (`open`, `close`, `finish`, `reclose`, `drop`,
  `cancel`, `mark`, `account`, `defer`, `satisfy`) проходит на обеих
  реализациях; внешняя — на поддельном хранилище по контракту внутри теста.
- Ни одна команда не запрашивает у хранилища все задачи или все выпуски
  проекта: число и размер запросов не зависят от числа закрытых. Тест
  прогоняет цикл на хранилище с большой историей и сверяет запросы.
- Выпуск, открытый операцией хранилища без команды ядра, закрывается тем же
  путём, что и открытый командой: задачи обязательств заведены, порог
  вопросов проверен.
- Сбой операции хранилища после поставленного тега: повтор команды доводит
  запись по манифесту тега и не ставит второго тега.
- Отказ проверки после заморозки снимает заморозку; сбой команды между
  заморозкой и тегом повтор команды разбирает сам, без ручных действий.
- Операция над выпуском, пришедшая в хранилище во время закрытия, отказывает
  и состава не меняет: тест шлёт её между заморозкой и тегом.
- Отказ хранилища по инварианту доходит до человека кодом и текстом
  хранилища; команда своей проверки поверх не добавляет.
- `docs-check` при внешнем хранилище не обращается к сети.
- `commits` без сети: известный номер проходит, неизвестный даёт
  предупреждение, с `--strict` — отказ.
- Ключ не появляется ни в выводе команд, ни в аргументах процессов.
- Версия контракта, которой хранилище не исполняет, даёт отказ с названием
  требуемой версии.
- `mise run verify` зелёный.

## Вне задачи

Реализация контракта на стороне трекера, перенос истории legacy-store и запуск
команды закрытия по кнопке — работа этих проектов.
