# Клиентский пакет отбрасывает поля расширения

## Проблема

`REQ-API-007` дал сервису порт `ErrorExtensions`: свои поля кладутся в тело
ошибки рядом с `code`. Клиентская половина контракта осталась прежней:
`problemDetailOf` в `@apocarteres/http` собирает объект из шести полей —
`type`, `title`, `status`, `detail`, `instance`, `code`, — а остальные ключи
тела не читает вовсе. Интерфейс `ProblemDetail` в типах пакета их тоже не
называет.

Ядро выпустило половину контракта: сервер поля отдаёт, клиент их теряет.

## Чем подтверждено

Заявка потребителя [issue #3](https://github.com/apocarteres/platform/issues/3),
ядро 1.7.0, задача потребителя `CL-API-004`. Замер по собранному пакету
`fesm2022/apocarteres-http.mjs`: перечень читаемых ключей закрыт. Ответ на отказ
списания со склада несёт три собственных поля, и после перехода на контракт они
переставали доходить до диалога.

Потребитель держит собственный перехватчик, который разбирает тело раньше
`sanitisingInterceptor`, — тот самый локальный обход, которого обязательство
`web-errors` стремится не оставлять.

## Последствия при сохранении текущего поведения

Каждый сервис, объявивший порт расширений, обязан завести на клиенте свой
разбор тела. Разбор контракта перестаёт быть один и переезжает к потребителям —
ровно то, против чего введён `REQ-API-001`.

## Ожидаемый результат

Поля расширения доходят до клиента средствами пакета: `ProblemDetail` несёт их
отдельным полем `extensions`, обязательные поля RFC 9457 остаются на своих
местах. Отдельное поле предпочтительнее свободных ключей: оно не заставляет
потребителя гадать, какое имя занято контрактом.

## Критерии приёмки

- `problemDetailOf` сохраняет ключи тела, не входящие в обязательный состав, и
  отдаёт их отдельным полем.
- `ApiFailure` даёт доступ к расширениям без разбора тела руками.
- Правило `REQ-API` называет клиентскую половину расширений.
- Тест закрепляет: тело с собственным полем доходит до обработчика.

## Откуда пришла задача

Заявка потребителя [issue #3](https://github.com/apocarteres/platform/issues/3):
серверная половина `CORE-API-004` вышла в 1.7.0, клиентская отсутствует.

## Что сделано

`ProblemDetail` несёт поле `extensions` — всё, что не входит в обязательный
состав RFC 9457 и расширение `code`. Поле есть всегда: при теле без собственных
полей оно пусто, поэтому приложению не нужна проверка на его отсутствие.
`ApiFailure.extensions` даёт к нему доступ прямо из отказа.

Отдельное поле выбрано вместо свободных ключей рядом с обязательными: иначе
приложение обязано знать, какие имена уже заняты контрактом, и это знание
расходится при каждом расширении RFC 9457. Предпочтение потребителя совпало с
этим доводом.

`REQ-API-007` теперь называет обе половины контракта: серверную — порт, и
клиентскую — разбор. Обязательство `web-errors` называет `ApiFailure.extensions`
как замену собственному разбору тела.

Закреплено тремя тестами: разбор тела с тремя собственными полями, пустые
расширения у тела без них и прогон через собранный конвейер перехватчиков, где
поля доходят до обработчика.
