# Пакет процессных правил и инструментов документации

## Цель

Опубликовать npm-пакет `@apocarteres/project-conventions`: CLI с проверками документации и генераторами сводок плюс тексты правил (`RULES.md` задач и выпусков, `TEMPLATE.md`, общий фрагмент `AGENTS.md`, единый документ требований к UI). Оба проекта и сам репозиторий `platform` становятся его потребителями.

## Основание

1. В zavpn и clanlog одна идея правил реализована двумя несовместимыми форматами и двумя наборами скриптов: 1274 строки Node с тестами против 730 строк Python и Node без тестов ([ADR-0001](../../decisions/ADR-0001-shared-core.md), раздел 2.3).
2. Требования к модалкам были скопированы из clanlog в zavpn и разошлись: из общего текста осталось четыре совпадающие строки.
3. Инструментарий в этом репозитории был перенесён из zavpn (`scripts/docs`) с двумя правками: терпимость к отсутствующим каталогам и обязательный раздел «Почему не делаем» у отменённой задачи. Копия жила до шага 2 этой задачи, где переехала в пакет.

## Последствия при сохранении текущего поведения

Каждое улучшение правил делается дважды и проверяется по-разному; расхождения обнаруживаются только при чтении глазами.

## Требуется

1. Параметризовать `check-docs.mjs`: перечень обязательных целей каталога, имена индексных файлов и расположение задач читаются из конфигурации проекта, а не из констант.
2. Оформить CLI с командами `check`, `tickets-index`, `releases-index`, `file-sizes`, `toolchain-pins`, `money-types`, `config-secrets` (последние четыре переносятся из `clanlog/scripts/ops`) и `sync`.
3. Команда `sync` вписывает тексты правил в проект между маркерами `<!-- conventions:begin -->` и `<!-- conventions:end -->`; `check` отказывает при ручной правке внутри маркеров и при отставании версии пакета.

## Критерии приёмки

- [x] `mise run docs-check` в платформе и в потребителе вызывает CLI пакета одной и той же закреплённой версии — `.platform-version` и `platform-bom` сверяются при установке
- [x] Тесты инструментов живут в пакете и выполняются наборами `check` и `verify` — 90 тестов; CI исключён решением [ADR-0003](../../decisions/ADR-0003-local-artifact-publishing.md)
- [x] Ручная правка внутри маркеров приводит к отказу `check` — проверено тестом `cli.test.mjs`
- [x] CLI содержит все команды из пункта 2 требований, включая четыре перенесённые проверки
- [x] Общие правила каталогов перенесены в ядро: `REQ-TICKETS` и `REQ-RELEASE-022`…`REQ-RELEASE-025`

## Границы

Правило о комментариях и минимальный CLI (`check`, `sync`, `baseline`) выделены в [OPS-002](OPS-002-code-comments-rule.md) и выполнены. Миграция формата задач clanlog вынесена в [отдельную задачу](DOC-003-clanlog-ticket-format-migration.md) по решению владельца от 2026-09-07: она ждёт его слова о переводе clanlog, а остальная работа от неё не зависит. Здесь остаётся перенос остальных общих правил, полный CLI и переносимые храповики. Reusable workflow исключён решением [ADR-0003](../../decisions/ADR-0003-local-artifact-publishing.md): GitHub Actions не используются.

## Открытые вопросы

Работа по зависимым пунктам не начинается, пока вопросы не сняты. Ответ записывается рядом с вопросом с датой.

1. Имя индексного файла каталога: `README.md` (zavpn, унаследовано сюда) или `INDEX.md` (clanlog, правило «`README.md` в роли индекса запрещён»). Рекомендация: `INDEX.md`, поскольку `README.md` в GitHub отображается как описание каталога и смешивает роли. Зависит: пункт 1 требований. **Ответ 2026-09-07: `INDEX.md` везде.** Переименование выполняется в ядре и в zavpn, включая сводки задач; `README.md` остаётся только там, где документ описывает каталог, а не перечисляет его содержимое.
2. Нужен ли в сводке задач разрез по областям, заменяющий каталоги clanlog, или достаточно колонки «Области». Зависит: пункт 2. **Ответ 2026-09-07: достаточно колонки «Области».** Группировка не вводится: задача с тремя областями появлялась бы в сводке трижды.
3. Приоритет при противоречии общего фрагмента `AGENTS.md` и проектной части. Рекомендация: общий фрагмент задаёт минимум; проект может ужесточить правило снаружи маркеров, но не ослабить. Зависит: пункт 3 требований. **Ответ 2026-09-06: правила наследуются.** Решение владельца: правило платформы и правило проекта соблюдаются оба, проект ужесточает и не ослабляет. Записано нормативно в [правилах проекта поверх правил платформы](../../requirements/project-rules.md).
4. Состав общего фрагмента `AGENTS.md`. Зависит: пункт 3 требований. **Ответ 2026-09-07: фрагмент содержит только ссылку.** Решение владельца: к потребителям попадают ссылки, а не содержимое. Построчное разделение не потребовалось: общие правила переехали в требования ядра, фрагмент сократился до четырёх строк с путём к доставленным текстам, а проектные ссылки живут снаружи маркеров. Записано нормативно в [доставке нормативных текстов](../../requirements/rule-distribution.md).

## Ход выполнения

### Шаг 1 (2026-09-07)

Вопросы сняты ответами владельца, работа по зависимым пунктам разблокирована. Миграция формата задач clanlog вынесена отдельной задачей и ждёт решения о переводе clanlog.

Имя индексного файла закреплено нормативно: `REQ-PROJECT-PROCESS-021` требует `INDEX.md` и запрещает `README.md` в роли индекса, `REQ-PROJECT-PROCESS-022` требует полноты индекса и запрещает править генерируемые вручную.

В ядре переименованы шесть индексов: `docs/README.md`, `docs/decisions/README.md`, `docs/runbooks/README.md` и три сводки задач `SUMMARY.md`. Проверки и генераторы знают новое имя, тесты инструментов обновлены, ссылки во всех документах исправлены. Каталог выпусков уже назывался `INDEX.md` и не тронут.

### Шаг 2 (2026-09-07)

Инструменты документации переехали из копии в пакет: `check-docs`, `tickets-index`, `releases-index` и модели задач и выпусков теперь живут в `packages/project-conventions/lib/docs`, их тесты — в тестах пакета. Своего каталога `scripts/docs` в ядре больше нет.

Проверка параметризована так, как требовал пункт 1, но по факту потребовалось одно отличие вместо трёх: перечень обязательных целей каталога документации читается из `.conventions.json` полем `docs.requiredCatalogTargets` и добавляется к общему набору. Имена индексных файлов параметризовать не пришлось — они закреплены нормативно как `INDEX.md`; расположение задач тоже задано правилом, а не конфигурацией.

CLI получил три команды: `docs-check`, `tickets-index`, `releases-index`. Отдельно от `check`, а не внутри него, потому что вопросы разные: `docs-check` спрашивает, согласована ли документация, `check` — соблюдены ли правила кода. В ядре обе вызываются задачами менеджера окружения, в CI — напрямую.

Тестов в пакете стало 58.

### Шаг 3 (2026-09-07)

Решение владельца от 2026-09-07 убрало из задачи reusable workflow: GitHub остаётся хранилищем репозитория, проверки и публикация выполняются локально. Основание и цена решения записаны в [ADR-0003](../../decisions/ADR-0003-local-artifact-publishing.md).

Публикация ядра переведена на локальную: `mise run install-local` ставит Java-артефакты в локальный репозиторий Maven и собирает архив npm-пакета в `target/local-packages`. Версия по-прежнему берётся из тега, `-SNAPSHOT` отклоняется профилем release. Из `pom.xml`, `platform-bom/pom.xml` и `package.json` убраны адреса registry, workflow удалены.

Требование о registry заменено: `REQ-PUBLISHING-007` описывает локальную публикацию, `REQ-PUBLISHING-010` — как потребитель фиксирует версию ядра и получает артефакты. Инструкция `github-packages.md` переписана в `local-publishing.md`.

### Шаг 4 (2026-09-07)

Требование владельца от 2026-09-07: всё, что касается сборки, проверок качества и развёртывания, фиксируется на уровне платформы. Появились три нормативных документа, доставляемых пакетом:

- [Сборка](../../requirements/build.md) — сборка локальна и не требует секретов, инструменты закреплены и одинаковы на всех машинах, особенности машины живут в локальном файле настроек, отсутствующий инструмент запускается контейнером с явной версией, версия ядра закрепляется файлом, задачи с общим каталогом сборки не идут параллельно.
- [Проверки качества](../../requirements/quality-checks.md) — два набора с фиксированными именами `check` и `verify`, шлагбаум хуком `pre-push`, отказ называет файл и место, порог не снижается, храповик только убывает, код возврата читается напрямую, неустойчивый тест — дефект с задачей, утверждение о времени выражается через состояние, обратный опыт обязателен.
- [Развёртывание](../../requirements/deployment.md) — развёртывается коммит и собирается на месте теми же задачами, ревизия записывается манифестом, предпосылки проверяются до изменений на стенде, резервная копия до установки, проверка работоспособности после, подготовка данных явными идемпотентными шагами, развёртывается коммит с пройденным `verify`.

Ядро приведено в соответствие со своими же правилами: версии инструментов закреплены (`java = 21`, `node = 22.22.3`, `npm = 10.9.4`), задачи переименованы в `check` и `verify`, добавлен `install-hooks` с хуком `pre-push`, составные задачи выполняются последовательно.

Закреплением версий снят открытый вопрос 1 из [ADR-0001](../../decisions/ADR-0001-shared-core.md): потребители выравниваются по версиям, а не ядро собирается под каждую.

Доставляемых пакетом документов стало 14.

### Шаг 5 (2026-09-07)

Решение владельца от 2026-09-07: цикл выпуска детерминированный, одной командой, с автоматическим переносом обязательств ядра в следующий выпуск. Ответы на три вопроса о форме: номер выпуска сервиса — год, месяц и порядковый номер (`RELEASE-2026-09-1`, тег `2026.09.1`), у ядра номер равен версии артефактов; состав выпуска — запись сделанного, а не план; у обязательства есть срок в выпусках, до его истечения возможен перенос записью с причиной.

Механика собрана в пакете: `lib/release` из четырёх модулей — обязательства, расписка о проверках, документы выпусков, сам цикл. CLI получил команды `receipt`, `obligations` и `release status|close|open|defer`. Правило о непустом составе ослаблено ровно для черновика: свежеоткрытый выпуск законно пуст, потому что состав наполняется по факту закрытия задач.

Ядро объявляет три обязательства: наборы проверок `check` и `verify` со шлагбаумом, цикл выпуска, сведение храповика комментариев к нулю. Первые два со сроком в один выпуск, третье — в шесть. Себе ядро обязательств не должно: перечень объявлен здесь, и проверка это учитывает.

Правила ядра поймали мой же новый код дважды, и оба раза правкой по существу: пояснительные комментарии заменены ссылками на положения, а `new Date()` вынесен в единственный файл `lib/now.mjs`, который и попал в `clockAllowlist` — тот же приём, что я потребовал от потребителя.

Тестов в пакете стало 64: шесть новых на нумерацию, срок обязательства, материализацию задачи без повторов, отказ закрытия без расписки и при грязном дереве, запись состава и результата при закрытии.

Открыт первый выпуск ядра `RELEASE-0-19-0`.

### Шаг 6 (2026-09-07)

Цикл проверен на себе и на сервисе. Ядро прошло через него трижды: `0.19.0` — сам цикл, `0.20.0` — принятие цикла репозиторием с историей, `0.21.0` и `0.22.0` — дефекты, найденные принятием в zavpn. Каждый выпуск закрыт командой `mise run release <версия>`: расписка о `verify`, тег на проверенном коммите, локальная публикация артефактов из тега, открытие следующего выпуска.

Работа на настоящих данных нашла шесть дефектов, которых не было видно на тестовом проекте:

1. Закрытие считало имя тега, печатало его и не создавало. Ни один тест не проверял тег. Теперь закрытие сначала считает все правки, затем ставит тег, затем пишет: отказ на подготовке не оставляет ни тега, ни половины документов.
2. Закрытый выпуск оставлял неотмеченные критерии выхода, а проверка документации требует подтверждения у выпущенного документа. Критерии заполняются из расписки, тега и состояния обязательств. Критерий про развёртывание из документа убран: развёртывание происходит после закрытия, подтвердить его на закрытии невозможно.
3. Первый выпуск сервиса с историей объявлял своим составом всё, что закрывалось когда-либо: в zavpn — 92 задачи, давно развёрнутые в проде. Появилось однократное принятие цикла и значение `before-cycle`.
4. Состав собирался только из задач без выпуска, поэтому запланированное обязательство в состав не попадало и оставалось открытым после выполнения.
5. Закрытие обязательства ссылкой на уже сделанную работу оставляло задачу-заготовку в бэклоге и её строку в составе.
6. Проверка документации не знала о собственных данных цикла: поле `obligation`, `before-cycle`, переезд задачи в `closed/` и ссылку на нормативный документ, доставленный пакетом.

Тестов в пакете стало 70. Дефект 4 закрыт с обратным опытом: без выбора состава по «без выпуска либо этот выпуск» падает ровно один тест из 67.

Сервис zavpn принял цикл на ядре `0.22.0`: схема номеров по дате, расписка в конце `verify`, задача `release`, шлагбаум тега в развёртывании прода с проверкой тега на самом прод-хосте и журналом развёртывания. Из трёх обязательств ядра одно закрыто ссылкой на выполненную работу, одно — этой работой, у третьего остаётся срок в шесть выпусков.

[REQ-ADOPTION](../../requirements/adoption.md), а `README.md` пакета переписан из
заглушки в точку входа с командами. Проверено измерением на пустом проекте:
записанный порядок был невыполним — `release adopt` и `docs-check` падали
трассировкой Node на отсутствующих каталогах.

Последний пункт задачи закрыт переносом каталожных правил в ядро:
`docs/tickets/RULES.md` стал нормативным [документом задачи](../../requirements/tickets.md)
(`REQ-TICKETS`, 16 положений), `docs/releases/RULES.md` и `TEMPLATE.md`
растворились в цикле выпуска (`REQ-RELEASE-022`…`REQ-RELEASE-025`). Генераторы
сводок больше не ссылаются на каталожные файлы правил, а называют положение.
Ссылки закрытых выпусков отремонтированы по новому положению
`REQ-RELEASE-026`: ремонт навигации записью о выпуске не является.

Новому потребителю остаётся создать два своих документа вместо семи:
входную сводку и карту требований проекта. Измерено на пустом репозитории:

Доставляемых пакетом документов стало 17.

### Шаг 8 (2026-09-07)

Перенесены четыре последние проверки из `clanlog/scripts/ops`: размер файла,
согласованность закреплённых версий, денежные типы, литеральные секреты в
конфигурации. Нормативные тексты — `REQ-CODE-DESIGN-008`…`REQ-CODE-DESIGN-010`,
`REQ-CONFIG` и `REQ-BUILD-010`. Правило размера считает строки сверх предела,
поэтому общий храповик ядра заменил отдельный файл базового уровня целиком:
один храповик, одна команда записи, одно объяснение в разборе изменений.
Согласованность версий храповиком не покрывается — расхождение версий не долг,
а сломанный инвариант.

Подключение проверок в zavpn нашло два дефекта: правило размера считало
наборы тестов на Python рабочим кодом (исправлено выпуском 0.28.0), а шлагбаум
перед отправкой поймал неустойчивый тест прокси агента — его причина
установлена измерением и записана
[отдельной задачей потребителя](https://github.com/apocarteres/zavpn).

Скрипты остаются в clanlog до его перевода на ядро: перевод ведётся
[отдельной задачей](DOC-003-clanlog-ticket-format-migration.md) и ждёт слова владельца.

Задача закрыта: пакет содержит все запланированные проверки, инструменты
документации, цикл выпуска, правила подключения и доставляет 17 нормативных
документов.
