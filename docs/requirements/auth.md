# Аутентификация ядра: учётная запись, сессия, роли проекта

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: служба на Spring Boot и её одностраничный клиент.** Аутентификацию ядро поставляет библиотекой: starter `platform-auth`, ограничитель частоты `platform-rate-limit` и пакет клиента `@apocarteres/auth`. У каждого продукта свои пользователи, механика одна; единой аутентификации на все продукты ядро не даёт. Решение владельца от 2026-09-24, основание — два потребителя, написавших аутентификацию сами почти одинаково и с расхождениями там, где расходиться не должно (`CORE-ARC-013`).

**Уровень требования: директива.**

## Учётная запись и роли

1. <a id="REQ-AUTH-001"></a> **REQ-AUTH-001** — Учётная запись принадлежит ядру: ключ UUID, почта, хеш пароля, признаки подтверждения и блокировки, роли, время создания и последнего входа. Почта хранится приведённой к нижнему регистру, без пробелов по краям, и уникальна. Доменный профиль проекта — игрок, клиент — хранит свой ключ и ссылается на учётную запись; поля предметной области в учётную запись не попадают. Таблицы проект заводит своими переходами по образцу `sql/platform-auth/create-*.sql`. Текущую учётную запись код проекта получает из `CurrentAccount.id()`. Запросы проекта вправе соединять свои таблицы с `platform_account` по ключу для чтения; пишет в таблицы ядра только его API — иначе правило пароля и приведение почты живут во второй копии. Внешний ключ профиля на учётную запись — выбор проекта: `ON DELETE CASCADE`, если профиль стирается вместе с неподтверждённой записью, `ON DELETE RESTRICT`, если профиль держит то, что стирать нельзя (деньги) — такую запись очистка пропускает (`REQ-AUTH-013`).
2. <a id="REQ-AUTH-002"></a> **REQ-AUTH-002** — Роли объявляет проект настройкой `platform.auth.roles`, роли новой учётной записи — `platform.auth.default-roles`; обе обязательны. Роль — прописные латинские буквы, цифры и подчёркивание. У учётной записи набор ролей. Назначенная роль действует со следующего входа; отзыв роли завершает все сессии учётной записи — отозванное право не живёт до конца сессии. Роль, не объявленная проектом, не назначается.

## Регистрация и подтверждение

3. <a id="REQ-AUTH-003"></a> **REQ-AUTH-003** — Регистрация, вход и запрос сброса не раскрывают, есть ли такая почта: повторная регистрация и запрос для неизвестной почты отвечают так же, как успешные, и писем не шлют; вход с неизвестной почтой и с неверным паролем отвечает одним кодом `credentials-rejected`, и сравнение хеша выполняется в обоих случаях. Проверку «человек ли это» проект объявляет портом `HumanCheck` — отказ от неё только явной заглушкой `HumanCheck.NOT_REQUIRED`; непройденная проверка — отказ `human-check-failed` до всякой работы. Действие проекта при создании учётной записи — порт `RegistrationHook<P>`, явная заглушка `RegistrationHook.NONE` — выполняется в той же транзакции и получает профиль классом проекта (`REQ-AUTH-021`): отказ проекта откатывает создание. Учётная запись создаётся одним путём — при регистрации, из `Accounts.create` и для первого администратора, — и хук вызывается всегда: иначе запись без профиля ломает экраны, которые его ждут.
4. <a id="REQ-AUTH-004"></a> **REQ-AUTH-004** — Почта подтверждается ссылкой с одноразовым токеном; срок — 24 часа, проект задаёт свой. В базе хранится отпечаток токена, а не токен; действует последний выданный — выдача нового гасит прежние. Повторное письмо — не чаще раза в минуту на учётную запись; для подтверждённой и неизвестной почты — ответ тот же, писем нет.

## Вход и сессия

5. <a id="REQ-AUTH-005"></a> **REQ-AUTH-005** — Вход — почта и пароль. Отказ заблокированной учётной записи `account-blocked` и неподтверждённой `email-unverified` звучит только после верного пароля: пароль доказывает владение, и раскрывать состояние чужой записи незачем. Удачный вход меняет идентификатор сессии, записывает время входа и сбрасывает счёт неудачных попыток.
6. <a id="REQ-AUTH-006"></a> **REQ-AUTH-006** — Пароль сбрасывается ссылкой с одноразовым токеном; срок — 30 минут, проект задаёт свой. Токен гасится вместе с записью нового пароля в одной транзакции; после сброса все сессии учётной записи завершаются.
7. <a id="REQ-AUTH-007"></a> **REQ-AUTH-007** — Пароль — от 10 до 72 байт в UTF-8; проект задаёт свои пределы, верхний не больше 72: дальше BCrypt молча обрезает пароль, и хвост перестаёт что-либо значить. Хеш — BCrypt; хеши BCrypt, записанные проектом до ядра, принимаются как есть.
8. <a id="REQ-AUTH-008"></a> **REQ-AUTH-008** — Сессия хранится в Redis; срок бездействия — 8 часов, проект задаёт свой. Индекс сессий по учётной записи ведётся её идентификатором: почты в хранилище сессий нет. Cookie `SESSION` — `HttpOnly`, `SameSite=Lax`, `Secure` (отключается настройкой только для разработки). Изменяющие запросы требуют токена CSRF: cookie `XSRF-TOKEN` и заголовок `X-XSRF-TOKEN`; токен выдаёт `GET /api/auth/csrf` до первого изменяющего запроса. Отказы входа — ошибкой ядра: `authentication-required`, `access-denied`, `csrf-rejected`.
9. <a id="REQ-AUTH-009"></a> **REQ-AUTH-009** — Экраны администратора проект строит на Java API `Accounts`: поиск по части почты постранично и счёт найденного, создание учётной записи с паролем, ролями, признаком подтверждения и профилем, назначение пароля, блокировка и разблокировка, назначение и отзыв роли. Созданная запись проходит правило пароля и приведение почты ядра; назначение пароля и блокировка завершают все сессии учётной записи. Первого администратора объявляют настройки `platform.auth.admin.email`, `.password`, `.roles` и профиль `.profile.*` из окружения: при старте ядро создаёт подтверждённую учётную запись тем же путём, что и регистрацию, если её нет, и не трогает существующую.
10. <a id="REQ-AUTH-010"></a> **REQ-AUTH-010** — Письма входа проект поставляет портом `AuthLetters`: у ядра нет бренда, текста и перевода. Писем четыре вида: подтверждение почты, сброс пароля, подтверждение новой почты и извещение прежней (`REQ-AUTH-023`). Письмо уходит после фиксации транзакции: откатившаяся регистрация писем не шлёт. Ссылка строится от доверенного адреса `platform.auth.link-base` — `https`, `http` только для `localhost` — а не от заголовков запроса.

## Ограничение частоты

11. <a id="REQ-AUTH-011"></a> **REQ-AUTH-011** — Ограничитель частоты — модуль `platform-rate-limit`: действие, окно, предел. Счётчик живёт окно с первого обращения и не продлевается каждым. Субъект — адрес сети, почта или их пара — хранится в Redis отпечатком. Превышение — ошибка ядра `rate-limited`, `429` и `Retry-After`; недоступное хранилище — отказ `rate-limit-unavailable`, `503`: действие отклоняется, а не пропускается. Проект пользуется ограничителем и вне входа. Адрес сети берётся из запроса: за обратным прокси без `server.forward-headers-strategy` им будет адрес прокси, и пределы «с адреса» поделятся на всех пользователей.
12. <a id="REQ-AUTH-012"></a> **REQ-AUTH-012** — Пределы точек входа: вход — 50 за 15 минут с адреса сети и 10 неудачных за 15 минут на почту, удачный вход неудачи сбрасывает; регистрация — 10 в час с адреса; повторное письмо — 3 в час на почту; запрос сброса — 30 в час с адреса и 3 в час на почту; погашение токенов — 20 за 5 минут с адреса.

## Персональные данные

13. <a id="REQ-AUTH-013"></a> **REQ-AUTH-013** — Почта, адрес сети и хеш пароля — персональные данные (152-ФЗ): в журналы, метки метрик и ответы об ошибках они не попадают. Токены и субъекты ограничителя хранятся отпечатком. Отработавшие и просроченные токены стираются командой `Accounts.purgeTokens(срок)`, неподтверждённые учётные записи — `Accounts.purgeUnverified(срок)`: по одной записи, и запись, которую держит внешний ключ проекта, пропускается и считается — итог «стёрто, удержано», а одна удержанная запись очистку не останавливает; вызывает их планировщик проекта, ядро фоновую работу само не запускает. Оператором персональных данных остаётся проект.

## Доступ к API проекта

14. <a id="REQ-AUTH-014"></a> **REQ-AUTH-014** — Цепочка безопасности ядра обслуживает `/api/**`. Правила доступа к своим путям проект объявляет портом `ApiAccess` — роль администратора, открытые пути; явная заглушка `ApiAccess.AUTHENTICATED` оставляет всё под входом. Прочие виды доступа проекта — токены API, вход агентов — объявляются собственными цепочками с более ранним порядком и своими путями.

22. <a id="REQ-AUTH-022"></a> **REQ-AUTH-022** — Модуль ядра со своими точками под `/api/**` объявляет правила доступа к ним бином `ModuleApiAccess`, а не своей цепочкой: цепочка безопасности одна, и CSRF, сессия и ответы об отказе у модуля те же. Правила модулей применяются после правил аутентификации ядра и раньше правил проекта: проект не может закрыть открытую точку модуля своим шаблоном пути — для этого у модуля есть собственный порт с явным решением, как `GuestIntake` у центра поддержки (`REQ-SUPPORT`). Проект `ModuleApiAccess` не объявляет: его путь — `ApiAccess`. Добавлено 2026-09-25 для центра поддержки.

## Клиент

15. <a id="REQ-AUTH-015"></a> **REQ-AUTH-015** — Клиент объявляет вход один раз — `provideAuth()` из пакета `@apocarteres/auth` — и подключает `authInterceptor`. Пакет — логика без вида: служба `AuthSession` знает, кто вошёл (`account()`: неизвестно, не вошёл или учётная запись), выполняет вход, выход, регистрацию, подтверждение и сброс, берёт токен CSRF при запуске и после входа и выхода. Отказ `authentication-required` на любом запросе переводит состояние в «не вошёл»; отказ неверного пароля — нет. Охрана маршрутов `signedIn(перенаправление)` и `withRole(роль, перенаправление)` ждёт, пока станет известно, кто вошёл. Код отказа сервера читается `authFailureCode`. Формы, тексты и оформление принадлежат проекту.

## Что ещё проект решает сам

16. <a id="REQ-AUTH-016"></a> **REQ-AUTH-016** — Открыты ли точки аутентификации для запроса — регистрация, подтверждение, повторное письмо, вход, сброс пароля, — решает проект портом `EntryAccess`; явная заглушка `EntryAccess.OPEN` оставляет их открытыми. Закрытая точка отвечает ошибкой ядра `entry-closed`, `403`; выдача токена CSRF и правило пароля остаются открытыми. Порт, а не правило в `ApiAccess`: правила проекта идут после открытых правил ядра, и одно широкое правило, поставленное раньше, молча закрыло бы вход. Основание — заявка потребителя, у которого аутентификация доступна только в «полном» режиме доступа по адресу сети.
17. <a id="REQ-AUTH-017"></a> **REQ-AUTH-017** — После подтверждения почты ядро публикует событие Spring `AccountVerified` (идентификатор и почта) — после фиксации транзакции: слушатель видит запись подтверждённой. Событие, а не порт: забытый слушатель ничего не ломает, он лишь не реагирует.
18. <a id="REQ-AUTH-018"></a> **REQ-AUTH-018** — Правило пароля отдаётся клиенту открытой точкой `GET /api/auth/policy`: нижний и верхний предел в байтах. Форма клиента не держит своей копии правила. Ключ проверки «человек ли это» — забота проекта.
19. <a id="REQ-AUTH-019"></a> **REQ-AUTH-019** — Пользователь меняет свой пароль точкой `POST /api/auth/password`, назвав текущий: неверный текущий — `credentials-rejected` и счёт неудач, как при входе; новый проходит правило пароля. Прочие сессии учётной записи завершаются, текущая остаётся.
23. <a id="REQ-AUTH-023"></a> **REQ-AUTH-023** — Почту меняют двумя путями. **Сам человек** — точкой `POST /api/auth/email`, назвав текущий пароль: неверный пароль — `credentials-rejected` и счёт неудач, как при входе; на новую почту уходит письмо со ссылкой (`platform.auth.links.email-change`, срок `platform.auth.tokens.email-change`, по умолчанию 24 ч), и запись переходит на новую почту только по ссылке — `POST /api/auth/email/confirm`. Ответ не раскрывает, занята ли почта (`REQ-AUTH-003`): на занятую письмо не уходит, а занятая за время ссылки отказывает при подтверждении кодом `email-taken`. **Администратор проекта** — `Accounts.changeEmail(id, email, locale)` сразу, с исходом `CHANGED`, `SAME`, `TAKEN` или `ABSENT`. В обоих путях почта приводится, как при регистрации, прежняя почта получает извещение после фиксации, прочие сессии завершаются — при смене самим человеком текущая остаётся. Прежняя почта не остаётся ни в журналах, ни в учётной записи; новая, пока ждёт ссылки, лежит в токене и стирается вместе с ним (`REQ-AUTH-013`). Добавлено 2026-09-25 по заявке потребителя.
24. <a id="REQ-AUTH-024"></a> **REQ-AUTH-024** — Учётную запись удаляет `Accounts.delete(id)`: роли и токены стираются вместе с ней, сессии завершаются, исход — `REMOVED`. Запись, которую держит внешний ключ проекта (`RESTRICT`) или неудалённые обращения центра поддержки (`REQ-SUPPORT-011`), не удаляется — исход `HELD`, а не исключение базы; записи нет — `ABSENT`. Удаление учётной записи — часть ответа на запрос субъекта по 152-ФЗ: данные проекта, которые на неё ссылаются, проект стирает до неё. Добавлено 2026-09-25 по заявке потребителя.
25. <a id="REQ-AUTH-025"></a> **REQ-AUTH-025** — `Accounts.withRole(role)` отдаёт незаблокированные учётные записи с объявленной ролью — не больше 1000, старые первыми; необъявленная роль — отказ. Так модуль ядра обращается ко всем операторам, не читая таблиц аутентификации ядра: центр поддержки извещает операторов колокольчиком (`REQ-NOTIFICATIONS`). Добавлено 2026-09-25.
26. <a id="REQ-AUTH-026"></a> **REQ-AUTH-026** — Завершённая сессия недействительна сразу, при любом ходе часов. Хранилище сессий удаляет мягко — ставит сессии нулевой срок бездействия и считает её истёкшей, когда текущее время не меньше последнего обращения; шаг системных часов назад, обычный для виртуальных машин, оставлял завершённую сессию действующей, пока часы не догонят этот момент. Поэтому ядро перед удалением переносит последнее обращение сессии в начало эпохи. Найдено 2026-09-25 нестабильными тестами на машине сборки: после сброса пароля и блокировки прочая сессия отвечала `200`.
27. <a id="REQ-AUTH-027"></a> **REQ-AUTH-027** — Стенд сценариев, который входит сотни раз с одного адреса, поднимает пределы настройкой `platform.rate-limit.scale` — множителем от 1 до 1000 для каждого предела ограничителя; окна не меняются. Множитель больше 1 служба называет предупреждением при запуске, а с активным профилем Spring `production` — каноническим именем рабочей среды (`REQ-DEPLOYMENT-019`) — не стартует: пределы рабочей среды — пределы ядра. Заменяемый ограничитель отвергнут: пустой ограничитель уехал бы в рабочую среду незамеченным. Добавлено 2026-09-25 по заявке потребителя.

## Контракт

20. <a id="REQ-AUTH-020"></a> **REQ-AUTH-020** — Точки аутентификации ядра описаны контрактом OpenAPI 3.1 `openapi/platform-auth.openapi.json`: пути, схемы запросов и ответов, `ProblemDetail`, коды отказов у каждого ответа расширением `x-codes`, заголовок `X-Api-Version`. Контракт поставляется в `platform-auth` и копией в `@apocarteres/auth`. Тест ядра держит контроллер в соответствии с контрактом — пути, тела запросов, поля, коды и их статусы; типы клиента выводятся из контракта, и тест не даёт им отстать. Код у потребителя из контракта не генерируется: проект подключает контракт в свою спецификацию для описания — ссылкой либо `OpenApiCustomizer` — по образцам инструкции. Инструмент выпуска сверяет контракт двух версий: снятая точка, снятый ответ успеха, снятое поле и новое обязательное поле — несовместимость (`REQ-PUBLISHING-015`). Профиль проекта ядру не принадлежит: `GET /api/auth/me` отдаёт только учётную запись, профиль проект отдаёт своей точкой. Решение владельца от 2026-09-24, идея `CORE-IDEA-001`.
21. <a id="REQ-AUTH-021"></a> **REQ-AUTH-021** — Профиль регистрации — класс проекта: `RegistrationHook<P>` называет его методом `profile()`. Ядро разбирает `profile` запроса в этот класс и проверяет его аннотациями Bean Validation **до** транзакции; чужое поле, неразборчивое и неверное значение — отказ `profile-rejected`, `400`, с именами полей без значений. `Accounts.create` принимает профиль экземпляром класса либо словарём, профиль первого администратора — словарь из настроек; оба проходят тот же разбор. `RegistrationHook.NONE` объявляет пустой профиль `NoProfile`: любое поле — отказ. В контракте ядра `profile` открыт; схему задаёт проект, сужая её в своей спецификации (`allOf`). Клиент передаёт профиль своим типом: `register<P>(почта, пароль, профиль)`.
