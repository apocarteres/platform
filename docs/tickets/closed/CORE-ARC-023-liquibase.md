# Инструмент переходов базы — Liquibase, журналы таблиц ядра — от ядра

## Проблема

Ядро владеет таблицами своих модулей: учётные записи, токены, ключи
доступа, уведомления, центр поддержки, замок работы. Но отдаёт их только
образцами `create-*.sql` с указанием «создайте своим переходом базы».
Потребители выбирают инструмент сами, одни Liquibase, другие Flyway, и
каждый переписывает образцы в свой инструмент и свой порядок. Изменение
таблицы ядром превращается в ручную миграцию у каждого потребителя. Так
было со столбцом `email` в 10.0.0 и с таблицей `platform_access_key`
в 12.2.0.

## Подтверждение

Наблюдение владельца от 2026-09-30: часть потребителей ведёт переходы во
Flyway, часть — в Liquibase. В требованиях ядра инструмент не назван.
Правило `migration-labels` (`REQ-DEPLOYMENT-026`) читает метки из
комментариев SQL.

## Последствия при сохранении текущего поведения

Каждое изменение таблиц ядра — ручной перенос у каждого потребителя, и
расхождения между переносами никто не сверяет. Правила ядра о переходах
приходится держать для двух инструментов сразу.

## Решение владельца

Решение владельца от 2026-09-30: инструмент переходов базы — Liquibase.

Довод помимо привычки: переходы ядра и проекта должны складываться из
нескольких библиотек. У Flyway одна глобальная последовательность версий
(`V1`, `V2`, …), и номера переходов ядра и проекта конфликтуют. У Liquibase
идентификатор и автор задаются на каждый набор изменений (changeset), журнал
ядра подключается `include` из classpath, и порядок задан явно. Штатные
`labels` и `contexts` заменяют метки в комментариях, есть предусловия и
откат.

## Требуется

1. Директива в `REQ-DATA-ACCESS`: инструмент переходов базы — Liquibase.
   Версию закрепляет ядро (`REQ-DEPS-001`).
2. Журналы Liquibase для таблиц ядра в каждом модуле, владеющем таблицами:
   `platform-auth`, `platform-notifications`, `platform-support`,
   `platform-persistence`. Потребитель подключает их `include`. Образцы
   `create-*.sql` остаются справкой. Начать с `platform-auth`: этот модуль
   есть у всех потребителей.
3. Обязательство ядра для проектов на Flyway: переезд на Liquibase со сроком
   в 3 выпуска. Инструкция: `changelogSync` для уже применённых переходов,
   дальше переходы только в Liquibase. Проектам без базы ничего делать не
   нужно, и обязательство это называет.
4. Правило: Flyway в зависимостях проекта — отказ с ссылкой на обязательство.
5. `migration-labels` читает `labels` наборов изменений Liquibase. Метки в
   комментариях SQL — только до конца срока обязательства.
6. Смена таблиц ядра после перехода — новым набором изменений в журнале
   ядра. Это выпуск со сменой поведения; при смене версий компонентов
   действует `REQ-DEPS-010`.

## Критерии приёмки

- Тест первым: журнал ядра на чистой базе создаёт те же таблицы, что образцы
  `create-*.sql`, и тесты модулей идут на схеме из журнала, а не из образцов.
- Тест: проект с Flyway в зависимостях получает отказ правила, который
  называет обязательство.
- Тест: база, созданная из образцов, после `changelogSync` принимает журнал
  ядра без изменений схемы.
- Пробы: снятое правило, пропущенный набор изменений — тесты падают.

## Вопросы

1. Формат журнала ядра: YAML или XML. Ответ: YAML (решение владельца от 2026-09-30).
2. Идентификаторы наборов изменений ядра: схема имени, чтобы они никогда не
   совпали с наборами проекта. Ответ: `<модуль>:<трёхзначный номер>-<предмет>`,
   например `platform-auth:001-account`, автор — `platform` (решение владельца
   от 2026-09-30).
