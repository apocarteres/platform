# Резервные копии данных службы: объявление и проверки

## Проблема

Ядро говорит о копиях одним положением — `REQ-DEPLOYMENT-005`: копия
снимается до установки новых артефактов. Регулярная копия данных службы не
описана: что копируется, куда, как долго хранится, в каком состоянии
задание и как проверяется восстановление. Каждый потребитель решает это сам,
и решение живёт вне репозитория.

## Подтверждение

Заявка потребителя [issue #46](https://github.com/apocarteres/platform/issues/46)
по чтению рабочего хоста 2026-09-24:

- копия базы — скрипт хоста вне репозитория, общий для двух потребителей
  (`pg_dumpall` кластера, 90 дней, внешнее хранилище не объявлено нигде);
- юнит и таймер копии файлов доставлены развёртыванием (`REQ-DEPLOYMENT-020`),
  но таймер выключен: копия файлов не снималась ни разу, замечено только
  осмотром хоста.

Сверено с ядром 2026-09-25: кроме `REQ-DEPLOYMENT-005` о копиях положений нет;
`REQ-DEPLOYMENT-020` доставляет описание службы, но состояние «включено» не
объявляет и не сверяет; ни одна команда ядра о копиях не спрашивает.

## Последствия при сохранении текущего поведения

Потеря данных обнаруживается при попытке восстановления. Проверка ядра
зелёная, а копии нет.

## Решения владельца

Решения владельца от 2026-09-25 — объявление и проверки, без перевозки, как в
`REQ-DEPLOYMENT-020`:

1. **Объявление.** Раздел `backups` в `.conventions.json`: по записи на набор
   данных — вид (база, файлы, иное), расписание, срок хранения, имя внешнего
   хранилища; адрес и учётные данные — из окружения хоста, не из репозитория.
   Проект со службой и данными обязан объявить копии: обязательство ядра на
   3 выпуска.
2. **Включено, а не лежит.** Составляющая объявляет `enable: true`: скрипт
   развёртывания включает таймер, сверка после установки проверяет, что он
   включён.
3. **Проверка.** Задание копии пишет квитанцию — время, размер, отпечаток;
   `conventions backups --check` на хосте отказывает, если копия старше
   расписания с запасом или восстановление не проверялось дольше 90 дней
   (срок объявляет проект); проверку восстановления отмечает
   `conventions backups --restored`.
4. **Общий хост.** Каждый проект копирует свою базу сам (`pg_dump` своей
   базы) со своим сроком; общее для кластера — роли и настройки — копирует
   задание хоста, а не проект.
5. **Персональные данные (152-ФЗ).** Срок хранения копий конечен; удаление по
   запросу субъекта до копий не доходит — они стираются по сроку, и требование
   говорит это прямо, чтобы проект записал это в соглашении.

## Требуется

1. Требование о копиях данных службы в `REQ-DEPLOYMENT` или отдельным
   документом, с обязательством `backups`.
2. Разбор и проверка раздела `backups`; поле `enable` у составляющей и его
   сверка.
3. Команда `conventions backups` с `--check` и `--restored`; формат квитанции.
4. Инструкция: задание копии проекта, квитанция, внешнее хранилище, проверка
   восстановления.

## Критерии приёмки

- Тесты разбора объявления, квитанции, сроков, включённости.
- Пробы намеренной поломкой: просроченная копия, выключенный таймер,
  бессрочное хранение, давняя проверка восстановления — каждую ловит тест.
- Выпуск — старшая версия: новое правило и обязательство могут сделать
  `check` потребителя красным.
