# Проверки качества

[Карта требований](../REQUIREMENTS.md)

Документ нормативен для платформы и для всех проектов, подключивших пакет `@apocarteres/project-conventions`. Он не копируется в репозитории потребителей: пакет доставляет этот файл вместе с собой.

**Область действия: проверки любого сервиса.** Требования не зависят от языка.

**Уровень требования: директива.**

## Два набора

1. <a id="REQ-QUALITY-001"></a> **REQ-QUALITY-001** — Проверки собраны в два набора с фиксированными именами задач: `check` — быстрый шлагбаум перед отправкой изменений, `verify` — всё, что вообще проверяется локально. Третьего набора нет: проверка, не входящая ни в один из них, не выполняется никогда.
2. <a id="REQ-QUALITY-002"></a> **REQ-QUALITY-002** — `check` содержит проверку документации, проверку правил, модульные тесты всех компонентов, проверку проводки (`REQ-QUALITY-012`) и статический разбор с отказом на предупреждениях. Он обязан оставаться быстрым: минуты, а не десятки минут. Статический разбор назван поимённо, а не оставлен на усмотрение проекта: требование без названного набора остаётся пожеланием, и это подтверждено — у потребителя оно годами выполнялось для одного компонента из трёх, а у ядра, которое его предъявляло, ни для одного. Проект волен не пользоваться тем или иным языком, но если пользуется — набор для этого языка определяет ядро. Поддерживаемые языки и наборы: Java — `-Xlint:all` с `-Werror` и разбор исходников `ErrorProne`; TypeScript и JavaScript — `ESLint` с типовым разбором, где есть типы; Rust — `clippy` с отказом на предупреждениях. Язык, которого нет в перечне, — повод для заявки в ядро, чтобы ядро его поддержало, а не повод проекту выводить свой набор: иначе каждый выводит заново и выводит по-разному. Разбор роняет сборку сам, а не сообщает находки в отчёт: результат читается кодом возврата (`REQ-QUALITY-008`). Существующие находки засеиваются ограничителем (`REQ-QUALITY-007`) — без права на засев отказ на предупреждениях неисполним: доля шума у инструментов различается на порядок. Автоматическая правка разбора — предложение, а не исправление: она проходит разбор изменения наравне с рукописной, потому что инструмент рассуждает о чтении значения и не рассуждает о побочном действии. Порядок внедрения и эксплуатационные подробности — [инструкция](../runbooks/static-analysis.md). Решение владельца от 2026-09-15 по заявке потребителя.
3. <a id="REQ-QUALITY-003"></a> **REQ-QUALITY-003** — `verify` содержит `check` целиком плюс интеграционные тесты, требующие внешних служб, сборку всех компонентов, аудит зависимостей, контрактные тесты скриптов и сканирование секретов. Тест, которому внешние службы не нужны, живёт в `check`: относить его к `verify` значит выводить из-под шлагбаума то, что можно проверить за секунды.
4. <a id="REQ-QUALITY-012"></a> **REQ-QUALITY-012** — Проверка проводки поднимает контекст приложения каждого рантайма без внешних служб: без базы, брокера, сети и учётных данных. Рантаймом считается каждый способ запуска компонента — веб-приложение, консольная команда, обработчик очереди; у библиотеки — контекст с её автоконфигурацией. Проверка отвечает на один вопрос: поднимается ли приложение вообще. Отказ такого рода — отсутствующий бин, условная конфигурация, не сработавшая в этом рантайме, несошедшиеся границы транзакций — виден только при запуске, поэтому набор `check` без него оставляет класс поломок за шлагбаумом: зелёная проверка читается как «можно отправлять», хотя приложение не запускается. Основание — задача `CORE-OPS-021` и случай потребителя, где бины двух шифров были объявлены в веб-условной конфигурации: веб работал, `check` был зелёным, а команда провижининга не поднималась вовсе.
5. <a id="REQ-QUALITY-004"></a> **REQ-QUALITY-004** — Шлагбаум перед отправкой изменений ставится хуком `pre-push`, который выполняет `check`. Хук устанавливается задачей менеджера окружения и не хранит собственной логики проверок. Хук сверяет и сообщения коммитов **отправляемого диапазона**: коммит, не называющий задачу, не должен становиться общим, потому что после отправки его исправление стоит дороже (`REQ-RELEASE-041`). Сверяется именно диапазон, а не вся история, и это существенно: сверка истории целиком не дала бы отправить ничего проекту, у которого такой коммит уже отправлен, — то есть наказывала бы за прошлое, которое правилом уже не исправить. Диапазон хук получает от системы контроля версий, отдельной настройки это не требует. Решение владельца от 2026-09-17 по заявке потребителя.

## Что проверки обязаны делать

6. <a id="REQ-QUALITY-005"></a> **REQ-QUALITY-005** — Отказ проверки называет файл и место. Проверка, сообщающая только «не пройдено», считается недоделанной.
7. <a id="REQ-QUALITY-006"></a> **REQ-QUALITY-006** — Порог проверки не снижается ради прохождения: ни ослаблением уровня важности находки, ни общим исключением, ни отключением шага. Исключение оформляется задачей с указанием предмета, причины, компенсирующей меры и срока снятия. Послабление для тестового кода исключением не считается и срока снятия не имеет: это объявленное постоянное свойство тестовой компиляции с записанной причиной. Подложный объект приходится передавать за сотрудника, которого тест не задействует; ожидание идёт через другой держатель; подстановка пустого значения в тесте часто и есть предмет проверки. Это не долг, который когда-нибудь вернут, и требование срока приучало бы писать срок для вида. Послабление объявляется один раз на набор тестовой компиляции, а не на месте употребления, и на рабочий код не распространяется ни при каких условиях: именно разделение двух наборов делает постоянное послабление безопасным. Без него разбор начинает диктовать устройство теста из соображений, к предмету теста отношения не имеющих. Решение владельца от 2026-09-15 по заявке потребителя.
8. <a id="REQ-QUALITY-007"></a> **REQ-QUALITY-007** — Существующие нарушения фиксируются храповиком и могут только убывать. Первичное засеивание разрешено; рост требует явного ключа и объяснения. Единица, которую ограничитель считает, зависит от разбора и объявляется вместе с ним. Там, где находки могут только убывать, единица — их счёт. Там, где не могут, единица — множество объявленных послаблений. Разбор необязательности перемещает находки, а не устраняет их: объявляя поле необязательным, вы сообщаете это всем вызывающим, находки уходят из размеченного типа и появляются у них, и счёт при верной работе стоит на месте. Послаблением считается всё, что выведено из-под разбора: непомеченный пакет, объявленное в коде разрешение, запись в файле исключений. Множество засеивается один раз и может только убывать; что делается со счётом находок внутри разобранной части, ограничителя не касается. Ограничитель, считающий не ту единицу, запрещает верный путь внедрения, и это уже случилось: правило в прежней редакции требовало явного ключа и объяснения на каждый шаг верной работы. Решение владельца от 2026-09-15 по заявке потребителя.
9. <a id="REQ-QUALITY-008"></a> **REQ-QUALITY-008** — Результат проверки читается кодом возврата задачи, а не глазами по выводу. Конвейер, скрывающий код возврата, в проверках запрещён.

13. <a id="REQ-QUALITY-013"></a> **REQ-QUALITY-013** — Доставляемая настройка разбора объявляет нужные ей правила поимённо и на состав групп инструмента не полагается. Состав групп принадлежит инструменту, а не ядру, и меняется между версиями; правило, работавшее потому, что попало в группу, на новой версии молчит. Отказ при этом бесшумный и неотличим от чистоты: настройка лежит на месте, задаёт правилу данные, проверка зелёная, а запрет не действует. Это уже случилось: запрет обращений к стенным часам в Rust держался на членстве `disallowed_methods` в группе `clippy::all`; на закреплённом ядром наборе правило работало, у потребителя на более новом — нет, и ноль находок при двадцати восьми обращениях выглядел как успех. Проверка ядром на своей закреплённой версии этого не ловит по устройству: она подтверждает работу там, где всё и так работает. Решение владельца от 2026-09-18 по заявке потребителя.

14. <a id="REQ-QUALITY-014"></a> **REQ-QUALITY-014** — Принятие доставленной проверки подтверждается заведомым нарушением: проект вносит нарушение, убеждается, что проверка отказывает, и снимает его. Зелёная проверка сама по себе доказательством не является — ровно как зелёная проверка после правки (`REQ-QUALITY-011`), — потому что она одинаково выглядит и когда нарушений нет, и когда проверка ни к чему не подключена. Подтверждение делается один раз при принятии и в набор проверок не входит: его предмет — что проверка жива, а не что код чист. Решение владельца от 2026-09-18 по заявке потребителя.

## Устойчивость проверок

10. <a id="REQ-QUALITY-009"></a> **REQ-QUALITY-009** — Тест, исход которого зависит от момента запуска, машины или порядка выполнения, считается дефектом и получает задачу. Неустойчивый тест не «перезапускается до зелёного»: причина называется и подтверждается измерением.
11. <a id="REQ-QUALITY-010"></a> **REQ-QUALITY-010** — Утверждение о времени выполнения выражается через состояние, а не через предел на часах, если состояние доступно. Предел на часах допустим только как грубая защита от регрессии, с запасом, не спорящим с нагрузкой машины.
12. <a id="REQ-QUALITY-011"></a> **REQ-QUALITY-011** — Зелёная проверка после правки доказательством не является, пока не показано, что до правки отказ воспроизводился.

15. <a id="REQ-QUALITY-015"></a> **REQ-QUALITY-015** — Автонастройка не решает условием о бине, который регистрирует другая автонастройка. `@ConditionalOnBean` и `@ConditionalOnSingleCandidate` видят только то, что зарегистрировано к моменту их вычисления, а порядок автонастроек условию не принадлежит: условие вычисляется раньше — бин молча не создаётся. Нужный бин берётся поставщиком `ObjectProvider` в методе бина: метод исполняется после того, как объявлены все бины, и порядок на него не влияет. Объявление порядка условие не спасает: оно перечисляет известные автонастройки и молчит о неизвестных, поэтому тот же отказ возвращается при первой чужой поставке, регистрирующей тот же бин. Отказ такого рода не виден ничем: ответы правильны, требование выглядит исполненным, а наблюдаемости нет — счётчик ошибок `api.errors` у потребителя не писался с самого перехода на поставку и обнаружился сверкой перечня метрик с ожидаемым. Доказательством служит контекст с той автонастройкой, которая регистрирует нужный бин, и наблюдаемое следствие — счётчик сдвинулся; модульный тест класса такой дефект не ловит, потому что дефект живёт целиком в порядке. Контекст, где бин объявлен потребителем, доказательством не служит: бины потребителя регистрируются раньше автонастроек, и условие на них срабатывает — именно так проверка ядра была зелёной при неработающей метрике. Правило `wiring-conditions` проверяет это в `check`. Основание — заявка потребителя от 2026-09-21.

16. <a id="REQ-QUALITY-016"></a> **REQ-QUALITY-016** — Каждое правило ядра показано на формах своих потребителей, а не на той, которую ядро себе представило. Эталонный потребитель собирается в двух формах: контейнеры с агентом на Rust и служба на хосте с настройкой веб-сервера и описанием службы; в обеих — клиент с лениво загружаемыми страницами, модуль Java с родителем ядра, доставленный словарь. На чистой форме ни одно правило не находит ничего; на форме с заложенным нарушением каждое правило его находит. Правило без закладки на форме — отказ проверки, если нет названной причины, почему правило к форме не относится. Основание — разбор заявок за 2026-09-11–22: шесть раз проверка ядра была зелёной при неисполненном требовании, потому что проверялся только тот случай, который ядро держало в уме, — только архив классов (#28), только страницы значением (#33), только Rust без времён жизни (#23), только реестр, объявленный потребителем (#25); и всякий раз дефект находил потребитель сверкой, а не отказ проверки. Сборка форм сразу нашла две слепые зоны самого эталона: он не получал словаря, и правила о терминах на нём ничего не проверяли, и не содержал манифеста Java, и разбор Java проходил на нём впустую.
