# Вход в ядре: учётная запись, регистрация, сессия, роли проекта

## Проблема

Оба потребителя написали вход сами и почти одинаково: почта и пароль в
BCrypt, роли `USER` и `ADMIN`, подтверждение почты, сброс пароля с
завершением всех сессий, Spring Session в Redis, CSRF через cookie,
reCAPTCHA v3, ограничение частоты на счётчиках Redis, блокировка
администратором. У каждого 1,1–1,4 тыс. строк на сервере и отдельно клиент.

Расходится то, что расходиться не должно:

- пароль ограничен у одного только максимумом в 16 знаков, у другого — от 10
  до 200;
- у одного срок сессии в настройке 8 ч, а в требовании 24 ч; SameSite в
  настройке `strict`, в коде `Lax`;
- индекс сессий по почте у одного — отпечатком, у другого — открытым
  текстом;
- сроки токенов и ограничения частоты разные без причины.

## Решение владельца

Решение владельца от 2026-09-24:

- Ядро поставляет вход **библиотекой**: у каждого продукта свои пользователи,
  механика одна. Единого входа на все продукты не делаем.
- Проект объявляет свои роли.
- Первый выпуск — почта и пароль, подтверждение почты, сброс пароля, сессии,
  роли, блокировка, ограничение частоты, требование `REQ-AUTH`. Внешние
  способы входа, второй фактор и токены API — позже.
- Вход делается раньше центра поддержки (CORE-ARC-012 на паузе); поддержка
  строится поверх него.

## Требуется

**Сервер — starter `platform-auth`:**

1. Учётная запись ядра: почта, хеш пароля, подтверждение, блокировка, роли,
   время создания и последнего входа. Доменный профиль проекта (игрок,
   клиент) ссылается на неё.
2. Точки HTTP под `/api/auth/*`: регистрация, подтверждение, повторное
   письмо, вход, выход, текущая учётная запись, выдача токена CSRF, запрос и
   подтверждение сброса. Ответ не раскрывает, есть ли такая почта.
3. Одноразовые токены действий одной таблицей с назначением, в базе —
   отпечаток; действует последний непогашенный.
4. Сессии Spring Session в Redis; индекс по учётной записи без почты в
   открытом виде; смена идентификатора сессии при входе; все сессии
   завершаются при сбросе пароля и блокировке.
5. Роли объявляет проект; ядро хранит назначение и даёт проверку. Роль при
   регистрации — объявленная по умолчанию.
6. Порты с явным решением, как у модальных окон: письма входа, проверка
   «человек ли это» (явная заглушка, если проекту она не нужна), действие при
   регистрации в той же транзакции (создать игрока, открыть счёт).
7. Ограничение частоты на Redis — отдельным модулем: оба проекта пользуются
   им и вне входа.
8. Java API для экранов администратора проекта: блокировка, назначение роли,
   первый администратор из окружения.

**Клиент — пакет `@apocarteres/auth`,** логика без вида: состояние сессии,
вход, выход, регистрация, сброс; охрана маршрутов по входу и роли; токен CSRF
до первого изменяющего запроса; связь с `sessionExpiredInterceptor`. Формы
рисует проект.

**Требование `REQ-AUTH`:**

- сроки токенов и сессии;
- правило пароля — с учётом предела BCrypt в 72 байта;
- ограничения частоты;
- отказ без раскрытия почты;
- письма вне транзакции;
- персональные данные (152-ФЗ): почта и адрес сети не попадают в журналы и
  метрики, сроки хранения токенов и журнала входа.

**Переход потребителей:** перенос пользователей в учётные записи ядра. Хеши
BCrypt совместимы — сброса паролей не нужно; доменная таблица получает ссылку
на учётную запись.

## Открытые вопросы

1. Тип ключа учётной записи: UUID (у одного потребителя сейчас `long`, у
   другого UUID). Ответ: UUID; доменный профиль сохраняет свой ключ и
   ссылается на учётную запись.
2. Роли: набор ролей на учётную запись или одна роль (сейчас у обоих одна).
   Ответ: набор ролей.
3. Письма входа: текст даёт проект портом (у ядра нет бренда и перевода) или
   ядро держит шаблоны. Ответ: порт; позже письма уходят в сервис
   уведомлений.
4. Значения по умолчанию: пароль от 10 до 72 байт; сессия 8 ч без действий;
   токен подтверждения 24 ч, сброса 30 мин. Ответ: принять, проект
   переопределяет.

Ответы — решения владельца от 2026-09-24.

## Что сделано

- `platform-rate-limit`: `RateLimit`, `RateLimiter` на Redis одним скриптом,
  субъект отпечатком, `rate-limited` 429 с `Retry-After`, `rate-limit-unavailable`
  503 при недоступном хранилище.
- `platform-auth`: учётная запись ядра с набором ролей проекта, точки
  `/api/auth/*`, токены действий отпечатком с последним действующим, сессии
  Spring Session в Redis с индексом по идентификатору, CSRF через cookie, порты
  `AuthLetters`, `HumanCheck`, `RegistrationHook`, `ApiAccess` с явными
  заглушками, Java API `Accounts`, первый администратор из окружения, образцы
  таблиц `sql/platform-auth/create-*.sql`.
- `@apocarteres/auth`: `provideAuth`, `AuthSession`, `authInterceptor`,
  `signedIn`, `withRole`, `authFailureCode`.
- Требование `REQ-AUTH-001…015`; обязательство `core-auth` на 3 выпуска.
- `platform-web-errors` не менялся: коды входа идут через `CodedFailure`
  (`REQ-API-011`).

## Чем закреплено

- 12 тестов полного цикла на настоящих Postgres и Redis в контейнере, 6 тестов
  ограничителя, проверки границ модулей; 9 тестов клиента.
- Пробы намеренной поломкой: 24 на сервере, 8 на клиенте. Шесть сначала не
  различали и получили свои тесты: письмо вне транзакции (признак
  `isActualTransactionActive` в `afterCommit` ложен — видимость проверяется с
  другого соединения), смена сессии при повторном входе, пароль раньше
  состояния записи, действует только последняя ссылка, охрана маршрутов ждёт
  ответа. Две пробы были сломаны сами и отвергнуты Error Prone.
- Проверка границ модулей нашла ссылки на внутренние классы автонастроек
  других модулей — порядок теперь задан именами.
